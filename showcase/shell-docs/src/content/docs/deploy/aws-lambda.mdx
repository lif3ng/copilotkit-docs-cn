CopilotKit 运行时本质上是一个 Fetch 处理器，因此不需要服务器就能跑在 Lambda 上。唯一需要上心的是**流式传输**：聊天响应以 Server-Sent Events 的形式送达，而一个会做缓冲的入口（front door）会把一场实时对话变成一段漫长的停顿，随后整个回复一次性涌出。

## 从这里开始：选对入口

| 入口 | 是否支持 SSE 流式？ | 适用场景 |
| --- | --- | --- |
| 带 `InvokeMode: RESPONSE_STREAM` 的 **Lambda Function URL** | 是 | 默认之选。浏览器与函数之间没有任何中间环节。 |
| 带 `responseTransferMode: STREAM` 的 **API Gateway REST API** | 是 | 你需要在运行时前面使用 REST API 特性——WAF、用量计划、自定义授权方，或要扩展的既有 REST API。 |
| API Gateway **HTTP** API | 否 | 响应流式仅限 REST API。缓冲模式：上限 10 MB，超时 29 秒。 |
| Application Load Balancer | 否 | ALB 对 Lambda 目标没有流式通道。 |

<Callout type="warn" title="每条路径上的流式传输都需显式开启">
  两种流式入口默认都开启缓冲——Function URL 默认使用 `BUFFERED` 调用模式，
  API Gateway 集成默认使用 `responseTransferMode: BUFFERED`。不打开开关就直接部署，
  聊天会在智能体运行的整段时间里看似卡死，然后一次性倾倒出完整回复。
</Callout>

下面两种流式路径的处理函数代码完全相同；差异只在事件结构与基础设施配置。

## 支持响应流式的 Function URL

响应流式需要满足三个条件：一个调用模式设为 `RESPONSE_STREAM` 的 Function URL、一个由 `awslambda.streamifyResponse` 包装的处理函数，以及 20 或更高版本的 Node.js 托管运行时。AWS 自 Node.js 18 起就支持响应流式，但 `@copilotkit/runtime` 要求 Node.js 20。

### 1. 处理函数

Lambda Function URL 以负载格式 2.0 送达事件。把它转换成 `Request`，交给 CopilotKit 处理函数，再把 `Response` 响应体接入 Lambda 响应流。

```ts title="src/handler.ts"
import { Readable } from "node:stream";
import { pipeline } from "node:stream/promises";
import type { LambdaFunctionURLEvent } from "aws-lambda";
import {
  CopilotRuntime,
  createCopilotRuntimeHandler,
  BuiltInAgent,
} from "@copilotkit/runtime/v2";

// Created once per container, reused across warm invocations.
const runtime = new CopilotRuntime({
  agents: {
    default: new BuiltInAgent({ model: "openai/gpt-4o-mini" }),
  },
});

const copilotHandler = createCopilotRuntimeHandler({
  runtime,
  basePath: "/api/copilotkit",
  cors: true,
});

function toFetchRequest(event: LambdaFunctionURLEvent): Request {
  const method = event.requestContext.http.method;
  const host = event.headers.host ?? "localhost";
  const query = event.rawQueryString ? `?${event.rawQueryString}` : "";

  const hasBody = method !== "GET" && method !== "HEAD" && event.body != null;

  return new Request(`https://${host}${event.rawPath}${query}`, {
    method,
    headers: new Headers(event.headers as Record<string, string>),
    body: hasBody
      ? event.isBase64Encoded
        ? Buffer.from(event.body!, "base64")
        : event.body
      : undefined,
  });
}

export const handler = awslambda.streamifyResponse(
  async (event: LambdaFunctionURLEvent, responseStream) => {
    const response = await copilotHandler(toFetchRequest(event));

    // Status and headers must be attached before the first byte is written.
    const stream = awslambda.HttpResponseStream.from(responseStream, {
      statusCode: response.status,
      headers: Object.fromEntries(response.headers),
    });

    if (!response.body) {
      stream.end();
      return;
    }

    // Readable.fromWeb bridges the Fetch ReadableStream to a Node stream, so
    // SSE chunks reach the client as the agent produces them.
    await pipeline(Readable.fromWeb(response.body as any), stream);
  },
);
```

`awslambda` 是托管 Node.js 运行时注入的全局变量，因此需要让 TypeScript 知道它的存在：

```ts title="src/awslambda.d.ts"
import type { Writable } from "node:stream";

declare global {
  namespace awslambda {
    function streamifyResponse<TEvent>(
      handler: (event: TEvent, responseStream: Writable, context: unknown) => Promise<void>,
    ): (event: TEvent, responseStream: Writable, context: unknown) => Promise<void>;

    namespace HttpResponseStream {
      function from(
        stream: Writable,
        metadata: { statusCode: number; headers?: Record<string, string> },
      ): Writable;
    }
  }
}

export {};
```

### 2. 设置调用模式

流式传输默认关闭。Function URL 必须在创建时就带上 `InvokeMode: RESPONSE_STREAM`——之后再想改，需要更新的是 URL 配置，而不是函数本身。

<Tab value="AWS CLI">
```bash
aws lambda create-function-url-config \
  --function-name copilotkit-runtime \
  --auth-type NONE \
  --invoke-mode RESPONSE_STREAM \
  --cors '{"AllowOrigins":["https://myapp.com"],"AllowHeaders":["content-type","authorization"],"AllowMethods":["GET","POST"]}'
```
</Tab>
<Tab value="AWS CDK">
```ts title="lib/stack.ts"
import { NodejsFunction } from "aws-cdk-lib/aws-lambda-nodejs";
import { Runtime, FunctionUrlAuthType, InvokeMode } from "aws-cdk-lib/aws-lambda";
import { Duration } from "aws-cdk-lib";

const fn = new NodejsFunction(this, "CopilotKitRuntime", {
  entry: "src/handler.ts",
  runtime: Runtime.NODEJS_22_X,
  // Long enough for a full agent run; Lambda's ceiling is 15 minutes.
  timeout: Duration.minutes(5),
  memorySize: 1024,
  environment: {
    OPENAI_API_KEY: process.env.OPENAI_API_KEY!,
  },
});

fn.addFunctionUrl({
  authType: FunctionUrlAuthType.NONE,
  invokeMode: InvokeMode.RESPONSE_STREAM,
  cors: {
    allowedOrigins: ["https://myapp.com"],
    allowedHeaders: ["content-type", "authorization"],
  },
});
```
</Tab>

<Callout type="info" title="关于显式的 useSingleEndpoint">
  上面的 Function URL 处理函数提供的是多路由（multi-route）模式，即默认模式。
  省略该 prop 时，`<CopilotKit>` 与 `<CopilotKitProvider>` 都会协商传输方式，
  因此这里的 `{false}` 是可选的：它的作用是直接锁定多路由 REST 路由，而不是去逐一探测。
  如果你选择的是下文的缓冲入口，并以 `mode: "single-route"` 挂载了处理函数，那么可以去掉这个 prop。参见
  [提供方与处理器配对](/backend/runtime-endpoints#provider-and-handler-pairs)。
</Callout>
</FrontendOnly>

<FrontendOnly frontend="angular">
```ts title="src/app/app.config.ts"

  runtimeUrl: "https://<url-id>.lambda-url.<region>.on.aws/api/copilotkit",

```
</FrontendOnly>

<Callout type="info" title="验证流式是否真正生效">
  在 run 端点上执行 `curl -N`，应当能看到 SSE 事件逐步输出。如果整个响应体一次性到达，
  说明流式并未生效——请检查 Function URL 的调用模式是否为 `RESPONSE_STREAM`，
  以及它前面是否还坐着一层会缓冲的东西（HTTP API、ALB，或未配置流式的 CloudFront 分发）。
</Callout>

## 支持响应流式的 API Gateway REST API

REST API 自 2025 年 11 月起支持响应流式。该能力按集成单独开启且默认关闭：把 `responseTransferMode` 设为 `STREAM` 后，API Gateway 会通过 [`InvokeWithResponseStream`](https://docs.aws.amazon.com/lambda/latest/api/API_InvokeWithResponseStream.html) 调用函数，并随字节到达即时转发，这同时解除了缓冲式集成适用的 10 MB 响应上限与 29 秒集成超时。

如果你想在运行时前面使用 REST API 特性，就走这条路径。否则，上文的 Function URL 要配置的东西更少。

### 1. 将处理函数适配到负载格式 1.0

处理函数中流式的那一半保持不变——`awslambda.streamifyResponse` 与 `HttpResponseStream.from` 输出的正是 API Gateway 所期望的“元数据加分隔符”格式。变化的是事件：REST 代理集成送达的是负载格式 1.0，而不是 Function URL 发送的 2.0 形态。

```ts title="src/handler.ts"
import type { APIGatewayProxyEvent } from "aws-lambda";

// REST proxy integrations deliver payload format 1.0: `httpMethod` and `path`
// rather than `requestContext.http.method` and `rawPath`. `path` excludes the
// stage name, which is what we want — it lines up with the runtime's basePath.
function toFetchRequest(event: APIGatewayProxyEvent): Request {
  const method = event.httpMethod;
  const headers = new Headers();
  for (const [name, value] of Object.entries(event.headers)) {
    if (value != null) headers.append(name, value);
  }

  const query = new URLSearchParams();
  for (const [name, values] of Object.entries(
    event.multiValueQueryStringParameters ?? {},
  )) {
    for (const value of values ?? []) query.append(name, value);
  }
  const search = query.toString();

  const hasBody = method !== "GET" && method !== "HEAD" && event.body != null;

  return new Request(
    `https://${headers.get("host") ?? "localhost"}${event.path}${search ? `?${search}` : ""}`,
    {
      method,
      headers,
      body: hasBody
        ? event.isBase64Encoded
          ? Buffer.from(event.body!, "base64")
          : event.body
        : undefined,
    },
  );
}
```

Function URL 一节中的 `awslambda.streamifyResponse(...)` 代码块可以原样叠加在此之上。

### 2. 配置集成

有三个设置很关键：Lambda **代理**（`AWS_PROXY`）集成、以 `/response-streaming-invocations` 结尾的 URI，以及 `responseTransferMode: STREAM`。非代理集成类型不支持流式传输。

<Tabs groupId="iac" items={["AWS CLI", "AWS CDK", "AWS SAM"]}>
<Tab value="AWS CLI">
对于既有集成，同时修补 URI 与传输模式，然后重新部署阶段：

```bash
aws apigateway update-integration \
  --rest-api-id a1b2c3 \
  --resource-id aaa111 \
  --http-method ANY \
  --patch-operations '[
    {"op":"replace","path":"/uri","value":"arn:aws:apigateway:us-east-1:lambda:path/2021-11-15/functions/arn:aws:lambda:us-east-1:111122223333:function:copilotkit-runtime/response-streaming-invocations"},
    {"op":"replace","path":"/responseTransferMode","value":"STREAM"},
    {"op":"replace","path":"/timeoutInMillis","value":"900000"}
  ]'

aws apigateway create-deployment --rest-api-id a1b2c3 --stage-name prod
```

注意 URI 路径中的 API 版本：是 `2021-11-15/.../response-streaming-invocations`，而不是缓冲式 Lambda 代理集成所用的 `2015-03-31/.../invocations`。权限保持不变——`InvokeWithResponseStream` 针对 `lambda:InvokeFunction` 进行授权，因此既有的 `add-permission` 授权依然有效。
</Tab>
<Tab value="AWS CDK">
```ts title="lib/stack.ts"
import { LambdaIntegration, ResponseTransferMode, RestApi, EndpointType } from "aws-cdk-lib/aws-apigateway";
import { Duration } from "aws-cdk-lib";

const api = new RestApi(this, "CopilotKitApi", {
  // Regional gets a 5-minute idle timeout; edge-optimized gets 30 seconds.
  endpointConfiguration: { types: [EndpointType.REGIONAL] },
});

api.root.addResource("api").addResource("copilotkit").addResource("{proxy+}").addMethod(
  "ANY",
  new LambdaIntegration(fn, {
    responseTransferMode: ResponseTransferMode.STREAM,
    timeout: Duration.minutes(15),
  }),
);
```

`responseTransferMode` 需要较新版本的 `aws-cdk-lib`；该 construct 会替你设置好流式调用的 URI。

### 3. 规避流式传输的限制

- **选择 Regional 端点。** 流受空闲超时约束：Regional 与私有端点为 5 分钟，而**边缘优化端点只有 30 秒**。如果智能体在两次 SSE 事件之间思考超过 30 秒，它的流会在边缘优化的 API 上被切断。想保留边缘缓存，办法是用自己的 CloudFront 分发架在 Regional API 前面，并调高其响应超时。
- **调高集成超时。** 默认仍是 29 秒。使用 `STREAM` 时，在 Regional 与私有 API 上最高可调至 15 分钟——与 Lambda 超时保持一致即可。
- **`STREAM` 会在该集成上禁用仅缓冲模式可用的特性**：端点缓存、内容编码与 VTL 响应转换。如有需要，请在集成内部完成压缩。
- **带宽。** 每个流式响应的前 10 MB 不限量；超过后 API Gateway 限速为 2 MB/s。
- **客户端超时不会让函数停下来。** 当 API Gateway 关闭连接后，Lambda 仍会继续运行并计费，直到执行完毕或触发自身超时。

<Callout type="warn" title="控制台的测试标签页总是缓冲">
  `TestInvokeMethod` 与控制台的 **Test** 标签页会先缓冲整个流再一次性返回，
  因此配置正确的集成在那里看起来仍是缓冲的。请改用 `curl -i --no-buffer`
  对已部署的阶段进行验证。
</Callout>

## 缓冲回退：HTTP API 与 ALB

在 HTTP API 或 Application Load Balancer 之后没有流式通道，因此用 `serverless-http` 包装 Express 处理函数已是最好的做法。聊天功能端到端仍然可用，只是每个响应都会在运行结束时一次性到达。

```
npm install express serverless-http @copilotkit/runtime
```

```ts title="src/handler.ts"
import express from "express";
import serverlessHttp from "serverless-http";
import { CopilotRuntime, BuiltInAgent } from "@copilotkit/runtime/v2";
import { createCopilotExpressHandler } from "@copilotkit/runtime/v2/express";

const runtime = new CopilotRuntime({
  agents: {
    default: new BuiltInAgent({ model: "openai/gpt-4o-mini" }),
  },
});

const app = express();

app.use(
  createCopilotExpressHandler({
    runtime,
    basePath: "/api/copilotkit",
    cors: true,
  }),
);

export const handler = serverlessHttp(app);
```

需要提前规划的两个限制：

- **10 MB 响应上限。** 带着大型工具结果的长智能体运行可能超出该上限，此时请求会直接失败，而不是被截断。
- **29 秒集成超时。** 超过该时长的智能体运行会返回 504，即便 Lambda 仍在继续执行。在 HTTP API 上这一上限不可更改；`responseTransferMode: STREAM` 在 REST API 上解除的正是这两个限制。

单路由（single-route）模式在这里很合适：它把运行时收拢为一个 `POST` 端点，免去了配置通配代理资源的麻烦：

```ts
createCopilotExpressHandler({
  runtime,
  basePath: "/api/copilotkit",
  mode: "single-route",
  cors: true,
});
```

## 身份验证

使用运行时的 `onRequest` 钩子，在任何路由发生之前就拒绝未通过身份验证的调用。它在上述每一种入口上的行为完全一致。

```ts
const copilotHandler = createCopilotRuntimeHandler({
  runtime,
  basePath: "/api/copilotkit",
  cors: true,
  hooks: {
    onRequest: async ({ request }) => {
      const token = request.headers.get("authorization");
      if (!token || !(await verifyToken(token))) {
        // Throwing a Response short-circuits the handler.
        throw new Response("Unauthorized", { status: 401 });
      }
    },
  },
});
```

若想改用 AWS 原生的身份验证，可把 Function URL 的 `AuthType` 设为 `AWS_IAM`，并让调用方用 SigV4 签名请求。这会把校验交给 IAM，但浏览器将无法再直接调用该 URL——你需要在中间加一层签名代理。

参见[身份验证](/auth)，了解如何把用户身份一路转发到你的智能体。

## 运维注意事项

- **把依赖打包进部署包。** `@copilotkit/runtime` 不在任何 AWS 托管层（layer）中。请使用 `NodejsFunction`（CDK）、`BuildMethod: esbuild`（SAM），或你自己的打包器。
- **在处理函数之外构造运行时。** 把 `new CopilotRuntime(...)` 放在模块作用域，热调用就能复用它，而无需每个请求都重建。
- **把超时设置得足以覆盖一次完整的智能体运行。** Lambda 的上限是 15 分钟；默认的 3 秒几乎什么都会被切断。
- **冷启动在聊天中能被感知。** 如果首 token 延迟很重要，预置并发（provisioned concurrency）是常规解法。
- **流式传输有它自己的限制。** 流式响应可达 200 MB，而缓冲上限是 6 MB；但超过前 6 MB 后 Lambda 会限速 2 MB/s（API Gateway 则是超过前 10 MB 后）。流式还会产生额外费用，而且即使客户端断开连接，一次流式运行仍会按完整的函数执行时长计费。
