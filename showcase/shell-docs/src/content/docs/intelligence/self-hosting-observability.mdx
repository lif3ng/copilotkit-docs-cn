## 概览

自托管的 CopilotKit Intelligence 部署可以把遥测数据发送到你自行运行的 OpenTelemetry 采集器，再由你转发给团队已有的链路追踪与日志工具。本页列出每条数据流的内容、开启方法，以及哪些信号可以表明安装处于健康状态。

Intelligence 不会安装采集器。本页的数据流只会发往你配置的端点，且在配置之前每条数据流都处于关闭状态。

## 什么时候该用它？

- 你使用 [Helm chart](/intelligence/self-hosting) 或 [ECS bundle](/intelligence/self-hosting-ecs) 自托管 Intelligence。
- 你希望在自己的可观测性工具中查看 Intelligence 的请求链路、错误与日志。
- 你想确认一次新安装或升级是否健康。

云端托管的 Intelligence 不会向客户导出这些数据流。

## 前置条件

- 一个正在运行的自托管 Intelligence 部署。
- 一个 Intelligence 服务可通过 HTTP 访问的 OpenTelemetry Collector（`otel/opentelemetry-collector-contrib` 发行版）。Intelligence 只通过 HTTP 发送 OTLP，不使用 gRPC。
- 在 Kubernetes 上采集 pod 日志：需要一个以 DaemonSet 方式运行、能读取各节点 `/var/log/pods` 的采集器。

## 数据流一览

| 数据流 | 信号 | 发送方 | 开启方式 | 状态 |
| --- | --- | --- | --- | --- |
| 后端链路 | OTLP 链路 | app API、实时网关、Automatic Learning 调度器 | `observability.tracing`（Helm）或 `otlpEndpoint`（ECS） | 稳定 |
| 调度器指标 | OTLP 指标 | Automatic Learning 调度器 | `observability.tracing`（Helm） | 稳定 |
| 产品事件 | OTLP 日志 | app API、Automatic Learning 调度器与 reconciler | `appApi.channelTelemetry`（Helm） | 预览 |
| 应用日志 | stdout 上的 JSON 行 | 所有服务 | `config.logLevel`（Helm） | 稳定 |

应用日志不会通过 OTLP 发送。你的采集器或日志代理会从容器的标准输出中读取它们。

<Callout type="info" title="产品事件为预览功能">
  `eip.*` 产品事件的名称与属性可能随版本更迭而变化。如果需要稳定的契约，请基于链路和日志构建仪表盘。
</Callout>

## 发送链路与指标

### Helm

设置完整的 OTLP/HTTP 链路端点，路径必须以 `/v1/traces` 结尾。

```yaml
observability:
  tracing:
    enabled: true
    endpoint: http://otel-collector.observability.svc:4318/v1/traces
    environment: production
```

- 开启链路追踪时 `environment` 为必填项。取值可使用 1 到 64 个字母、数字、点、下划线、斜杠或连字符。
- chart 会把 app API、实时网关与 Automatic Learning 调度器的链路发送到该端点。
- 调度器还会把自身指标发送到同一个采集器，即相同基础 URL 下的 `/v1/metrics`。
- 如果端点不以 `/v1/traces` 结尾，`helm install` 和 `helm upgrade` 会失败。

### ECS

将 `otlpEndpoint` 设置为你采集器的基础 URL，不带路径。

```json
{
  "otlpEndpoint": "https://otel-collector.example.internal:4318"
}
```

- 发布栈会把 app API 与实时网关的链路发送到 `<otlpEndpoint>/v1/traces`。
- `cpki-ecs deploy` 会移除末尾的 `/` 或 `/v1/traces`，因此这两种形式的值同样可用。
- ECS bundle 会把 `deployment.environment.name` 设置为 `ecs`，且无法更改。
- 采集器必须能从部署所在的私有子网访问。

### 每个 span 携带的内容

每个 span 都带有以下资源属性：

| 属性 | 值 |
| --- | --- |
| `service.name` | `app-api`、`realtime-gateway` 或 `learning-scheduler` |
| `service.version` | 该发布的镜像标签 |
| `deployment.environment.name` | Helm 上为 `observability.tracing.environment`，ECS 上为 `ecs` |

各服务会对请求内发生的入站 HTTP 与 WebSocket 升级、出站 HTTP、PostgreSQL 和 Redis 命令进行追踪。常用的 span 属性包括：

- `http.request.method`、`http.route` 与 `http.response.status_code`
- PostgreSQL span 上的 `db.operation.name`
- 来自已知项目的请求上的 `cpki.organization.id` 与 `cpki.project.id`
- 实时网关上针对 Slack 与 Microsoft Teams 调用的 `provider.effect` span，带有 `cpki.provider.adapter` 与 `cpki.provider.outcome`
- 实时网关上的 `replay.restore` span，带有 `thread_id`、`organization_id` 与 `project_id`

在 span 离开进程之前，各服务会移除以下属性：

- `db.statement` 与 `db.query.text`（SQL 文本）
- `http.url`、`url.full`、`url.path` 与 `url.query`（完整 URL、路径与查询字符串）
- 所有 `http.request.header.*` 与 `http.response.header.*` 属性

健康探测请求不会创建 span。

<Callout type="warn" title="span 仍会标识客户端">
  服务端 span 会保留 `client.address`（客户端 IP 地址）与 `user_agent.original`。如果你的策略不允许在链路追踪工具中出现 IP 地址，请在采集器中删除它们。
</Callout>

## 发送产品事件

产品事件是描述产品动作的 OTLP 日志记录，例如某个线程被创建或某个 skill 被批准。可以用它们构建自己的用量报表。

```yaml
appApi:
  channelTelemetry:
    endpoint: http://otel-collector.observability.svc:4318/v1/logs
    tokenSecret:
      name: otel-collector-token
      key: token
```

- 端点必须以 `/v1/logs` 结尾。
- 请设置 `tokenSecret` 或 `headers`，两者都不设置时 chart 会校验失败。
- app API 会以 `Authorization: Bearer <token>` 的形式发送该 token。
- 要发送其他请求头，请将 `headers` 设置为字面量 `key=value,key=value` 字符串。如果两者都设置了，token 对 `Authorization` 优先生效。
- 该数据流没有 ECS 对应项。

| 事件 | 触发时机 |
| --- | --- |
| `eip.thread.created` | 线程被创建 |
| `eip.thread.run_requested` | 在某个线程上请求智能体运行 |
| `eip.channel.created` | Channel 被创建 |
| `eip.channel.attached` | Channel 连接到 Slack 或 Microsoft Teams |
| `eip.channel.inbound` | Channel 收到新的消息事件 |
| `eip.learning.run_started` | Automatic Learning 运行开始 |
| `eip.learning.run_completed` | Automatic Learning 运行结束 |
| `eip.learning.skill_approved` | 审阅者批准某个 skill |
| `eip.learning.skill_pulled` | 某个运行时拉取某个 skill |

每个属性名都以 `copilotkit.` 开头。重试之后用于去重的键因事件族而异：

- **线程与 Learning 事件**：`copilotkit.event_id`，形如 `<event>:<organization>:<project>:<resource>`。在 `eip.learning.skill_pulled` 上，resource 部分是每次拉取新生成的随机 ID，因此对同一 skill 的两次拉取是两个事件。
- **`eip.channel.inbound`**：`copilotkit.channel_event_id`，即入站消息事件的 ID。
- **`eip.channel.created` 与 `eip.channel.attached`**：没有事件 ID。不要按 ID 对这些事件去重。

产品事件绝不包含消息内容、原始提供方载荷、凭据、Channel 名称、线程名称、skill 文本或 insight 文本。它们确实包含标识符：组织、项目、线程、运行以及 API 密钥的 ID，还有登录用户的 ID。`eip.channel.created` 与 `eip.channel.attached` 还可能携带 `copilotkit.principal_email`，即做出更改的用户邮箱地址。

## 采集应用日志

app API、实时网关、线程压缩 worker、连接器 outbox 与线程清理器会向 stdout 每行写入一个 JSON 对象。有两个服务输出纯文本：

- **应用前端**：默认 Nginx 文本格式的 Nginx 访问与错误日志。
- **Embeddings**：text-embeddings-inference 服务器日志。

对于 JSON 服务：

- **日志级别**：在 Helm 上通过 `config.logLevel` 设置。
- **请求行**：app API 与实时网关会在每个 HTTP 请求结束时写一条 `http.server.request.completed` 行，包含 `duration_ms`、`http.method`、`http.route`、`http.status_code` 与 `outcome`。在 app API 的行中，`method`、`route` 与 `status_code` 嵌套在 `http` 对象之下。前端不会写这种行；要查看前端错误，请读取其 Nginx 访问日志中的状态码。
- **链路关联**：开启链路追踪时，app API 的行会携带 `trace_id` 与 `span_id`。实时网关的行会以 Datadog 十进制格式携带 `dd.trace_id` 与 `dd.span_id`。
- **脱敏**：app API 日志会将授权头、cookie、API 密钥，以及名称类似 `password`、`token` 或 `secret` 的字段替换为 `[REDACTED]`。

在 Kubernetes 上，使用采集器的 `filelog` receiver 读取 `/var/log/pods` 下的日志。在 ECS 上，日志位于 CloudWatch 日志组 `/ecs/<deploymentName>/...` 中。

## 配置采集器

以下配置会接收所有 OTLP 数据流、读取 pod 日志，并将所有内容转发到你的后端。请把 exporter 替换为适配你所用工具的那一个。

```yaml
receivers:
  otlp:
    protocols:
      http:
        endpoint: 0.0.0.0:4318
  filelog:
    # Replace intelligence with the namespace of your release.
    include: [/var/log/pods/intelligence_*/*/*.log]
    include_file_path: true
    operators:
      - type: container
      # Parse the JSON services. Nginx and embeddings lines stay as text.
      - type: json_parser
        if: 'body matches "^\\s*\\{"'
      # Link app API lines to their traces.
      - type: trace_parser
        if: 'attributes.trace_id != nil'
        trace_id:
          parse_from: attributes.trace_id
        span_id:
          parse_from: attributes.span_id

processors:
  memory_limiter:
    check_interval: 1s
    limit_percentage: 80
    spike_limit_percentage: 25
  # A second layer. The services already remove these attributes.
  transform/redact:
    error_mode: ignore
    trace_statements:
      - context: span
        statements:
          - delete_key(attributes, "db.statement")
          - delete_key(attributes, "db.query.text")
          - delete_key(attributes, "url.full")
          - delete_key(attributes, "url.query")
  batch: {}

exporters:
  otlphttp:
    endpoint: https://otlp.your-backend.example.com
  debug:
    verbosity: basic

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [memory_limiter, transform/redact, batch]
      exporters: [otlphttp]
    metrics:
      receivers: [otlp]
      processors: [memory_limiter, batch]
      exporters: [otlphttp]
    logs:
      receivers: [otlp, filelog]
      processors: [memory_limiter, batch]
      exporters: [otlphttp]
```

- 将 `observability.tracing.endpoint` 指向 `http://<collector-service>.<namespace>.svc:4318/v1/traces`。
- 将 `appApi.channelTelemetry.endpoint` 指向同一主机的 `/v1/logs`。
- `filelog` 的 operators 会把 JSON 行解析为属性，因此你可以查询 `http.status_code` 等字段。非 JSON 的行会在 body 中保留原始文本。
- `trace_parser` 会把 app API 的 `trace_id` 与 `span_id` 映射到日志记录上。实时网关的 `dd.trace_id` 是十进制数，因此无法映射为 OpenTelemetry 的 trace ID。
- 要验证配置，可在某个 pipeline 的 `exporters` 中加入 `debug`，然后查看采集器的输出。

## 检查安装健康状态

### 探针

| 服务 | 存活探针 | 就绪探针 | 就绪检查内容 |
| --- | --- | --- | --- |
| app API | `/api/health` | `/api/health` | 一次 PostgreSQL 查询。数据库失败时返回 `503`；当 Channels 已开启但缺少其加密密钥时返回 `200` 与 `"degraded"`。 |
| 实时网关 | `/health/live` | `/health/ready` | 仅检查排空状态与许可证门槛 |
| 应用前端 | `/healthz` | `/healthz` | 仅检查 web 服务器 |

使用 marketplace 构建时，app API 使用 `/api/health/live` 与 `/api/health/ready`。

### 需要关注的信号

- **错误率**：错误 span、`http.status_code` 为 500 及以上的 `http.server.request.completed` 行，以及状态码为 5xx 的前端 Nginx 访问行。
- **数据库**：app API 的 `app-api health check failed` 日志行，以及失败的 `postgresql.*` span。
- **实时网关内存**：每 5 秒一条的 `gateway_memory` 行，以及当某个容器占用其内存限制的 80% 或以上时出现的 `gateway_memory_pressure` 警告。
- **Product Analytics 管道**：开启 Product Analytics 时的 `realtime_gateway.analytics.projector.health` 行。事件在队列中等待、失败或进入隔离区时，该行以 warning 级别记录；网关无法读取队列时以 error 级别记录。请关注 `analytics_projector.queue_depth`、`analytics_projector.quarantine_depth` 与 `analytics_projector.oldest_queue_age_ms`。
- **配置**：启动时出现 `telemetry.config_rejected` 警告，表示某个端点已设置但被拒绝，对应的数据流处于关闭状态。

### 未覆盖的检查项

- 没有任何探针检查 Redis、对象存储，或 app API 与实时网关之间的连接。Redis 故障只会表现为请求错误和错误 span。
- 没有任何服务导出健康指标或连接数。请在你自己的工具中使用上述信号。
