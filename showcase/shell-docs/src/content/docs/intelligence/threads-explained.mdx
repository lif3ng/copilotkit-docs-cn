## 概览

先阅读 [AG-UI Streams 概览](/AG-UI-Streams)，了解 AG-UI Streams 提供了什么，并在预构建的 Drawer 与自定义无头 UI 之间做出选择。本页讲解这两条路径底层的持久化与重放架构。客户端侧的生命周期（生成 `threadId`、加载时注入历史、切换或新建线程）请参阅[线程与历史生命周期](/threads-lifecycle)。

## 什么是线程？

框架线程管理智能体的会话与模型上下文，而 Intelligence 的 **AG-UI 流**负责记录这次交互并交付给你的用户。

CopilotKit 的 `threadId` 标识某段会话，Intelligence 会存储并重放该会话的 AG-UI 事件。使用 `useThreads` 或 `CopilotThreadsDrawer` 列出并选择会话，再把选中的 `threadId` 传给你的聊天组件。

| 概念 | 职责 |
|---|---|
| 框架线程或 ADK session | 智能体会话、模型上下文以及框架专属的执行状态。 |
| Intelligence 的 AG-UI 流 | 记录交互事件、重放、追平，以及向已连接客户端的投递。 |
| Channel 线程 | Slack 或 Microsoft Teams 上的原生会话。 |

模型上下文压缩与用户可见的历史服务于不同目的。Intelligence 独立于框架的上下文存储，记录经它交付的 AG-UI 事件。重放使用这些被记录的事件；这种分离并不意味着无限期保留，也不意味着可以恢复从未被记录的历史。

## 线程如何与框架存储协同工作

从头开始？CopilotKit Intelligence 提供会话持久化：它存储交互事件，让用户可以跨会话、跨设备重新打开完整的对话，重连到进行中的运行，并管理自己的线程。

接入 Intelligence 时，可以保留你现有的线程系统。当会话经由你连接的 CopilotKit runtime 运行时，Intelligence 会自动记录一份它所支持的 AG-UI 交互历史副本。你的框架继续管理原始会话与智能体状态。请保持已配置的[持久化 LangGraph checkpointer 或部署](https://docs.langchain.com/oss/python/langgraph/persistence)。对于 ADK，请保持已配置的[持久化 session service](https://google.github.io/adk-docs/sessions/session/)。重放已记录的 AG-UI 历史并不会从检查点恢复框架执行，这类恢复仍由你的框架负责。

继续某段会话时，请沿用同一个线程 ID，或与原生线程/session ID 保持稳定映射。[自带线程系统](/intelligence/bring-your-own-thread-system)说明了 Intelligence 会记录什么，并给出了一个既有 LangGraph 应用的示例。

历史导入是可选的。它只复制受支持的历史，不会在数据库之间建立通用的复制链路。Intelligence 的重命名、归档与删除操作只影响它自己的记录。

## 核心概念

### 线程与 Run

**线程**是持久容器，**run** 是线程内的一次智能体执行。一个线程可以包含多个 run。用户每发送一条消息并得到智能体回应，就是一次新的 run；线程会累积其所有 run 的事件。

### 各部分如何协作

从开发者的视角看，线程涉及三样东西：

| 你使用的 | 它做什么 |
|-------------|-------------|
| 前端线程 API | 列出、重命名、归档与删除线程。支持分页，并通过 WebSocket 跨标签页与设备保持同步。 |
| 携带 `threadId` 的 `CopilotChat` | 连接到指定线程，加载其历史，并实时流式接收新事件。 |
| `CopilotRuntime` | 服务端层，负责执行智能体、把线程数据存入 CopilotKit Intelligence，并向已连接的客户端转发事件。 |

你只会直接与其中前两者交互。持久化与同步由 runtime 和平台在幕后完成。

要把这些组件接进自定义聊天 UI，请遵循[无头线程](/headless-threads)。

### 自动命名

新线程创建且第一个 run 完成后，runtime 会用 LLM 自动生成一个简短名称（2–5 个词）。这一步异步进行，因此不会阻塞线程创建或智能体响应。生成的名称通过实时同步经前端线程 API 呈现。

自动命名默认开启。可在 runtime 上用 `generateThreadNames: false` 关闭。用户始终可以通过 `renameThread()` 覆盖生成的名称。

### 归档与删除

线程支持两种语义不同的移除操作：

- **归档**是软删除。线程仍被存储，但会从默认列表中消失。在前端线程 API 中设置 `includeArchived: true` 即可显示已归档线程。线程还可以取消归档，恢复到活跃列表。
- **删除**是永久且不可逆的。线程及其历史会被彻底移除。

这两种操作都没有内置确认对话框，因此如有需要，应用应自行实现。

## 工作原理

客户端侧的步骤（生成 `threadId`、加载时注入历史、切换或新建线程）见[线程与历史生命周期](/threads-lifecycle)。本节介绍平台在其下做了什么：持久化 run、重放 run，并让每个已连接的客户端保持同步。

### 持久化与重放

智能体运行时，runtime 会把每个事件（消息、工具调用与状态更新）写入 CopilotKit Intelligence 中的线程。Intelligence 持久化 AG-UI 事件，并为回归的客户端构建重放。重连的客户端可以用自己的重放游标追平错过的事件。

当客户端打开既有线程时，Runtime 会提供连接凭据。前端加入事件流并收到已记录的历史。如果有 run 正在进行，重放完成后新事件会经同一连接继续推送。
当有 run 正在进行时，重放的历史之后会紧跟实时更新。如果客户端正在切换线程时，上一个线程的某个工具调用完成了，其结果会被丢弃而不是插入新线程，因此过期的输出绝不会在会话之间泄漏。

### 后台执行

浏览器断开本身并不会让权威的智能体运行停止。只要你的 Runtime 与智能体仍在运行，执行就可以继续，Intelligence 会记录其事件。用户重新打开会话即可追平进度。这不能替代框架的检查点恢复，也无法在 Runtime 故障后恢复某个 run。

### 实时同步

前端线程客户端会为线程元数据变更维护一个 WebSocket 订阅。任何客户端创建、重命名、归档或删除线程时，更新都会自动推送到所有已连接的客户端。正因如此，在一个标签页创建的线程无需轮询就会出现在另一个标签页的侧边栏中。

### 悲观更新

线程变更（`rename`、`archive`、`delete`）采用悲观更新模型：客户端等待服务器经 WebSocket 确认之后才更新线程列表。这意味着：

- 在服务器确认操作之前，线程列表不会变化。
- 如果服务器拒绝变更，UI 永远不会显示错误状态。
- 返回的 promise 只在服务器确认后 resolve，失败时 reject。

## 错误处理

### 变更失败

所有变更方法（`renameThread`、`archiveThread`、`deleteThread`）都返回 promise，当服务器无法完成操作时会以 `Error` reject。常见原因：

- **网络故障**：客户端无法连接到 runtime。
- **线程不存在**：你的变更到达之前，线程已被其他客户端删除。
- **授权失败**：用户没有修改该线程的权限。
- **超时**：服务器在 15 秒内没有响应。

线程客户端会暴露最近一次列表或变更错误，并在下一次成功操作后将其清除。

### WebSocket 断开

如果 WebSocket 连接中断（网络切换、服务器重启、笔记本休眠）：

- **线程列表**：前端线程 API 会停止接收实时更新，列表会变得过时，直到连接重建。重连自动进行，采用指数退避。
- **进行中的对话**：如果 `CopilotChat` 在 run 进行中失去 WebSocket，智能体的输出可能被中断。重新加载页面，或切走再切回该线程，会触发重连流程，重放所有错过的事件。

### 线程被锁定

如果某线程已有一个进行中的 run，而另一个客户端尝试在同一线程上启动新 run，请求会被 **409 Conflict** 拒绝。这可以防止两个智能体 run 在同一线程上交错写入事件。必须等既有 run 完成或被停止后，才能开始新的 run。

runtime 会在每个 run 期间获取一个基于 Redis 的线程锁。你可以在 runtime 上调整这一行为：

| 选项 | 默认值 | 最大值 | 说明 |
|--------|---------|-----|-------------|
| `lockTtlSeconds` | `20` | `3600`（1 小时） | 锁在被自动过期之前持有多久。 |
| `lockHeartbeatIntervalSeconds` | `15` | `3000`（50 分钟） | run 期间 runtime 续期的频率。心跳始终运行，你只需要调整间隔。 |
| `lockKeyPrefix` | — | — | 线程锁的自定义 Redis 键前缀。多个应用共享一个 Redis 实例时很有用。 |

run 正常完成后，锁会立即释放。TTL 是一种兜底保护，用于 runtime 崩溃且未释放锁的情况。

## 设计决策

### 为什么用事件重放而不是消息快照？

Intelligence 记录 AG-UI 事件，而不只依赖框架当前的消息列表。这样可以实现：

- **追平**：重连的客户端可以用自己的重放游标获取错过的事件，而不是重新加载整个历史。
- **可交互的历史**：被记录的消息、工具调用与状态更新可以重建对话。重放在投递时可能会压缩事件；它并不保证每个原始事件都原样送达。

代价是重放比加载一个消息数组更复杂。平台承担了这份复杂度，你的应用无需关心。

### 什么时候线程不是合适的工具

- **临时交互**：如果你的用户不需要会话历史（例如一次性的问答小组件），线程只会带来不必要的复杂度。使用不带 `threadId` 的 `CopilotChat`。
- **仅客户端状态**：如果你只需要本地聊天历史而不需要服务端持久化，请改在前端状态或 localStorage 中管理消息。
