## 这是什么？

子智能体是多智能体的经典模式：顶层的 **监督者**（supervisor）LLM 将一个或多个专门化的 **子智能体**（sub-agent）各自暴露为一个工具并加以编排。监督者决定委派什么，子智能体完成各自范围内的任务，其结果再回流到监督者的下一步。

这在结构上与工具调用本质相同，只是每个“工具”本身就是一个完整的智能体，拥有自己的系统提示词，通常还拥有自己的工具、记忆和模型。

## 什么时候应该使用它？

当一项任务包含多个界限清晰、各有所长的子任务，且每个子任务都能受益于独立的专注点时，就适合使用子智能体：

- **研究 → 写作 → 评审**管线：每个阶段需要不同的系统提示词和 temperature。
- **路由 + 专家**：由一个智能体对请求进行分类，并分派给合适的专家。
- **分而治之**：任何能干净地拆分为并行或串行子问题的问题。

下面的示例使用“研究 → 写作 → 评审”形态作为标准示例。

每个子智能体都是一次隔离的智能体调用，拥有自己的模型、系统提示词和可选工具。它们不与监督者共享记忆或工具；监督者只会看到子智能体返回的内容。

<Snippet region="subagent-setup" title="backend/agent.py —— 三个子智能体" />

子智能体的系统提示词要保持狭窄而专注。这一模式的核心在于每个子智能体只把一件事做好。如果一个子智能体需要了解完整的用户上下文才能完成工作，那就说明边界划分有问题。

## 将子智能体暴露为工具

监督者通过调用工具来委派。每个委派工具都是对专门化智能体调用的一层轻量包装，它会：

1. 使用传入的 `task` 字符串运行子智能体。
2. 将这次委派记录到共享智能体状态的 `delegations` 插槽中（以便 UI 能渲染实时日志）。
3. 将子智能体的最终消息作为工具结果返回，监督者会在它的下一轮看到该结果。

<Snippet region="supervisor-delegation-tools" title="backend/agent.py —— 监督者工具" />

这正是 CopilotKit 共享状态通道大显身手的地方：监督者的工具调用在发生时会即时修改 `delegations`，前端则实时渲染每一条新记录。

<Callout type="warn">
  为每次委派分配一个稳定的 `id`，并按该 `id` 合并新记录。客户端在每次运行时都会把它持有的共享状态副本作为运行输入发回，因此一个盲目追加所收到内容的插槽——例如 LangGraph 的 `Annotated[list, operator.add]` reducer——会把客户端刚回传的记录拼接到智能体已有的记录之后，线程继续时日志就会翻倍。
</Callout>
