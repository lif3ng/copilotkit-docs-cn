用户输入的任何内容都会到达你的模型，模型产出的任何内容都会到达你的用户。在 LangGraph 中，对两者进行筛查是中间件的职责：`AgentMiddleware` 提供了围绕智能体、模型调用和每次工具调用的钩子，而 `CopilotKitMiddleware` 本身就是其中之一——因此你的检查可以与它组合，而不是包裹整个运行时。

本页介绍输入筛查、输出与 DLP 筛查，以及如何让这两者与 CopilotKit 自身的中间件正确排序。

## 各 Hook 的位置

一次运行会按顺序经过以下钩子：

| Hook | 执行时机 | 用途 |
| --- | --- | --- |
| `before_agent` | 整个运行开始前执行一次 | 拒绝整个会话——速率限制、被封锁的租户 |
| `before_model` | 每次模型调用前 | 针对最新用户消息的输入筛查 |
| `wrap_model_call` | 包裹每次模型调用 | 输出筛查；你能看到发出去的请求和返回的响应 |
| `wrap_tool_call` | 包裹每次工具调用 | 筛查工具参数与工具结果 |
| `after_model` | 每次模型调用后 | 无需修改响应的事后检查 |

`before_*` 钩子返回一个状态更新字典（或 `None`）。`wrap_*` 钩子会接收到一个必须调用的 `handler` 以继续调用链——这正是它们能够检查并改写结果的原因。

## 从内置的 PII 中间件开始

在编写任何自定义逻辑之前，先看看 `PIIMiddleware` 是否已经满足需求。它随 LangChain 一起提供，能在输入和输出两个方向上处理常见的 DLP 场景：

```python title="agent.py"
from langchain.agents import create_agent
from langchain.agents.middleware import PIIMiddleware
from copilotkit import CopilotKitMiddleware

agent = create_agent(
    model="openai:gpt-4o",
    tools=[...],
    middleware=[
        # Redact emails the user sends in.
        PIIMiddleware("email", strategy="redact"),
        # Mask card numbers wherever they appear, including in tool results.
        PIIMiddleware(
            "credit_card",
            strategy="mask",
            apply_to_output=True,
            apply_to_tool_results=True,
        ),
        # Refuse outright if an API key shows up.
        PIIMiddleware("api_key", detector=r"sk-[a-zA-Z0-9]{32}", strategy="block"),
        CopilotKitMiddleware(),
    ],
)
```

内置类型包括 `email`、`credit_card`、`ip`、`mac_address` 和 `url`；其他任何名称都会成为自定义类型，由你提供的 `detector`（正则或可调用对象）驱动。策略包括 `block`（抛出 `PIIDetectionError`）、`redact`、`mask` 和 `hash`。

<Callout type="info" title="apply_to_output 默认关闭">
  除非另有指定，`PIIMiddleware` 只筛查**输入**。传入 `apply_to_output=True` 可筛查模型输出，传入 `apply_to_tool_results=True` 可筛查工具的返回值——这是数据泄露的常见源头，因为工具结果来自你自己的系统。
</Callout>

## 输入筛查

对于 PII 检测无法表达的场景——主题限制、提示注入启发式规则、按租户的策略——可以实现 `before_model`，并在检查不通过时结束运行。

```python title="guardrails.py"
from typing import Any

from langchain.agents.middleware import AgentMiddleware, AgentState, hook_config
from langchain_core.messages import AIMessage, HumanMessage
from langgraph.runtime import Runtime


class InputFirewall(AgentMiddleware):
    """Rejects user input that fails policy before it reaches the model."""

    def __init__(self, *, refusal: str = "I can't help with that request."):
        super().__init__()
        self.refusal = refusal

    # can_jump_to declares the edge; without it, "jump_to" is ignored.
    @hook_config(can_jump_to=["end"])
    def before_model(
        self, state: AgentState, runtime: Runtime[Any]
    ) -> dict[str, Any] | None:
        messages = state.get("messages", [])
        latest = next(
            (m for m in reversed(messages) if isinstance(m, HumanMessage)), None
        )
        if latest is None:
            return None

        verdict = screen_input(str(latest.content))  # your classifier or rules
        if not verdict.allowed:
            # Ending with an AIMessage means the user sees the refusal in chat
            # rather than an error toast.
            return {
                "jump_to": "end",
                "messages": [AIMessage(content=self.refusal)],
            }

        return None
```

有两点值得了解：

- **必须使用 `@hook_config(can_jump_to=["end"])`**。它在编译期声明这个条件边。没有它，返回 `{"jump_to": "end"}` 会静默失效。
- **返回 `AIMessage` 比抛出异常更友好**。抛出的异常会表现为运行错误；而注入的消息会渲染为普通的一轮助手回复，用户能得到解释，会话也能继续使用。

## 输出与 DLP 筛查

输出筛查应放在 `wrap_model_call` 中，因为它是唯一能在下游任何环节看到模型产出之前将其改写的钩子。调用 `handler(request)`，检查结果，然后返回原始响应或替换内容。

```python title="guardrails.py"
from dataclasses import replace
from typing import Awaitable, Callable

from langchain.agents.middleware import (
    AgentMiddleware,
    ModelRequest,
    ModelResponse,
)
from langchain_core.messages import AIMessage


class OutputFirewall(AgentMiddleware):
    """Scrubs or blocks model output before it leaves the agent."""

    def wrap_model_call(
        self,
        request: ModelRequest,
        handler: Callable[[ModelRequest], ModelResponse],
    ) -> ModelResponse:
        response = handler(request)

        scrubbed = []
        for message in response.result:
            if isinstance(message, AIMessage) and isinstance(message.content, str):
                clean = redact_sensitive(message.content)  # your DLP pass
                if clean != message.content:
                    message = message.model_copy(update={"content": clean})
            scrubbed.append(message)

        return replace(response, result=scrubbed)

    async def awrap_model_call(
        self,
        request: ModelRequest,
        handler: Callable[[ModelRequest], Awaitable[ModelResponse]],
    ) -> ModelResponse:
        response = await handler(request)
        # ...same scrubbing as above
        return response
```

<Callout type="warn" title="流式传输会绕过简单的输出过滤器">
  `wrap_model_call` 看到的是已完成组装的响应。当模型流式输出时，token 在此之前就已经到达浏览器——因此在这里应用的清洗只能修正存储下来的消息，而用户可能已短暂看到原始内容。`PIIMiddleware` 的处理方式是在状态级检查之外再安装一个流转换器。如果你的自定义规则也必须在流式传输期间生效，要么将其表达为 `PIIMiddleware` 的自定义 detector，要么避免对该智能体使用流式传输。
</Callout>

对于异步智能体，请实现带 `a` 前缀的变体（`awrap_model_call`、`abefore_model`）——同步方法在异步路径上不会被使用。

## 筛查工具调用

工具是另一个值得设防的边界：参数把受用户影响的数据带出去，结果把系统数据带回来。

```python
from langgraph.types import Command
from langchain_core.messages import ToolMessage
from langchain.agents.middleware import ToolCallRequest


class ToolFirewall(AgentMiddleware):
    def wrap_tool_call(
        self,
        request: ToolCallRequest,
        handler: Callable[[ToolCallRequest], ToolMessage | Command],
    ) -> ToolMessage | Command:
        if not tool_call_allowed(request):  # your policy
            return ToolMessage(
                content="This action is not permitted.",
                tool_call_id=request.tool_call["id"],
            )
        return handler(request)
```

不调用 `handler` 而直接返回 `ToolMessage`，可以在阻断执行的同时保持对话连贯——模型会看到一个它可以回应的拒绝消息。

## 与 `CopilotKitMiddleware` 的顺序

中间件按**列表第一项作为最外层**的方式组合。对于 `wrap_*` 钩子，这意味着排在最前面的中间件最早看到请求、最晚看到响应。

`CopilotKitMiddleware` 会将前端工具合并进请求，并在返回途中拦截前端工具调用。请把你的护栏放在列表中它的**前面**：

```python
middleware=[
    InputFirewall(),        # outermost: screens before anything else runs
    OutputFirewall(),       # sees the final response last
    CopilotKitMiddleware(), # innermost: frontend tools, state exposure
]
```

这个顺序有一个具体的理由：`CopilotKitMiddleware` 会把浏览器端的前端工具添加到模型请求中。放在它*之后*的护栏，检查到的请求已经包含了策略层未曾批准的工具；更重要的是，放在它之后的输出过滤器，会在 CopilotKit 组装完前端实际收到的响应之前运行。

<Callout type="info">
  列表顺序是唯一的排序控制手段。没有优先级字段，中间件也无法声明自己必须先于另一个运行。
</Callout>

## 这不涵盖的内容

中间件保护的是智能体。它并不保护智能体周围的运行时——验证调用方身份、按用户限流，以及在智能体运行开始前直接拒绝请求，这些都属于运行时层的职责：

- [身份验证](/auth)——运行时 handler 上的 `onRequest` 与 `onBeforeHandler` 钩子
- [线程授权](/auth#thread-authorization)——阻止一个用户访问另一个用户的会话

而对于那些应该由人来决定、而非由策略检查来把关的操作，[人机协同](/human-in-the-loop)是更合适的工具：把操作呈现出来等待批准，而不是静默阻断。
