## 这是什么？

`useInterrupt` 让你的智能体在运行中途暂停，通过一个自定义 React
组件把控制权交给用户，再带着用户返回的任何内容恢复运行。这个暂停
如何实现取决于框架的运行时。

<WhenFrameworkHas flag="interrupt_pattern" equals="native">

这个框架内置一等公民级的中断原语，让运行中的工作可以自行挂起并把
控制权交给客户端
（[LangGraph](https://docs.langchain.com/oss/python/langgraph/interrupts)、
[AWS Strands](https://strandsagents.com/docs/user-guide/concepts/interrupts/)）。
运行在服务端被冻结，直到客户端带载荷解析这个中断，届时执行恢复，
就好像 interrupt 调用只是返回了那个载荷。

CopilotKit 的 `useInterrupt` 是这份契约的前端一半：它订阅被暂停的
运行，渲染你给出的任何组件，并带着用户的答案回调智能体。

</WhenFrameworkHas>

<WhenFrameworkHas flag="interrupt_pattern" equals="promise-based">

有些运行时无法像 LangGraph 的 `interrupt()` 那样在工具中途暂停
运行，因此这个演示改用带 Promise 处理器的 `useFrontendTool`。
智能体像调用其他工具一样调用 `schedule_meeting`；客户端处理器渲染
选择器，让请求保持打开，直到用户选定时段或取消才兑现 Promise。
在读者眼里是同样的 UX——智能体暂停、用户作答、智能体恢复——
底层机制不同。

</WhenFrameworkHas>

<WhenFrameworkHas flag="interrupt_pattern" absent>

> **此框架不可用**。`useInterrupt` 只有在底层运行时暴露原生
> `interrupt(...)` 原语（LangGraph、AWS Strands）或可兑现 Promise
> 的前端工具路径时才有意义。对于其他所有集成，请改用
> [`useHumanInTheLoop`](../human-in-the-loop)——它是基于工具调用的
> 暂停/恢复流程的标准 hook，可用于所有支持工具调用的框架。

</WhenFrameworkHas>

## 何时使用 `useInterrupt`？

当暂停是一个**由图强制的检查点**——代码路径_必须_停下来等人，
而不是由 LLM 发起的工具调用——就用 `useInterrupt`。典型情况：

- 敏感操作（支付、不可逆写入）必须经过审批
- 某个必需的状态未知，只能从用户那里收集
- 智能体在更长的流程中明确到达一个审批节点
- 你希望服务端契约是 `interrupt(...)` 并带载荷恢复

对于由 LLM 发起、模型临场决定询问用户的暂停，优先选择
[`useHumanInTheLoop`](../human-in-the-loop)。

有两点值得注意：

- 载荷（`{"topic": topic, "attendee": attendee}`）
  是前端从中断上读到的东西。保持为普通的可序列化对象。它是 UI
  渲染所需的“暂停时上下文”。它落在哪取决于桥接层：LangGraph
  把它作为 `event.value` 交给 `render`，而标准 AG-UI
  中断则把它带在中断本身上——要么放在 `metadata`
  里，要么 JSON 编码进 `message`。请阅读你的桥接层实际使用的通道，
  不要凭假设。
- 返回侧契约（`{chosen_label, chosen_time}` 或
  `{cancelled: true}`）完全由你定义。客户端可以发送任何东西作为
  解析载荷；是工具赋予它意义。

## 前端：`useInterrupt` 的 render prop

在客户端，你为每个智能体注册一个 `useInterrupt` hook。当被暂停的
运行到达时，`render` 同时收到原始 `event` 与 `interrupt`

上，标准 AG-UI 中断则把它带在 `interrupt` 上（其 `metadata`，

### 关键 props

- **`agentId`** —— 必须与运行时注册的智能体匹配。省略时 hook
  假定为 `"default"`。不匹配意味着中断永远不会触发。
- **`render`** —— 接收 `{ event, interrupt, resolve }`。
  你在服务端传给 `interrupt(...)` 的载荷，在旧版自定义事件中断上
  经 `event.value` 到达，在标准中断上则落在 `interrupt`。
- **`renderInChat`** —— 为 `true` 时（如上），选择器内联出现在
  聊天记录中，位于被暂停的助手回合与尚未发生的续接之间。

## 多个中断？用 `enabled` 加类型与门控

如果你的图会发出不止一种中断（例如 `"ask"` 与
`"approval"`），在载荷上用一个 `type` 字段给每种打标，并按形态
各装一个 `useInterrupt`，分别用 `enabled` 谓词门控：

```tsx
useInterrupt({
  agentId: "gen-ui-interrupt",
  enabled: (event) => event.value.type === "ask",
  render: ({ event, resolve }) => (
    <AskCard question={event.value.content} onAnswer={resolve} />
  ),
});

useInterrupt({
  agentId: "gen-ui-interrupt",
  enabled: (event) => event.value.type === "approval",
  render: ({ event, resolve }) => (
    <ApproveCard content={event.value.content} onAnswer={resolve} />
  ),
});
```

## 用 `handler` 预处理

当中断有时可以在_没有_用户输入的情况下解析（例如当前用户已有
权限），传入一个在 `render` 之前运行的 `handler`。处理器可以自行
调用 `resolve(...)` 提前恢复智能体——恢复运行开始时中断卡片即卸载。
或者返回一个值，`render` 会以 `result` 收到它：

```tsx
useInterrupt({
  agentId: "gen-ui-interrupt",
  handler: async ({ event, resolve }) => {
    const dept = await lookupUserDepartment();
    if (event.value.accessDepartment === dept || dept === "admin") {
      resolve({ code: "AUTH_BY_DEPARTMENT" });
      return; // agent will resume; card unmounts when the run starts
    }
    return { dept };
  },
  render: ({ result, event, resolve }) => (
    <RequestAccessCard
      dept={result?.dept}
      onRequest={() => resolve({ code: "REQUEST_AUTH" })}
      onCancel={() => resolve({ code: "CANCEL" })}
    />
  ),
});
```

</WhenFrameworkHas>

## AG-UI 标准中断流程与旧版流程

`useInterrupt` 支持两种中断传输方式。弄清你的智能体用的是哪一种，
有助于写出正确的 `render` 代码。

### 标准流程（`RUN_FINISHED` 且 `outcome.type === "interrupt"`）

当智能体后端遵循 AG-UI 协议时，它通过发出一个 `RUN_FINISHED`
事件来发出中断信号，其 outcome 携带 interrupts 数组：

```
outcome.type === "interrupt"
outcome.interrupts  // Interrupt[]
```

hook 在 `onRunFinishedEvent` 上检测到这一点，并在 `onRunFinalized`
触发**之后**才把中断暴露到 render props 上。你的 `render`
函数会收到：

- **`interrupt`** —— 主 `Interrupt`（`interrupts[0]`），形态为
  `{ id, reason, message?, toolCallId?, responseSchema?, expiresAt?, metadata? }`。
- **`interrupts`** —— 全部打开的中断集合（通常只有一个，但也支持
  多中断——见下文）。
- **`resolve(payload?, interruptId?)`** ——
  为目标中断（默认为主中断）记录
  `{ status: "resolved", payload }`。每个打开的中断都有响应后，
  智能体运行即恢复。
- **`cancel(interruptId?)`** ——
  为目标中断记录 `{ status: "cancelled" }`。同样适用先累积后提交的
  逻辑。

### 旧版流程（`on_interrupt` 自定义事件）

较旧的智能体（或尚未迁移到 AG-UI 中断规范的智能体）发出一个
自定义 `on_interrupt` 事件。hook 在 `onCustomEvent`
上检测到它，并把 `interrupt` 置为 `null`、`interrupts` 置为
`[]`。载荷在 `event.value` 里。调用 `resolve(payload)`
会经 `forwardedProps.command`（旧版恢复机制）恢复运行。`cancel()`
直接关闭中断而不恢复运行——智能体永远收不到响应。

### 优先级

如果两种信号出现在同一次运行上（迁移期间不太可能但有可能），
标准流程胜出。

### 批准 / 取消示例

```tsx
function ApprovalInterrupt() {
  useInterrupt({
    render: ({ interrupt, resolve, cancel }) => (
      <div className="p-3 border rounded">
        <p>{interrupt?.message ?? "Approve this action?"}</p>
        <div className="mt-2 flex gap-2">
          <button onClick={() => resolve({ approved: true })}>Approve</button>
          <button onClick={() => cancel()}>Cancel</button>
        </div>
      </div>
    ),
  });
  return null;
}
```

`resolve({ approved: true })` 记录一条已解析条目，并把 `resume`
数组提交给智能体。`cancel()` 记录一条已取消条目，做同样的事。
两者都在运行重启后返回 `RunAgentResult`。

### 多中断行为

有些智能体在一次运行中发出不止一个中断（例如两个独立的审批）。
每个中断有自己的 `id`。请逐个处理：

```tsx
useInterrupt({
  render: ({ interrupts, resolve, cancel }) => (
    <ul>
      {interrupts.map((i) => (
        <li key={i.id}>
          {i.message}
          <button onClick={() => resolve({ ok: true }, i.id)}>Approve</button>
          <button onClick={() => cancel(i.id)}>Cancel</button>
        </li>
      ))}
    </ul>
  ),
});
```

只有当**每个**打开的中断都被处理后，智能体运行才会恢复。带上具体
`interruptId` 调用 `resolve` 或 `cancel`
会把该中断标记为已完成；最后一个处理完时，hook
自动提交累积的响应。省略 `interruptId`
时，目标是主中断（`interrupts[0]`）。

### `responseSchema`——仅暴露，不做客户端校验

`Interrupt` 类型暴露一个 `responseSchema` 字段（一个 JSON Schema
对象），智能体可以用它描述期望的载荷形态。`useInterrupt`
把这个字段暴露在 `interrupt.responseSchema` 上供你的 UI 读取
（例如驱动一个表单），但**不会**据此校验 `resolve`
载荷。校验是智能体在恢复时的职责。
