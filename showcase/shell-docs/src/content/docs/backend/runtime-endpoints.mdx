当你用 `createCopilotExpressHandler`、
`createCopilotHonoHandler`、`copilotRuntimeNextJSAppRouterEndpoint` 或其他任何框架适配器挂载 CopilotKit 运行时，它会在你选择的
`basePath` 下服务一小组 HTTP 路由，比如 `/api/copilotkit`。大多数应用从不需要直接调用这些路由。前端代理（`ProxiedCopilotRuntimeAgent`）会替你调用。当你把运行时自托管在反向代理之后、要锁定认证，或要用 `curl` 调试连接失败时，用本页确认运行时到底暴露了什么。

<Callout type="info" title="其他运行时语言">
Python、Go、Ruby 和 C#/.NET 运行时要求 Intelligence 并服务多路由端点。React provider 请使用 `useSingleEndpoint={false}`；不要向那些服务器发送单路由信封。下文的 JavaScript handler 工厂、旧版端点与可选 TypeScript 特性都是 TypeScript 运行时特有的。原生服务器配置见 [Intelligence 快速开始](/intelligence/quickstart#connect-your-runtime)。
</Callout>

## Provider 与 handler 的配对

浏览器 provider 与 Runtime handler 必须在**传输方式**上达成一致。
CopilotKit 为每一半都提供了不止一个名字，而且它们不可互换：每种 provider 设置都要求匹配的 handler 模式。不同页面和旧应用展示着不同的配对，所以这张表就是映射关系：

<FrontendOnly frontend="react">

| Provider                                 | `useSingleEndpoint` | 传输方式                           | 所需 handler  | 路由文件                        |
| ---------------------------------------- | ------------------- | ---------------------------------- | ------------- | ------------------------------- |
| `<CopilotKit>` 或 `<CopilotKitProvider>` | 省略                | `auto`——从 Runtime 探测            | 皆可          | 与 handler 匹配                 |
| `<CopilotKit>` 或 `<CopilotKitProvider>` | `{true}`            | `single`                           | 单路由        | `route.ts`、`POST`              |
| `<CopilotKit>` 或 `<CopilotKitProvider>` | `{false}`           | `rest`                             | 多路由        | `[[...slug]]/route.ts`、4 个动词 |

`<CopilotKit>` 是一个向后兼容的包装器，内部渲染
`<CopilotKitProvider>`。两者都从
`@copilotkit/react-core/v2` 导出，而且自 1.70.2 起两者对省略的
`useSingleEndpoint` 一视同仁：传输方式为 `auto`，客户端会探测
Runtime 并匹配它实际服务的模式。

<Callout type="warn" title="固定了错误的模式会静默 404">
  向多路由 Runtime 传入 `useSingleEndpoint={true}` 会发送一个匹配不到任何路由的信封，于是 Runtime 返回 404，而 `GET /info` 仍返回 200，应用看起来像连上了。Runtime 的错误响应体会写明修复方法。

  1.70.2 之前，`<CopilotKit>` 内部把该标志固定为 `true`，因此省略它会选择单路由传输并对多路由 handler 返回 404。在这些版本上，请显式传入 `useSingleEndpoint={false}`。

</Callout>

两者出自同一个包入口，因此在它们之间切换只是改一下 import，不是迁移。有一个属性确实改名了：`<CopilotKit>` 用 `agent` 指定智能体，`<CopilotKitProvider>` 用 `agentId` 指定。

```tsx
// v1 wrapper
<CopilotKit runtimeUrl="/api/copilotkit" agent="my_agent" useSingleEndpoint={false}>

// v2 provider
<CopilotKitProvider runtimeUrl="/api/copilotkit" agentId="my_agent">
```

你也可以用 `<CopilotChat agentId="my_agent">` 为单个聊天指定智能体，或用 `<CopilotChatConfigurationProvider agentId="my_agent">` 为一个子树指定。provider 级的 `agentId` 是默认值，这两者可以覆盖它。

</FrontendOnly>

<FrontendOnly frontend="angular">

Angular 没有需要配置的 provider 配对：`provideCopilotKit` 会从 `/info` 发现传输方式，也不暴露 `useSingleEndpoint` 选项。对你而言只有下面的 handler 一半适用。

</FrontendOnly>

<FrontendOnly frontend="vue">

Vue 使用 `CopilotKitProvider`。省略 `use-single-endpoint` 时，它会从 `/info` 发现传输方式；单路由 handler 设为 `true`，多路由 handler 设为 `false`。

</FrontendOnly>

### 哪些 handler 服务哪种模式

| 模式                         | Handler                                                                                                                                                                                 |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 多路由（默认）               | `createCopilotRuntimeHandler`, `createCopilotHonoHandler`, `createCopilotExpressHandler`, `createCopilotNodeHandler`, `createCopilotNodeListener`                                       |
| 单路由                       | 以上任意一个加 `mode: "single-route"`                                                                                                                                                   |
| 仅单路由，无选项             | `copilotRuntimeNextJSAppRouterEndpoint`, `copilotRuntimeNextJSPagesRouterEndpoint`, `copilotRuntimeNodeHttpEndpoint`, `copilotRuntimeNodeExpressEndpoint`, `copilotRuntimeNestEndpoint` |

<Callout type="info" title="框架包装器支持 Intelligence 资源">
  每个 `copilotRuntime*Endpoint` 包装器都以
  `mode: "single-route"` 构建 handler。新式客户端与 Runtime 通过该端点承载 AG-UI Streams、Memory 与标注请求。设置
  `useSingleEndpoint={false}` 仍会让浏览器指向这些包装器并不服务的 REST 路由。

</Callout>

旧代码可能在用这些已弃用的别名：

| 已弃用                                    | 请改用                                                    |
| ----------------------------------------- | --------------------------------------------------------- |
| `createCopilotEndpoint`                   | `createCopilotHonoHandler`                                |
| `createCopilotEndpointSingleRoute`        | `createCopilotHonoHandler` 加 `mode: "single-route"`      |
| `createCopilotEndpointExpress`            | `createCopilotExpressHandler`                             |
| `createCopilotEndpointSingleRouteExpress` | `createCopilotExpressHandler` 加 `mode: "single-route"`   |

<Callout type="info" title="错配的配对在发现阶段就失败">
  错配在发现阶段就失败，而不是在你的应用代码里。多路由 provider 对单路由 Runtime 会在 `GET {basePath}/info` 上 404；单路由 provider 对多路由 Runtime 会发送 Runtime 不接受的信封。见[新线程上 connect 路由返回 404](#新线程上-connect-路由返回-404)。
</Callout>

## 多路由模式（默认）

默认情况下，运行时以**多路由**模式运行，每个操作暴露一条单独的路由。设 `basePath` 为 `/api/copilotkit`，路由如下：

| 方法与路径                                           | 用途                                                                                                                                                                                                         |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `GET /api/copilotkit/info`                           | Runtime 信息。前端在启动时调用它来发现已注册的智能体及其元数据。                                                                                                                                             |
| `GET /api/copilotkit/inspector-metadata`             | 给 Inspector 的可选受信项目、计划、许可、操作、用量与到期上下文。由 Intelligence 支撑的运行时会在 runtime-info 响应中以 `inspectorMetadata: true` 宣告这条路由。                                              |
| `POST /api/copilotkit/agent/:agentId/run`            | 启动一次智能体运行。请求体是 AG-UI 的 `RunAgentInput`；响应是 AG-UI 事件的 SSE 流。有 Intelligence 时，响应是 JSON。见[使用 Intelligence 运行与连接](#使用-intelligence-运行与连接)。                          |
| `POST /api/copilotkit/agent/:agentId/connect`        | 连接到智能体的线程。用于在重连或页面刷新后恢复流式传输。同样是 SSE 流，有 Intelligence 时为 JSON。                                                                                                            |
| `POST /api/copilotkit/agent/:agentId/stop/:threadId` | 停止给定线程上正在进行中的运行。可选的 JSON 体 `{ "runId": "..." }` 只停止该次运行。不是合法 JSON 或携带其他键的请求体会被以 400 拒绝，什么也不停止。                                                         |
| `POST /api/copilotkit/transcribe`                    | 转写音频（由语音 / 转写输入使用）。                                                                                                                                                                          |

`:agentId` 是你在 `new CopilotRuntime({ agents: { ... } })` 中注册智能体时用的键，比如 `default` 或
`research-agent`。`:threadId` 是该次运行所属的线程。

<Callout type="info">
  `GET /info` 路由与前端做智能体发现用的是同一个端点。如果它从运行时不可达，前端会报告一个
  `runtime_info_fetch_failed` 错误。见[错误调试](/troubleshooting/error-debugging)。
</Callout>

Intelligence 运行时还会返回 `runtimeEntitlements`。`ready` 包含归一化后的特性与限额值。`degraded`、`misconfigured` 与 `unavailable` 包含一个带 code、message 和重试标志的结构化错误。权益查询失败时 `/info` 请求仍然成功，核心 Runtime 行为得以继续；需要已验证权益的特性保持关闭。如果 Intelligence 以 `401` 拒绝项目密钥，Runtime 仍会从 `/info` 返回 `200`，响应体将 `runtimeEntitlements.status` 报告为 `misconfigured`，并附带不可重试的 `runtime_entitlements_misconfigured` 错误码。

### 使用 Intelligence 运行与连接

当运行时带有 `intelligence` 客户端时，run 与 connect 路由不再流式输出事件。它们返回一段 JSON，告诉客户端去哪里读取事件：

```json
{
  "threadId": "<thread id>",
  "runId": "<run id>",
  "joinToken": "<join token>",
  "realtime": {
    "clientUrl": "<Intelligence websocket URL>",
    "topic": "thread:<thread id>"
  }
}
```

客户端打开到 `realtime.clientUrl` 的 websocket，用 `joinToken` 加入 `realtime.topic` 频道。运行的 AG-UI 事件就到达该频道。runtime info 报告有 Intelligence 时，`CopilotKitProvider` 会替你做这一切。connect 路由返回相同的响应体但不含 `runId`；平台没有返回连接时，返回无响应体的 `204`。

直接向 run 路由发 `POST`（比如来自 `curl` 或测试脚本）只会得到这个 JSON 体而没有事件。要在没有 websocket 客户端的情况下读取线程的事件，请调用 `GET {basePath}/threads/:threadId/events`。它返回 `{ "events": [...] }`。见[线程路由](#线程路由)。

### Inspector 元数据

由 Intelligence 支撑的运行时会在 runtime-info 响应中加上 `inspectorMetadata: true`。主连接完成后，`@copilotkit/core` 会用这个标志在后台请求 `GET {basePath}/inspector-metadata`。旧运行时省略该标志，因此新客户端会跳过这个可选请求。

有效的响应是一个带版本的 `InspectorMetadataV1` JSON 对象。响应始终使用 `Cache-Control: no-store, private`。当数据缺失、schema 不受支持、运行时没有 Intelligence 支撑，或 provider 请求失败时，该路由以相同缓存策略返回 `204`。元数据失败不会改变运行时连接或智能体状态。上游 Intelligence 请求有五秒期限；超时走同样的私有 `204` 路径。

```json
{
  "schemaVersion": 1,
  "identity": {
    "organizationName": "Acme",
    "projectName": "Support"
  },
  "plan": {
    "code": "team",
    "label": "Team"
  },
  "license": {
    "state": "valid"
  },
  "action": {
    "kind": "manage_plan",
    "url": "https://ops.example.com/account/organization/org_123/organization-billing"
  },
  "usage": {
    "used": 42,
    "limit": {
      "kind": "finite",
      "value": 1000
    },
    "expiringSoonCount": 7
  }
}
```

每个模块都是可选且独立的。`usage.expiringSoonCount` 是一个增量式 V1 叶子字段，表示未来 24 小时内的到期数量：`0` 是一个已知的计数，而缺失表示没有可信的到期计数可用。共享层会移除格式错误的到期叶子，而不会移除有效的 `used`、`limit` 或同级模块。旧 V1 生产者可以省略该叶子，旧消费者也可以忽略它，无需同步部署。

```bash
curl -i http://localhost:4000/api/copilotkit/inspector-metadata
```

<Callout type="info">
  运行时用它的服务器端 Intelligence API 密钥发起上游请求。它不会把浏览器的请求头或 cookie 转发给 Intelligence，也不会把 provider 的错误响应体暴露给浏览器。认证请求头和 cookie 仍可以像保护任何其他运行时路由那样保护浏览器到运行时的请求。
</Callout>

### 线程路由

运行时还服务着线程 UI 背后的会话历史。无论你用哪个运行器，这些路由在多路由模式下都存在：

| 方法与路径 | 用途 |
|---|---|
| `GET /api/copilotkit/threads` | 列出线程。有 Intelligence 时，`agentId` 查询参数必填。没有 Intelligence 时，它可选并用于过滤列表。 |
| `GET /api/copilotkit/threads/:threadId/messages` | 该线程的完整消息历史。 |
| `GET /api/copilotkit/threads/:threadId/events` | 该线程的压缩 AG-UI 事件流。 |
| `GET /api/copilotkit/threads/:threadId/state` | 该线程的最后一次状态快照。 |
| `POST /api/copilotkit/threads/clear` | 清空内存中的线程历史。始终返回 `204`；在不持有本地存储的运行器上什么也不清。 |
| `PATCH` 或 `DELETE /api/copilotkit/threads/:threadId` | 重命名或删除线程。仅 Intelligence。 |
| `POST /api/copilotkit/threads/:threadId/archive` | 归档线程。仅 Intelligence。 |
| `POST /api/copilotkit/threads/subscribe` | 订阅线程变更。仅 Intelligence。 |

请求没有 `agentId` 时，Intelligence 运行时会以 `400` 应答 `GET /threads`。请发送你在 `CopilotRuntime` 中注册的智能体键。请求还必须带上你的 `identifyUser` 要读取的认证信息，因为列表只包含该用户的线程：

```bash
curl -s "http://localhost:4000/api/copilotkit/threads?agentId=default"
```

响应是 `{ "threads": [...], "nextCursor": ... }`。要翻页，传 `limit` 和上一次响应的 `cursor`。加 `includeArchived=true` 以包含已归档的线程。这三个参数仅在 Intelligence 下适用。

<Callout type="warn" title="线程路由不会替你做授权">
在默认的 `InMemoryAgentRunner`——以及任何继承它的实现（如
`AgentCoreRunner`）——上，这些路由读取运行器的本地存储，完全不解析用户：到达路由的任何调用者都能读取它点名的线程，`GET
/threads` 列出进程内的每个线程，而 `POST /threads/clear` 会清空所有。不持有本地存储的运行器（如 `SqliteAgentRunner`）则以 `422` 应答那四条读取路由。

Intelligence 运行时会把它**大多数**路由限定到 `identifyUser` 返回的用户，但不是全部：`threads/events`、`threads/state` 和
`POST /agent/:agentId/stop/:threadId` 仍只凭 id 读取线程。即便在平台上，这三条也要自己设防。

`:threadId` 由客户端在运行时选定，因此它不是秘密。如果你的部署不止一个人用，请自行给这些路由做授权——见
[线程授权](/auth#thread-authorization)。
</Callout>

### 用 curl 探测运行时

确认自托管运行时是否接好的最快办法，就是直接请求 `/info`：

```bash
curl -s http://localhost:4000/api/copilotkit/info
```

你应该得到一个描述已注册智能体的 JSON 响应体。如果得到 404，说明你的 `basePath` 与请求的 URL 不匹配（或者 handler 没有挂载）。如果得到连接错误，说明服务器没有在那个主机/端口上监听。

### 选择 Runtime 路由模式

单路由和多路由 handler 都能暴露 AG-UI Streams。当你的服务器应当只暴露一个 `POST` 端点时，用单路由：

### 构造 Intelligence 客户端

`intelligence` 是一个 `CopilotKitIntelligence` 实例。用你项目的 Intelligence API 密钥来构建它：

```ts
import { CopilotKitIntelligence } from "@copilotkit/runtime/v2";

const intelligence = new CopilotKitIntelligence({
  apiKey: process.env.CPK_INTELLIGENCE_API_KEY!,
});
```

`apiKey` 是唯一必填的选项。`copilotkit project select` 会把这个键写入你项目的 `.env`，名为 `CPK_INTELLIGENCE_API_KEY`，而这里正是消费它的地方。

密钥要保存在服务器端。它是项目 API 密钥，与 [Inspector](/inspector) 使用的、浏览器可见的 `NEXT_PUBLIC_COPILOTKIT_LICENSE_KEY` 是不同的凭证——不要相互替代。

`apiUrl` 和 `wsUrl` 默认指向云托管平台。API 与实时平面部署在**不同的主机**上，因此不能通过换协议（scheme）从其中一个推导出另一个。只在自托管或非生产部署时覆盖它们，并且要**同时覆盖两者**——只设一个会把两个平面指向不同的部署，并记录一条警告：

```ts
const intelligence = new CopilotKitIntelligence({
  apiKey: process.env.CPK_INTELLIGENCE_API_KEY!,
  apiUrl: process.env.INTELLIGENCE_API_URL,
  wsUrl: process.env.INTELLIGENCE_GATEWAY_WS_URL,
});
```

<Step>
### 识别已登录的应用用户

由 Intelligence 支撑的 Web Runtime 只有在能把线程限定到某个应用用户时才暴露 Threads。添加 `identifyUser`，从服务器验证过的会话或令牌解析用户：

```ts
const runtime = new CopilotRuntime({
  agents,
  intelligence,
  identifyUser: async (request) => {
    const user = await authenticateApplicationUser(request);
    if (!user) throw new Error("Unauthorized");
    return { id: user.id, name: user.name };
  },
});
```

完整的身份与授权模式见[将 AG-UI 流限定到登录用户](/threads-lifecycle#scope-rich-threads-to-the-signed-in-user)。

</Step>

单路由：挂载一个精确路径并允许 `POST`：

```ts title="app/api/copilotkit/[[...slug]]/route.ts"
export { handler as GET, handler as POST, handler as PATCH, handler as DELETE };
```

完整的适配器示例见[部署到任意运行时](/runtime-server-adapter#multi-route-vs-single-route)。

## 单路由模式

如果你更想只暴露一个 `POST` 端点——比如为了简化反向代理规则或 API 网关——传入 `mode: "single-route"`。在该模式下，运行时暴露一个 `POST {basePath}` 端点，接受 JSON 信封 `{ method, params, body }`，并在内部分发到同一批 handler：

```ts title="app/api/copilotkit/route.ts (Express)"
import { CopilotRuntime, BuiltInAgent } from "@copilotkit/runtime/v2";
import { createCopilotExpressHandler } from "@copilotkit/runtime/v2/express";

const runtime = new CopilotRuntime({
  agents: { default: new BuiltInAgent({ model: "openai/gpt-4o-mini" }) },
});

app.use(
  createCopilotExpressHandler({
    runtime,
    basePath: "/api/copilotkit",
    mode: "single-route",
  }),
);
```

<Callout type="info" title="自行安装 `express`">
  `express` 是 `@copilotkit/runtime` 的可选 peer 依赖，所以不会自动安装。在挂载适配器的应用中运行 `npm install express`（`^4.18.0 || ^5.0.0`）。没有它就调用 `createCopilotExpressHandler` 会抛错并写明修复方法。运行时里没有其他地方需要 express，因此 Hono 和 Next.js 应用什么也不必装。
</Callout>

<Callout type="warn" title="两种模式下 `basePath` 都是必填的">
  Express 与单路由 handler 在缺少 `basePath` 时都会在挂载时抛错——分别是 `basePath must be provided for Express endpoint` 和 `... for single-route endpoint`——因此服务器会启动失败，而不是在错误的路径上服务。把路由实际挂载的路径传给它。
</Callout>

<Callout type="warn" title="所有运行时 import 都走 `/v2`">
  从 `@copilotkit/runtime/v2` 导入运行时（Express 适配器从
  `@copilotkit/runtime/v2/express`）。从包根 `@copilotkit/runtime` 拿到的是 v1 接口面：在那里构建的 `CopilotRuntime` 不服务这些路由，而且这种错配表现为路由 404，而不是 import 报错。
</Callout>

可选的 Inspector 元数据操作用同一个端点，信封如下：

```json
{ "method": "inspector/metadata" }
```

它的响应与失败规则与 `GET {basePath}/inspector-metadata` 一致。

客户端通过同一端点以 `resource/request` 信封发送线程、记忆与标注操作。Runtime 只接受已知的资源路径，并把它们路由到与多路由模式相同的 handler。

<FrontendOnly frontend="react">
前端会自行检测这种模式，所以不需要任何属性。要显式固定，传 `useSingleEndpoint`：

```tsx
import { CopilotKit } from "@copilotkit/react-core/v2";

<CopilotKit runtimeUrl="/api/copilotkit" useSingleEndpoint>
  <YourApp />
</CopilotKit>;
```

<Callout type="warn">
前端传输方式必须与运行时模式匹配。运行时是单路由模式而前端发的是多路由请求（或反过来）时，每次调用都会 404。省略该属性从结构上就避免了这一点，因为客户端会探测运行时实际服务的模式——所以只有想跳过这次探测时才固定 `useSingleEndpoint`。
</Callout>
</FrontendOnly>

<FrontendOnly frontend="angular">
Angular SDK 从 Runtime info 响应协商传输方式。把 `provideCopilotKit` 指向基础端点即可；无需第二个路由配置：

```ts title="src/app/app.config.ts"
provideCopilotKit({
  runtimeUrl: "/api/copilotkit",
});
```

<Callout type="warn">
Runtime info 必须通过所选传输方式保持可达，Angular 客户端才能发现传输方式与已注册的智能体。
</Callout>
</FrontendOnly>

<FrontendOnly frontend="vue">
Vue SDK 同样从 Runtime info 发现传输方式。把 `CopilotKitProvider` 指向基础端点即可；无需第二个路由配置：

```vue
<CopilotKitProvider runtime-url="/api/copilotkit">
  <YourApp />
</CopilotKitProvider>
```

<Callout type="warn">
Runtime info 必须保持可达，Vue 客户端才能发现传输方式与已注册的智能体。
</Callout>
</FrontendOnly>

## CORS

Express 与 Hono 适配器默认应用宽松的 CORS（`origin: "*"`、所有标准方法、所有请求头），本地开发开箱即用。传 `cors: false` 可禁用内置中间件并自行处理 CORS，或传入配置对象在生产环境收紧范围：

```ts
createCopilotExpressHandler({
  runtime,
  basePath: "/api/copilotkit",
  cors: {
    origin: "https://app.example.com",
    methods: ["GET", "POST", "OPTIONS"],
  },
});
```

## 认证请求

这些路由跑在你的服务器上，因此正是实施认证的地方。适配器接受生命周期 `hooks`。`onRequest` hook 在每个请求之前运行，可以通过抛出一个 `Response` 来拒绝请求：

```ts
createCopilotExpressHandler({
  runtime,
  basePath: "/api/copilotkit",
  hooks: {
    onRequest: ({ request }) => {
      if (!request.headers.get("authorization")) {
        throw new Response("Unauthorized", { status: 401 });
      }
    },
  },
});
```

`onRequest` 在路由之前运行，因此它知道路径但不知道路由。要按线程做决策，请用 `onBeforeHandler`，它在路由之后运行，收到解析出的 `route`，包括其中的 `threadId`：

```ts
createCopilotExpressHandler({
  runtime,
  basePath: "/api/copilotkit",
  hooks: {
    onBeforeHandler: async ({ request, route }) => {
      const user = await resolveUser(request);

      // Routes that name a thread on `route`.
      if ("threadId" in route) {
        if (!(await userOwnsThread(user.id, route.threadId))) {
          throw new Response("Forbidden", { status: 403 });
        }
        return;
      }

      // agent/run and agent/connect carry the thread in the body instead.
      if (route.method === "agent/run" || route.method === "agent/connect") {
        // Clone: the handler still needs to read the original body.
        const { threadId } = await request.clone().json();
        if (threadId && !(await userOwnsThread(user.id, threadId))) {
          throw new Response("Forbidden", { status: 403 });
        }
      }
    },
  },
});
```

`route.threadId` 存在于 `agent/stop`、`threads/messages`、
`threads/events`、`threads/state`、`threads/update` 和 `threads/archive` 上。
`threads/list`、`threads/clear` 和 `threads/subscribe` 完全不携带线程，因此对这三条唯一可做的决定就是是否放行。

完整的认证指南见[身份验证](/auth)，本例假设的归属映射见
[线程授权](/auth#thread-authorization)。

对于 Inspector 元数据，Core 会在可选请求上发送当前这些浏览器到运行时的请求头与 fetch 凭证。随后 Runtime 以它配置的 Intelligence API 密钥另起一个服务器到 Intelligence 的请求。

## 新线程上 connect 路由返回 404

一个常见的自托管症状是：页面刚加载完、用户还没发送任何消息，`POST /agent/:agentId/connect` 路由就返回 `404`。这通常意味着以下两种情况之一：

1. **URL 中的 `agentId` 没有注册**。没有智能体匹配时，运行时以
   `404` 返回 `{"error":"Agent not found","message":"Agent '<id>' does not exist"}`。预构建组件默认使用名为
   `"default"` 的智能体，因此请在这个键下注册一个（或显式传入 `agentId`）。
2. **对自动铸造的线程，`connect()` 在任何 `run()` 之前被调用**。某些持久化后端只有在一次运行产出事件之后才认识这个线程。
   见 [AgentRunner](/backend/agent-runner) 指南和
   [`/connect` 返回 404 的故障排查条目](/troubleshooting/common-issues#connect-route-returns-404-on-a-fresh-thread)。
