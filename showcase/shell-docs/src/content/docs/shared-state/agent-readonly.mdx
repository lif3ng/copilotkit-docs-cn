## 这是什么？

有时你想让智能体*了解*当前 UI 的一些信息，比如已登录的用户、当前页面或最近的活动日志，但又不希望智能体能够修改它们。这正是 `useAgentContext` 的用途：一条 **UI → 智能体** 的单向只读上下文通道。

与完整的共享状态（智能体可以调用工具修改状态并同步回 UI）不同，`useAgentContext` 的值是纯输入。智能体会在每一轮通过运行时的上下文注入看到这些值，但它没有任何 setter，也没有工具能把值写回去。

## 什么时候应该使用它？

在以下情况下，应使用 `useAgentContext` 而不是完整的共享状态：

- 该值**由 UI 持有**，对智能体而言除了“用户当前正在看什么”之外没有别的意义。
- 智能体只应读取而绝不写入（用户身份、功能开关、选中的记录、滚动位置）。
- 你希望该值在组件卸载时自动注销（例如离开页面时“当前记录”上下文随之消失）。

可以把它理解为“智能体的 props”。

## 代码中的工作方式

<FrameworkSetup concept="agent-context-setup" />

每发布一个值就调用一次 `useAgentContext({ description, value })`。每次调用都会向运行时注册一个动态上下文条目，它会：

- 在 `value` 变化时刷新（React 重新渲染）。
- 在组件卸载时自动移除。
- 通过后端的 `CopilotKitMiddleware` 呈现给智能体，它会在每一轮把这些条目织入模型的消息历史。

`description` 很重要：它是智能体在看到值的同时看到的一段简短的人类可读标签，让智能体知道该拿这个值做什么。把它当作参数的 docstring 来对待。

## 接入你自己的状态

`useAgentContext` 并不关心值来自哪里：本地 state、React Context、Redux、查询缓存，什么都可以。唯一的要求是值的标识（identity）足够稳定，让 React 能避免陷入渲染循环。在演示中我们用了几个 `useState` 钩子；而在真实应用中，这些值很可能来自身份验证提供方、路由钩子以及你的领域状态存储。

## 设计上只读

由于智能体永远看不到这些值的 setter 或修改工具，即使 LLM 出现混乱也无法“更新”它们。这使得 `useAgentContext` 成为正确之选——只要所讨论的值是输入而非字段：它是“每一轮传给智能体的上下文对象”，而非“你与智能体共同编辑的共享工作区”。

当你既需要读取*又*需要写入时，应该改用完整的 **[共享状态](/shared-state)**。
