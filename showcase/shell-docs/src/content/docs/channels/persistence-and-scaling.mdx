Intelligence 以持久化方式持有提供方入口与规范的 Thread 历史。基于 Redis 的认领与有序包协调活跃的提供方投递。你的 Channels 进程仍持有 SDK 工作流状态。这是两个相互独立的持久化边界。

## 了解默认情况下哪些是进程本地的

如果没有 `createChannel({ store: { adapter } })`，SDK 会使用 `MemoryStore`。进程重启后，以下值会消失：

- `thread.state()`
- 用于恢复回调的已注册组件快照
- SDK 会话记录列表
- SDK 锁、去重窗口与队列

托管对话历史则不同：即使 SDK 存储还在内存中，Intelligence 也能重建近期的提供方回合。

<Callout type="warn" title="Online 不等于重启安全">
  Intelligence 的 **Online** 状态只证明监听器已连接。它不能证明一个待处理的审批或应用工作流能在部署后幸存。
</Callout>

## 配置带类型的工作流状态

使用 Standard Schema 为读取添加类型，并校验完整的替换值：

```bash title="Terminal"
npm install zod
```

<FrontendOnly frontend="slack">

```ts title="channel.ts"
import { createChannel } from "@copilotkit/channels";
import { z } from "zod";
import { durableStateStore } from "./state-store.js";

const workflowState = z.object({
  incidentId: z.string(),
  stage: z.enum(["triage", "awaiting-approval", "resolved"]),
});

const channel = createChannel({
  name: required("CHANNEL_CODE"),
  identifyUser: "platform",
  agent: makeAgent,
  store: {
    adapter: durableStateStore,
    state: workflowState,
  },
});

channel.onMessage(async ({ thread, message }) => {
  const current = await thread.state();

  await thread.setState({
    incidentId: current?.incidentId ?? "INC-421",
    stage: "triage",
  });

  await thread.runAgent({ prompt: message.text });
});
```

</FrontendOnly>

`setState(value)` 会替换整个值，不会合并部分补丁。请存储可 JSON 序列化的值；远程后端不会保留 `Date`、`Map`、类实例或函数。

## 实现 StateStore 的每个 facet

一个完整的生产级存储要实现：

| Facet   | 必需行为                                                     |
| ------- | ---------------------------------------------------------- |
| `kv`    | 读取、带可选 TTL 的写入、原子消费与删除                      |
| `list`  | 由旧到新的追加/范围读取、上限、裁剪、删除与列表 TTL           |
| `lock`  | 原子获取加上基于 token 校验的释放                            |
| `dedup` | 带 TTL 的原子首次可见检查                                    |
| `queue` | 先进先出的入队/出队/深度，配合有界溢出策略                    |

锁、去重和队列在共享同一后端的每个进程之间都必须是原子的。命名空间必须能防止一个项目或 Channel 读到另一个的键。

对你的适配器运行 SDK 的 Vitest 一致性测试套件：

```bash title="Terminal"
npm install -D vitest
```

```ts title="state-store.test.ts"
import { runStateStoreConformance } from "@copilotkit/channels/testing";
import { createRedisStateStore, closeRedisStateStore } from "./redis-store.js";

runStateStoreConformance(
  "redis",
  () => createRedisStateStore(),
  (store) => closeRedisStateStore(store),
);
```

针对真实后端运行它：

```bash title="Terminal"
npx vitest run state-store.test.ts
```

SDK 附带 `MemoryStore` 和一致性测试套件；umbrella package 中不附带完整持久化的 Redis 或 Postgres 实现。

## 让交互回调跨重启保留

只有同时满足以下两个条件，回调才能幸存：

1. JSX 来自注册在 `createChannel({ components })` 中的具名组件。
2. 操作快照存储在持久化的 `StateStore` 中。

<FrontendOnly frontend="slack">

```tsx title="channel.tsx"
const channel = createChannel({
  name: required("CHANNEL_CODE"),
  identifyUser: "platform",
  agent: makeAgent,
  components: [ApprovalCard],
  store: { adapter: durableStateStore },
});
```

</FrontendOnly>

<FrontendOnly frontend="teams">

```tsx title="channel.tsx"
const channel = createChannel({
  name: required("CHANNEL_CODE"),
  identifyUser: "platform",
  agent: makeAgent,
  components: [ApprovalCard],

```

</FrontendOnly>

保持已注册组件的 props 可 JSON 序列化，并从这些 props 推导处理器。测试方法：发送一张卡片，重启进程，然后点击旧卡片。

## 匹配托管的并发模型

### 投递认领（多副本）

每条准备好的投递只有一个认领胜者。每个声明了匹配 Channel 的已连接 Runtime 都可以收到邀请、检查本地容量并尝试认领。不同副本可以同时服务不同会话；不存在 Channel 级的领导者。

保持每个副本的 Channel 声明与智能体代码一致。托管监听器在内部限制活跃与待处理的投递工作量。达到内部容量的 Runtime 会在认领之前拒绝新邀请；该容量目前不是公开的 Channel 配置选项。

提供方效果每次只使用一个有序包。SDK 会在已知的重试等待或重连之后重试同一个包。如果一次提供方调用结果变得不确定，Gateway 会记录一个不确定的终态结果，而不是再次发送。当应用可能多次调用某个工具时，应用工具仍需要自己的幂等键；可使用 `message.eventId`、`message.turnId` 或持久的操作 ID。

### 回合并发（同一会话）

托管准入让一个规范 Thread 在一个 Runtime 上独占。当第一条投递仍然活跃时，该 Thread 的第二条邀请不会被认领。无关的 Thread 在托管监听器的有界容量内并行继续。

这个投递守卫与其它适配器路径使用的 SDK `store.concurrency` 设置是分开的。请为你的应用状态规则选择该设置；不要用它来提高托管的同 Thread 投递上限。参见 [`StoreConfig`](/reference/channels/types/StoreConfig)。

## 生产检查清单

- 优先使用智能体工厂；单例会在每次运行时自动克隆。
- 如果需要串行的工作流状态，请有意识地设置 `store.concurrency`。
- 在承诺重启安全的状态或回调之前，先提供持久化存储。
- 针对真实后端运行 StateStore 一致性测试套件。
- 在卡片等待点击时测试一次重启。
- 让外部写入保持幂等。
- 保持各副本的 Channel 声明一致；当托管监听器的有界本地容量不足时，进行水平扩展。
- 对 Intelligence 的 **Conflict**、**Offline** 和 **Delivery failing** 告警。
- 在收到 `SIGINT` 和 `SIGTERM` 时停止监听器。
