托管 Channel 是一个持有出站实时连接的长驻 worker。它不是无服务器请求处理器。请像部署队列消费者或 WebSocket worker 一样部署它。

## 使用经过验证的运行时组合

<ChannelsInstall />

请运行 Node.js 22 或更高版本。托管启动器依赖 Node.js 22+ 中提供的全局 `WebSocket`。

更改其中任一 package 后，请运行与初始快速开始相同的真实提供方冒烟测试。

## 先等激活落定再上报就绪

创建 Node 监听器即启动托管连接——声明的 Channel 因为被声明就会连接，不存在忘记调用 start 的问题。await `ready()` 以观察激活落定，然后检查 `status()`：

```ts title="health.ts"
const channels = listener.channels;

await channels.ready({ timeoutMs: 30_000 });

const initial = channels.status();
if (initial.overall !== "online") {
  throw new Error(`Channels not online: ${JSON.stringify(initial)}`);
}
```

`ready()` 可能在 `setup_required` 状态下 resolve；这意味着激活已落定，而不是投递健康。只有 `status().overall === "online"` 才视为健康的已连接激活。

运行时状态值如下：

| 运行时状态       | 含义                                                                                   |
| ---------------- | -------------------------------------------------------------------------------------- |
| `connecting`     | 激活尚未落定                                                                             |
| `online`         | 托管连接健康，可认领投递邀请                                                             |
| `setup_required` | Intelligence 提供方配置未完成                                                            |
| `reconnecting`   | 网关连接中断，正在重试                                                                   |
| `error`          | 激活失败，或重连放弃（默认约 60 秒）将会话标记为不可发送                                  |
| `stopped`        | Channels 控制器已停止                                                                    |

对上线后的 `error` 要谨慎对待：重连放弃后，客户端会标记 `error`，而 Phoenix **仍在底层持续重试**。重加入成功后无需重启进程即可恢复 `online`。激活阶段的 `error`（密钥错误、网关不可达、配置问题）则不同——请修复配置并重启 worker。

Intelligence UI 会把提供方与运行时细节转换为自己的运维可见状态，例如 **Waiting for runtime**、**Conflict**、**Offline**、**Delivery failing** 和 **Online**。

## 分别暴露存活与就绪探针

- 存活（liveness）回答 Node 进程与事件循环是否在运行。
- 就绪（readiness）回答 `channels.status().overall` 是否为 `online`。

短暂的 `reconnecting` 不要立即重启；实时客户端自身管理有界的重连与重加入（默认重连放弃窗口约为 60 秒，之后状态变为 `error`，但重试仍在继续）。对 `error` 告警；只有当超出你自己的中断预算，或激活在从未上线之前就失败时才重启。

从你的健康检查端点或监控循环轮询 `status()`。不要永久缓存启动时的结果，因为一个在线会话之后可能转为 reconnecting 或 error。

## 干净地关停

要在**创建监听器**之前注册信号处理器，而不仅仅是在 `ready()` 之前。创建监听器即开始激活，因此连接窗口内到达的信号必须已有落点——否则它会命中 Node 的默认处理器，并遗留下一个仍存活的网关会话：

```ts title="channel.ts"
let teardown: (() => Promise<void>) | undefined;
const shutdown = async () => {
  await teardown?.();
};

process.once("SIGINT", shutdown);
process.once("SIGTERM", shutdown);

const listener = createCopilotNodeListener({ runtime });
const server = createServer(listener);
teardown = async () => {
  await listener.channels.stop();
  if (server.listening) server.close();
};

await listener.channels.ready({ timeoutMs: 30_000 });
```

给 worker 足够的终止宽限期以停止其托管会话。在可以优雅关停的情况下，避免在 `channels.stop()` 释放所有权之前强行切断。

## 保存并轮换密钥

以下内容只保存在服务端：

```dotenv title=".env"
CPK_INTELLIGENCE_API_KEY=<project-runtime-key>
CHANNEL_CODE=<exact-intelligence-code>

# Optional paired overrides for self-hosted or non-production Intelligence:
# INTELLIGENCE_API_URL=https://intelligence.example.com
# INTELLIGENCE_GATEWAY_WS_URL=wss://realtime.intelligence.example.com
```

云端托管的 Intelligence 会提供默认端点。对于自托管或非生产部署，请同时覆盖两个 base。不要从一个推导另一个，也不要追加 `/api`、`/socket`、`/runner`、`/client` 或 `/channels`。

提供方凭据保存在 Intelligence 中。runner 不应包含 Slack token 或 Microsoft Teams 的 client secret。通过你的密钥管理器轮换项目运行时密钥，用新值重启监听器，并确认它恢复为 **Online**。

## 限制活跃副本

Intelligence 会把每一条准备好的投递提供给声明了匹配 Channel 的已连接 Runtime。一条投递由一个 Runtime 认领；其他副本可以同时认领不同的投递。

在每个副本上运行相同的构建与 Channel 声明。托管监听器在内部限制活跃与待处理的投递工作量。已满载的 Runtime 会在认领投递之前拒绝邀请，从而让另一个符合条件的副本得以认领它。该容量目前没有作为公开的 Channel 配置选项暴露出来。

## 观测完整投递路径

至少要记录：

- 启动过程与首个非 online 状态
- 向 `reconnecting`、`error` 的转换以及恢复到 `online`
- Channel Code 与提供方，不含凭据
- 应用工具错误及其幂等 id
- 用于关联的 `message.eventId`、`message.turnId` 和 `message.deliveryId`
- `thread.postFile()` 失败

默认情况下不要记录消息正文、已水合的文件、API 密钥、Slack token、Microsoft Teams secret 或原始提供方 payload。

## 发布检查清单

1. 在 Node.js 22 上构建 runner 并进行类型检查。
2. 确认 lockfile 中包含确切的 package 组合。
3. 启动预期的副本集，并等待每个监听器报告 `online`。
4. 发送一条真实提供方消息并验证收到回复。
5. 实测一个工具、一条富消息和一次交互。
6. 在有待处理审批的情况下重启，并验证你的持久化承诺。
7. 测试一次短暂断网，观察 `reconnecting` 恢复。
8. 发送并发消息，验证各副本在各自本地限额内认领互不相同的投递。
9. 发送 `SIGTERM` 并确认优雅关停。

控制平面状态请参阅 [Intelligence 演练](/channels/intelligence)，重启安全的应用状态请参阅[持久化与扩展](/channels/persistence-and-scaling)。
