## 概览

Automatic Learning 把真实智能体运行中的模式转化为你可以发布的 Skill。它读取 [AG-UI Streams](/AG-UI-Streams) 中已完成的对话，撰写 Insight，并提议供你审阅的指令，审阅通过后才会发布。

## 从你的编码智能体开始

## Automatic Learning 的工作方式

Learning 从一个容器开始，容器把同一类工作的线程归为一组。Intelligence 会分析该容器中已完成的运行，并把反复出现的模式总结为 Insight。

当某个模式可以复用时，Learning 会提议一个 Skill。你审阅支撑它的线程，并决定是否发布。已发布的 Skill 是一组带版本的指令，由你加载进智能体；Learning 不会改变模型本身。

Automatic Learning 按每日计划检查符合条件的容器。在你批准某个 Skill 之后，[Skill 交付](/intelligence/learned-skills)会让已连接的智能体能够使用它。计划运行不会自动批准 Skill。开启交付也不会替你连接智能体。

要记录用户在应用中围绕智能体的操作，例如工具 UI 中的点击与页面切换，请参阅[捕获交互](/intelligence/capture-interactions)。

## 收集运行并交付 Skill

Learning 闭环包含两条连接。运行摄取把证据收集到 Learning 容器中；Skill 交付把已发布的指令加载进智能体。

| 连接 | 配置 | 结果 |
| --- | --- | --- |
| Runtime 到 Automatic Learning | `CopilotKitIntelligence.getLearningContainerId` | 把选定的线程分配到某个容器以供分析。 |
| 浏览器活动到 Automatic Learning | `CopilotKitIntelligence.getTrajectoryLearningContainerIds` | 把捕获的轨迹分配到既有的 Learning Space。 |
| Learning 到智能体 | 适配你的框架的 Intelligence SDK 适配器 | 让已发布的 Skill 在智能体调用期间可用。 |

当智能体需要从自己的工作流中学习时，请为两条连接使用相同的项目和容器。SDK 适配器也可以用于 CopilotKit 前端之外的原生智能体，但它们不会自动收集这些智能体的运行。

智能体配置请参考 [Mastra](/intelligence/learned-skills#mastra)、[LangGraph TypeScript](/intelligence/learned-skills#langgraph-typescript) 或 [LangGraph Python](/intelligence/learned-skills#langgraph-python) 示例。交付指南还涵盖 [Google ADK](/intelligence/learned-skills#google-adk)、[BuiltInAgent](/intelligence/learned-skills#builtinagent) 与 [Microsoft Agent Framework](/intelligence/learned-skills#microsoft-agent-framework)。

## 将浏览器活动分配到 Learning Space

对于已连接 Intelligence 的捕获，请在 Runtime 的服务端配置中选择既有的 Learning Space：

```ts
const intelligence = new CopilotKitIntelligence({
  apiKey: process.env.CPK_INTELLIGENCE_API_KEY!,
  getTrajectoryLearningContainerIds: ({ trajectoryId, user }) =>
    ["expense-review"],
});
```

请在捕获开始之前创建好 Space。回调会收到浏览器选择的轨迹 ID，以及经你的 Runtime 验证的应用用户。它不需要线程或智能体对话。浏览器提供的 Space ID 会被忽略。已关联线程所在的 Space 并不会把轨迹加进去；要在分析期间展示轨迹对应的聊天，还需用 `getLearningContainerId` 把它的线程分配到同一个 Space。

返回 `[]` 可显式表示不请求新的分配；返回 `null` 或 `undefined` 则在连接请求中省略分配。每次连接只会增加成员关系，绝不会移除既有成员关系，因此在多次重连之间请保持选择稳定。在 Intelligence 中被移除的成员关系会保持移除状态。

分配出问题绝不会让捕获停止。如果所选 Space 在项目中不存在，Runtime 会带着轨迹与 Space ID 记录一条警告，并在完全没有任何分配（包括确实存在的 Space）的情况下连接轨迹。回调有 5 秒的时限。它的可选第二个参数是一个 `AbortSignal`，在请求结束或时限到期时取消。如果回调抛出异常、返回无效 ID 或超出时限，Runtime 会记录错误，并在没有分配的情况下连接轨迹。当轨迹没有出现在某个 Space 中时，请检查 Runtime 日志。你的 Intelligence 后端必须支持 Automatic Learning 的轨迹输入。仅分配本身不会启动分析，也不保证产生 Insight。

## 手动配置 Automatic Learning

完成后，你的 Runtime 会把选定的线程发送到 Learning 容器，等待分析并转化为经审阅的 Skill。

<Steps>
  <Step>
    ### 连接 CopilotKit Intelligence

    先完成 [Intelligence 快速开始](/intelligence/quickstart)。该页面会用 CLI 帮你登录并选择项目。然后发送一条消息，确认它出现在 [AG-UI Streams](/AG-UI-Streams) 中。在 [CopilotKit Intelligence](https://dashboard.operations.copilotkit.ai/) 中打开你的项目，确认 Learning 可用。

  </Step>

  <Step>
    ### 创建 Learning 容器

    在你的 Intelligence 项目中，打开 **Learning** 并选择 **Create Learning container**。为容器设置一个稳定 ID、一个描述性名称，以及关于“什么算好的工作”的可选指引。

    让每个容器只聚焦一类工作，例如报销审核、支持质量或客户入职。稳定 ID 由 1–64 个小写字母、数字或单个连字符组成，例如 `expense-review`。

    也可以使用 CLI。在你选择项目的文件夹中运行以下命令。首先，列出现有的容器：

    ```bash title="终端"
    npx copilotkit@latest learning containers list
    ```

    如果已有针对这类工作的容器，请复用它的 ID。不要为同一类工作创建第二个容器。

    如果没有合适的容器，打印项目的默认容器 ID。CLI 会根据你的项目 slug 生成这个 ID，它不会检查容器是否存在。

    ```bash title="终端"
    npx copilotkit@latest learning containers default-id
    ```

    然后用该 ID 和一个名称创建容器：

    ```bash title="终端"
    npx copilotkit@latest learning containers create --id <container-id> --name "<container name>"
    ```

    要提供关于“什么算好的工作”的指引，还可以附加带文本值的 `--prompt-context`，例如 `--prompt-context "Use approved answers."`。

  </Step>

  <Step>
    ### 从你的 Runtime 分配线程

    在你已在运行的 CopilotKit runtime 上，通过 `getLearningContainerId` 返回容器的稳定 ID。智能体保持原样即可。该回调对所有智能体框架都一样。

    ```ts title="你的 CopilotKit Runtime"
    import {
      CopilotKitIntelligence,
      CopilotRuntime,
    } from "@copilotkit/runtime/v2";

    const intelligence = new CopilotKitIntelligence({
      apiKey: process.env.CPK_INTELLIGENCE_API_KEY!,
      getLearningContainerId: ({ agentId }) =>
        agentId === "expense-agent" ? "expense-review" : undefined,
    });

    const runtime = new CopilotRuntime({
      agents,
      intelligence,
      identifyUser,
    });
    ```

    当某次运行不应参与时，返回 `null` 或 `undefined`。可以利用回调提供的 user、surface、agent 与 run 输入，把不同的工作流路由到不同的容器。

    <Callout type="warn" title="保持线程的分配稳定">
      在线程的第一次运行之前就完成分配，并在之后的每次运行中返回相同的容器 ID。既有证据不会被回填，线程也不能在容器之间移动。
    </Callout>

  </Step>

  <Step>
    ### 收集示例

    正常使用应用，并完成几个相关的工作流。纠正操作、工具调用与应用交互都能帮助 Learning 理解什么样的结果才算好。

    容器会显示已有多少符合条件的线程就绪，还需要多少。默认情况下，无论是首次运行还是每次成功之后的运行，Automatic Learning 都要求 **15 个符合条件的线程**。如果你的部署采用了不同阈值，请以容器中显示的数量为准。

  </Step>

  <Step>
    ### 设置每日计划

    在容器中选择 **Edit schedule**。在 **This project** 下，保持 **Use organization schedule** 或选择 **Custom project schedule**，设置每日时间与时区并保存。该计划适用于项目中的所有容器。

    组织的每日默认时间为 **02:00 UTC**。**Organization default** 标签页会更改所有未单独覆盖的项目的计划，并要求你确认这个作用范围。设置了自定义计划的项目会保留自定义；重新选择 **Use organization schedule** 会恢复继承，包括之后对默认值的更改。

    当容器符合条件时，**Next scheduled run** 会显示倒计时，以及本地时区与 UTC 的计划时间。这是下一次资格检查：达到线程阈值并不会立即启动运行。进行中的分析、失败阻止或已禁用的 Automatic Learning 都可能阻止运行。保存计划不会启动或取消分析。

  </Step>

  <Step>
    ### 运行 Learning 并审阅

    等待计划运行，或选择 **Start manual run now**，在不等待每日计划或自动线程阈值的情况下分析现有证据。在 **Analysis results** 下跟踪进度。

    审阅产生的 Insight 及其来源线程，然后批准或拒绝每个提议的 Skill。已批准的修订会出现在 **Skills** 下。自动运行使用同样的审阅流程；只有已发布的 Skill 才可供交付。

  </Step>
</Steps>

## 在你的服务端管理 Learning

`CopilotKitIntelligence` 可以在应用服务器上列出容器、启动手动运行并审阅提议的 Skill。
这些实验性的 Learning 管理方法需要具备运行时 Learning 管理 API 的 Intelligence 部署。其 SDK 契约在正式发布前可能变化。
它们使用现有客户端配置中的项目 API 密钥。

请把密钥保存在你的服务端。调用这些方法之前，先对每个应用用户进行授权。
项目密钥可以读取证据并在整个项目中发布 Skill。
它并不代表在你应用中点击控件的那个用户。

### 选择容器并启动一次运行

```ts title="应用服务器"
import { CopilotKitIntelligence } from "@copilotkit/runtime/v2";

const intelligence = new CopilotKitIntelligence({
  apiKey: process.env.CPK_INTELLIGENCE_API_KEY!,
});

const page = await intelligence.experimental.learning.listLearningContainers();
// Use page.nextCursor to request another page when it is not null.
const container = await intelligence.experimental.learning.getLearningContainer({
  containerId: "expense-review",
});

// Call only after the authorized user requests a manual run.
const admittedRun = await intelligence.experimental.learning.startLearningRun({
  containerId: container.id,
});
const runs = await intelligence.experimental.learning.listLearningRuns({
  containerId: container.id,
});
const progress = runs.find((run) => run.id === admittedRun.id);
```

启动成功的响应只确认已受理，并不代表已完成。`listLearningRuns` 返回最近 100 次运行，包括它们的状态与失败码。
手动运行会分析所选容器内符合条件的证据，包括共享该容器的其他应用的证据。
这些方法不会上传工作区文件、移动线程或更改线程的分配。

### 审阅提议的 Skill

```ts title="应用服务器"
const candidates = await intelligence.experimental.learning.listLearningCandidates({
  containerId: "expense-review",
});
const pending = candidates.find((item) => item.status === "pending_review");
if (pending) {
  const candidate = await intelligence.experimental.learning.getLearningCandidate({
    containerId: "expense-review",
    candidateId: pending.id,
  });
  const evidence = await Promise.all(
    candidate.supportingInsights.map((insight) =>
      intelligence.experimental.learning.getLearningInsightEvidence({
        containerId: "expense-review",
        insightId: insight.id,
      }),
    ),
  );
  // Show candidate.bundle.files and evidence to the authorized reviewer.
}
```

`listLearningCandidates` 返回最近 500 个候选，包括已完成审阅的。
证据中包含缺失线程与轨迹的可用性字段。

在审阅者明确选择 **Approve** 或 **Reject** 之后，从你经过授权的服务端 handler 调用 `reviewLearningCandidate`：

```ts title="经过授权的审阅 handler"
const review = await intelligence.experimental.learning.reviewLearningCandidate({
  containerId: "expense-review",
  candidateId, // The candidate the reviewer inspected.
  action: "approve", // Use "reject" for an explicit rejection.
});
```

批准会把提议的更改发布到共享容器；拒绝则不会发布。
已发布的 Skill 内容仍可通过 [Skill 交付](/intelligence/learned-skills)获取。

### 处理错误与取消

所有管理方法都接受可选的 `signal: AbortSignal`，并有 30 秒的请求时限。
取消只会终止请求本身；它不会撤销服务器已经接受的运行或审阅。
SDK 不会自动重试这些请求。

HTTP 错误使用导出的 `PlatformRequestError`，包含 `status`、`retryable` 与可选的后端 `code`。
错误消息不包含后端的原始细节。无效的响应会直接失败，而不是返回部分数据。
如果写操作的响应丢失了，请在提供下一次操作之前先读取当前的运行或候选。

## 使用已发布的 Skill

### 配置 Skill 交付

发布 Skill 之后，把应当使用它的智能体连接起来：

<Steps>
  <Step>
    #### 为容器启用交付

    打开容器的 **Skills** 标签页，确认 **Skill delivery** 显示 **Delivery enabled**。它控制来自该容器的对已发布 Skill 的新请求。
  </Step>

  <Step>
    #### 连接你的智能体

    选择 **Set up skill delivery**，再选择 **Copy setup prompt**，并把它粘贴到你的编码智能体中。这段提示词包含你的容器 ID，并要求编码智能体检查你的框架、保留既有智能体行为，并配置受支持的原生适配器。

    手动配置请参考[框架适配器示例](/intelligence/learned-skills#native-setup)。为你已在运行的智能体挑选适配器，并在智能体服务器环境中使用与上文相同的项目密钥和容器 ID 配置该适配器。

    如果那台服务器还没有密钥，请在它的目录中登录并选择项目：

    ```bash title="终端"
    npx copilotkit@latest login
    npx copilotkit@latest project select
    ```

    ```bash title="智能体服务器环境"
    CPK_INTELLIGENCE_API_KEY=cpk-...
    CPK_INTELLIGENCE_LEARNING_CONTAINER_ID=expense-review
    ```

    密钥请保存在服务端。让 `CPK_INTELLIGENCE_SKILLS_REVISION` 保持未设置，即可跟随最新发布的 Skill。自托管端点与精确的修订锁定请参阅[容器配置](/intelligence/learned-skills#configure-one-container)。
  </Step>

  <Step>
    #### 在新调用中验证交付

    初始化适配器并发起一次新的智能体调用。确认已发布的 Skill 出现在它的目录中，`copilotkit_load_skill` 能加载它的 `SKILL.md`，并且如果该 Skill 带有支持文件，`copilotkit_read_skill_file` 能读取它。仅复制配置提示词或打开开关并不足以验证连接。

    适配器会自动刷新已发布的 Skill，默认的新鲜度窗口为 5 秒。每次调用保留一个快照；新发布的修订会在刷新后对后续调用可用。何时加载并遵循某个 Skill 由模型决定。
  </Step>
</Steps>

<Callout type="info" title="暂停交付与 Learning 相互独立">
  关闭 **Skill delivery** 不会停止 Learning 运行，也不会撤销已发布的修订。适配器一旦检查交付并收到拒绝，就会阻止新的调用；进行中的调用保留其已获取的 Skill。同样，暂停 Learning 运行也不会停止已发布 Skill 的交付。
</Callout>

### 手动下载 Skill

需要离线检查，或框架没有受支持的适配器时，请使用 CLI。如果把某个智能体从下载的 Skill 切换到自动交付，请移除该容器原有的手动加载逻辑，以免重复加载相同的 Skill。

在智能体目录中登录并选择同一个 Intelligence 项目。然后下载该容器已发布的 Skill：

```bash title="终端"
npx copilotkit@latest login
npx copilotkit@latest project select
npx copilotkit@latest skills download expense-review --output ./learned-skills
```

输出中包含每个已发布 Skill 的一个目录和 `SKILL.md`。配置智能体环境加载 `./learned-skills`，之后才能在运行中期待新行为。

## 故障排查

| 问题                                     | 检查要点                                                                                                                                |
| ------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 线程一直没出现在容器中 | 确认回调在线程第一次运行之前返回了一个存在的稳定 ID，且该运行到达了终态。 |
| Runtime 报告容器冲突 | 选择器为已绑定的线程返回了另一个 ID。恢复原映射，或者新建线程。 |
| 某次运行没有新证据 | 在分配之前创建、仍在进行中、或已包含在更早 Learning 运行中的运行，不算新输入。 |
| 自动运行没有启动 | 检查容器的就绪数量、每日计划以及进行中或失败的分析。如果显示 **Automatic learning is off**，说明该部署已禁用计划；修改时间无法启用它。手动运行仍然可用。 |
| 运行失败后 Learning 在等待 | 在 **Analysis results** 下查看失败原因。Automatic Learning 会等待更多符合条件的线程再重试该证据；你也可以启动手动运行。 |
| 运行成功但没有 Skill 候选 | 检查各条 Insight。证据可能有价值，但不足以支撑一个可复用的流程性 Skill。 |
| 已批准的 Skill 对智能体没有生效 | 确认交付已启用、适配器使用了正确的项目和容器，且新的调用能加载该 Skill。检查是否存在精确的修订锁定。手动加载时，请下载最新的 bundle，并确认你的智能体加载了它的目录。 |
| 交付状态不可用 | 选择 **Retry delivery status**。对于自托管部署，在依赖适配器之前，请确认交付端点与迁移已安装。参见[部署要求](/intelligence/learned-skills#deployment-requirements)。 |
