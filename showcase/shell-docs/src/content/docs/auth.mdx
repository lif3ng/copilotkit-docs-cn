你有一个聊天界面或一个驱动智能体的 hook，并且希望每次智能体运行都知道请求*来自谁*。读完本指南，你的前端将转发一个令牌，运行时会将其透传，而你的智能体代码会在每一轮读取得到的用户信息。

## 适用场景

- **多租户应用**：智能体需要读写按用户划分的数据。
- **工具访问控制**：某些工具只应对已授权的用户运行。
- **审计与计费**：每次运行都需要一个可归属的身份。
- **会话感知的 UX**：智能体的行为取决于用户的角色或权限。

如果你运行的是不带 Intelligence 的 TypeScript 运行时，且以上需求一概没有，你的智能体可以匿名运行。Intelligence 运行时则要求受保护的 Web 请求携带可信的应用用户身份。

<Callout type="info" title="运行时身份验证 API">
本页的运行时 hook 使用 TypeScript API。Python、Go、Ruby 和 C#/.NET 则使用各自宿主的请求与身份验证 API；请参考它们的 [Intelligence 配置示例](/intelligence/quickstart#connect-your-runtime)。无论哪种语言，都要从已验证的会话或令牌解析用户，并把 Intelligence API 密钥保存在服务器端。
</Callout>

## 前端

通过 `<CopilotKit>` 上的 `headers` 属性传递你的令牌。CopilotKit 转发的每个请求都会附带该请求头。

```tsx title="frontend/src/app/page.tsx"
import { CopilotKit } from "@copilotkit/react-core/v2";

<CopilotKit
  runtimeUrl="/api/copilotkit"
  headers={{
    Authorization: `Bearer ${userToken}`,
  }}
  useSingleEndpoint={false}
>
  <YourApp />
</CopilotKit>
```

<Callout type="info" title="关于显式设置的 useSingleEndpoint">
  下方 `createCopilotRuntimeHandler` 路由提供的是多路由传输（默认形态）。
  省略该属性时 `<CopilotKitProvider>` 会协商传输方式，但当前发布的每个
  `<CopilotKit>` 内部仍把它固定为 `true`——这会选择单路由传输，并对此路由返回 404。请保留
  `{false}`。参见
  [Provider 与 handler 的配对](/backend/runtime-endpoints#provider-and-handler-pairs)。
</Callout>

## 后端

通过 `onRequest` hook 将身份验证接入 V2 运行时。该 hook 在任何智能体代码之前运行，操作的是原始 `Request`，因此它正适合用来读取 `Authorization` 请求头、运行你的校验器，然后要么放行请求，要么以 401 短路返回：

```ts title="app/api/copilotkit/[[...slug]]/route.ts"
import type { NextRequest } from "next/server";
import {
  CopilotRuntime,
  createCopilotRuntimeHandler,
} from "@copilotkit/runtime/v2";

const runtime = new CopilotRuntime({ agents: { default: myAgent } });

const handler = createCopilotRuntimeHandler({
  runtime,
  basePath: "/api/copilotkit",
  hooks: {
    onRequest: ({ request }) => {
      const authHeader = request.headers.get("authorization");
      if (!authHeader?.startsWith("Bearer ")) {
        throw new Response(
          JSON.stringify({ error: "unauthorized" }),
          { status: 401, headers: { "content-type": "application/json" } },
        );
      }
      const token = authHeader.slice("Bearer ".length);
      const user = verifyJwt(token); // your validation
      // attach user to request-scoped context here
    },
  },
});

export const POST = (req: NextRequest) => handler(req);
export const GET = (req: NextRequest) => handler(req);
export const PATCH = (req: NextRequest) => handler(req);
export const DELETE = (req: NextRequest) => handler(req);
```

> V1 的 Next.js 适配器（`copilotRuntimeNextJSAppRouterEndpoint`）不会转发 `hooks` 选项。当你需要 `onRequest` 门禁时，请直接使用 `@copilotkit/runtime/v2` 中的 `createCopilotRuntimeHandler`。

## 前端

通过 `headers` 属性传递你的令牌。CopilotKit 会把它附加到每个运行时请求上，运行时再将 `Authorization` 请求头转发给你的智能体——无论它是 LangGraph 部署还是自托管的 AG-UI 端点。

```tsx title="frontend/src/app/page.tsx"
import { CopilotKit } from "@copilotkit/react-core/v2";

<CopilotKit
  runtimeUrl="/api/copilotkit"
  headers={{
    Authorization: `Bearer ${userToken}`,
  }}
>
  <YourApp />
</CopilotKit>
```

<Callout type="warning" title="`properties` 不是认证通道">
本指南的旧版本曾通过 `properties={{ authorization: userToken }}` 传递令牌。运行时把 `properties` 作为 AG-UI `forwardedProps` 交付给智能体——它是运行载荷数据，不是请求头——因此没有任何环节会把它转换成 Bearer 凭证。认证请使用 `headers`。服务器在智能体自身配置的请求头在冲突时仍然优先，因此服务间令牌不会被浏览器端覆盖。
</Callout>

## 后端

LangGraph 支持两种部署模式。上面的前端代码在两种模式下都相同，但后端接线的差别在于解析出的用户身份落在哪里。请选择与你的智能体运行位置匹配的标签页。

<Tabs items={['LangGraph Platform', 'Self-hosted (FastAPI)']}>
<Tab value="LangGraph Platform">

在 LangGraph Platform（以及 `langgraph dev`）上，身份验证是一项托管服务。你声明一个 `@auth.authenticate` handler，服务器会在图启动之前对每个请求运行它。转发的 `Authorization` 请求头作为 handler 的 `authorization` 参数传入，handler 的返回值对运行中的每个节点都可用。

```python title="backend/auth.py"
from langgraph_sdk import Auth

auth = Auth()

@auth.authenticate
async def authenticate(authorization: str | None):
    if not authorization or not authorization.startswith("Bearer "):
        raise Auth.exceptions.HTTPException(status_code=401, detail="Unauthorized")

    token = authorization.replace("Bearer ", "")
    user_info = validate_your_token(token)  # your validation logic

    return {
        "identity": user_info["user_id"],
        "role": user_info.get("role"),
        "permissions": user_info.get("permissions", []),
    }
```

handler 的返回值会出现在每个节点的 `config["configurable"]["langgraph_auth_user"]` 中。有了它，限定工具访问范围或过滤数据都很直接：

```python title="backend/agent.py"
from langchain_core.runnables import RunnableConfig

async def my_agent_node(state: AgentState, config: RunnableConfig):
    user_info = config["configurable"]["langgraph_auth_user"]
    user_id = user_info["identity"]
    user_role = user_info.get("role")
    # agent logic with user context
    return state
```

handler 的完整细节见 [LangGraph Platform 身份验证文档](https://docs.langchain.com/langsmith/auth#authentication)。

</Tab>
<Tab value="Self-hosted (FastAPI)">

当你把智能体自托管在 FastAPI 之后，就没有托管认证 handler 可挂靠了——校验是你的职责，而它天然的位置就是服务 AG-UI 流的端点。`add_langgraph_fastapi_endpoint` 会为你挂载该端点，但它只接受一个预构建的智能体，也不提供按请求的 hook，所以要用等价的自建路由替换它：由 FastAPI dependency 校验运行时转发来的 `Authorization` 请求头，并把解析出的用户烘焙进按请求创建的智能体 `config`。

```python title="backend/main.py"
from typing import Optional

from ag_ui.core.types import RunAgentInput
from ag_ui.encoder import EventEncoder
from copilotkit import LangGraphAGUIAgent
from fastapi import Depends, FastAPI, Header, HTTPException, Request
from fastapi.responses import StreamingResponse

from src.agent import graph

app = FastAPI()

def current_user(authorization: Optional[str] = Header(default=None)) -> dict:
    if not authorization or not authorization.startswith("Bearer "):
        raise HTTPException(status_code=401, detail="Missing bearer token")
    return validate_your_token(authorization.removeprefix("Bearer ").strip())  # your validation

@app.post("/")
async def run_agent(
    input_data: RunAgentInput,
    request: Request,
    user: dict = Depends(current_user),
):
    encoder = EventEncoder(accept=request.headers.get("accept"))

    # One agent per request: the verified identity rides on this run only, and
    # each request gets its own isolated streaming state.
    agent = LangGraphAGUIAgent(
        name="sample_agent",
        graph=graph,
        config={"configurable": {"auth_user": user}},
    )

    async def event_generator():
        async for event in agent.run(input_data):
            yield encoder.encode(event)

    return StreamingResponse(event_generator(), media_type=encoder.get_content_type())
```

未认证的请求根本到不了图——它们会被 dependency 以 401 拒绝。已认证的请求则带着已验证的用户进入 config，节点直接读取身份即可，无需重新校验原始令牌：

```python title="backend/src/agent.py"
from langchain_core.runnables import RunnableConfig

async def my_agent_node(state: AgentState, config: RunnableConfig):
    user = config["configurable"]["auth_user"]
    user_id = user["user_id"]
    user_role = user.get("role")
    # agent logic with user context
    return state
```

<Callout type="info" title="如果你只需要 401 门禁">
当节点不需要身份——你只是想拒绝未认证流量时——保留 `add_langgraph_fastapi_endpoint` 并把 dependency 挂到应用上：`FastAPI(dependencies=[Depends(current_user)])`。门禁照样生效，但不会向运行 config 写入任何东西，因此 `config["configurable"]` 中不会包含用户上下文。
</Callout>

<Callout type="warning" title="`CopilotKitRemoteEndpoint` 在此已不可用">
为 CopilotKit v1 编写的指南会把图包装在 `CopilotKitRemoteEndpoint(agents=lambda context: [...])` 中。这条路已退役：`copilotkit` 不再导出 `LangGraphAgent`（会抛 `ImportError`），而现在的 `LangGraphAGUIAgent` 暴露的是 `run()`，不再是 `CopilotKitRemoteEndpoint` 调用的 `execute()`——于是报出 `AgentExecutionException: 'LangGraphAGUIAgent' object has no attribute 'execute'`。请改用上面的端点。
</Callout>

## 后端

后端有两项职责：在智能体分发之前校验令牌，并把解析出的用户身份作为一个**依赖**（dependency）穿入运行，供工具稍后读取。依赖只留在服务器端——与会话变量不同，它们永远不会作为状态流式传输到客户端。

先在 AG2 的 `/chat` 端点上校验令牌。`Authorization` 请求头会作为普通的 FastAPI `Header(...)` 参数传入：

```python title="backend/server.py"
from fastapi import FastAPI, Header, HTTPException
from fastapi.responses import StreamingResponse

from ag2 import Agent
from ag2.ag_ui import AGUIStream, RunAgentInput
from ag2.config import OpenAIResponsesConfig

agent = Agent(
    name="assistant",
    prompt="You are a helpful assistant.",
    config=OpenAIResponsesConfig(model="gpt-5.5"),
)

stream = AGUIStream(agent)
app = FastAPI()

def validate_your_token(token: str) -> dict:
    if token != "valid-token":
        raise HTTPException(status_code=401, detail="Unauthorized")
    return {
        "user_id": "user_123",
        "role": "member",
        # The scope `get_account_data` below checks against.
        "allowed_accounts": ["acct_456"],
    }

@app.post("/chat")
async def run_agent(
    message: RunAgentInput,
    accept: str | None = Header(None),
    authorization: str | None = Header(None),
) -> StreamingResponse:
    if not authorization:
        raise HTTPException(status_code=401, detail="Missing authorization header")

    token = authorization.replace("Bearer ", "")
    user_info = validate_your_token(token)

    return StreamingResponse(
        stream.dispatch(message, dependencies={"auth_user": user_info}, accept=accept),
        media_type=accept or "text/event-stream",
    )
```

令牌校验通过后，AG2 的工具可以用 `Inject` 注解来请求用户身份。这样就能让每次工具调用都知道请求者是谁，而不必手动把用户对象穿透每一个辅助函数——也不会把它暴露给 LLM 或客户端：

```python title="backend/tools.py"
from typing import Annotated

from ag2 import Inject, tool

@tool
def get_account_data(
    account_id: str,
    auth_user: Annotated[dict, Inject("auth_user")],
) -> dict:
    """Return account data for the authenticated user."""
    if not auth_user:
        return {"error": "unauthorized"}
    if account_id not in auth_user.get("allowed_accounts", []):
        return {"error": "forbidden"}
    return {"account_id": account_id, "owner": auth_user["user_id"]}
```

最后，把工具注册到智能体上，让 LLM 可以调用它：

```python title="backend/server.py"
from backend.tools import get_account_data # [!code highlight]

agent = Agent(
    name="assistant",
    prompt="You are a helpful assistant.",
    config=OpenAIResponsesConfig(model="gpt-5.5"),
    tools=[get_account_data], # [!code highlight]
)
```

using Microsoft.Agents.AI.Hosting.AGUI.AspNetCore;
using Microsoft.AspNetCore.Authentication.JwtBearer;
using OpenAI;
using OpenAI.Chat;

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        options.Authority = builder.Configuration["JwtAuthority"];
        options.Audience = builder.Configuration["JwtAudience"];
        options.TokenValidationParameters = new Microsoft.IdentityModel.Tokens.TokenValidationParameters
        {
            ValidateIssuer = true,
            ValidateAudience = true,
            ValidateLifetime = true,
            ValidateIssuerSigningKey = true,
        };
    });

builder.Services.AddAuthorization();
builder.Services.AddAGUIServer();

var app = builder.Build();

app.UseAuthentication();
app.UseAuthorization();

string openAiApiKey = builder.Configuration["OPENAI_API_KEY"]

var agent = openAI.GetChatClient("gpt-5.4-mini")
    .AsAIAgent(name: "AGUIAssistant", instructions: "You are a helpful assistant.");

## 工具访问控制

接入认证最常见的原因，就是让单个工具有权拒绝运行。在工具的 handler 里读取解析出的用户，角色不匹配就中止：

```python
def delete_record(record_id: str, *, user: User):
    if "admin" not in user.permissions:
        raise PermissionError("admin role required")
    # do the delete
```

它可以与[人机协同](/human-in-the-loop)组合：先做认证门禁，再弹出确认卡片，最后执行。

## 线程授权

验证了调用者*是谁*，还不能阻止他访问*别人的会话*。这方面你需要自己构建多少，取决于你运行的是哪个运行时。

| 运行时 | 由谁把线程限定到某个用户 |
| --- | --- |
| `CopilotRuntime` 加 `intelligence` | 主要由运行时通过 [`identifyUser`](#copilotkit-intelligence-管辖大多数线程路由) 完成——但有三条路由你仍需自己设防。 |
| 其他一切——SSE 运行时、自定义存储、本地内存运行器 | 由你完成。见[自行划定线程范围](#自行划定线程范围)。 |

### CopilotKit Intelligence 管辖大多数线程路由

Intelligence 运行时要求提供一个 `identifyUser` 回调——没有它（或没有至少一个 Channel），构造时就会抛错。回调在服务器上运行，每个请求一次，它返回的 id 就是运行时交给平台的范围。（下文的 `intelligence` 是一个 `CopilotKitIntelligence` 实例；[将你的运行时接入 Intelligence](/intelligence/quickstart) 介绍了如何构建它。）

```ts title="app/api/copilotkit/[[...slug]]/route.ts"
const runtime = new CopilotRuntime({
  agents: { default: agent },
  intelligence,
  identifyUser: async (request) => {
    const session = await verifyAppSession(request); // Your server-side auth.
    if (!session?.user) throw new Error("Unauthorized"); // Backstop; see below.

    return { id: session.user.id, name: session.user.name };
  },
});
```

<Callout type="warn" title="`identifyUser` 不是认证门禁">
  大多数路由通过 `identifyUser` 解析调用者，但**并非所有路由都如此**——不这么做的路由根本不会调用你的回调。拒绝未认证请求是 `onRequest` 的职责：它在路由之前运行，覆盖每一条路由，无一例外。把 `identifyUser` 视作为已认证的调用者*命名*的环节，绝不要把它视作决定调用者能否进入的环节。
</Callout>

在确实解析调用者的路由上，接下来关键是这个 id 是否真的*作为范围传到了平台*：

| 路由 | 是否限定到解析出的用户？ |
| --- | --- |
| `agent/run`、`agent/connect` | 是 |
| `threads/list` | 是——并按 `agentId` 过滤，因此 `useThreads` 返回的是调用者自己的线程，而非整个项目的 |
| `threads/messages` | 是 |
| `threads/update`（通过 `PATCH` 重命名、通过 `DELETE` 删除）、`threads/archive` | 是 |
| 线程订阅令牌 | 是 |
| `threads/events`、`threads/state` | **否**——解析调用者后便将其忽略 |
| `agent/stop` | 是——在中止运行之前会以调用者身份获取该线程 |

<Callout type="warn" title="两条路由不按用户限定">
  **`threads/events` 与 `threads/state`** 支撑着[检查器](/inspector)。两者都会解析调用者然后把结果丢弃，仅凭 id 读取线程——运行时调用的是平台以项目身份认证的 `_inspect` 端点，它们不接受用户参数。任何调用者只要拿到 `threadId`，就能读取项目内任意线程的完整事件日志与当前智能体状态。

  这两条都要自己设防。下方的 `onBeforeHandler` 模式同样适用于 CopilotKit Intelligence 路径，只需收窄到这几条路由：

  ```ts
  onBeforeHandler: async ({ request, route }) => {
    // Switch rather than an array `includes`, so `route` narrows and
    // `route.threadId` type-checks — both variants carry one.
    switch (route.method) {
      case "threads/events":
      case "threads/state":
        break;
      default:
        return;
    }

    // None of these is scoped platform-side; check your own ownership record.
    const user = await verifyRequest(request);
    if (!(await userOwnsThread(user.id, route.threadId))) {
      throw new Response("Not found", { status: 404 });
    }
  },
  ```

  如果你没有自己的归属记录，请直接拒绝这些路由，而不是放任其开放。
</Callout>

对表中所有“是”的行，你无需构建任何归属表。你要做好的是 `identifyUser` 本身：

- **从服务器验证过的凭证派生 id**。回调收到的是原始 `Request`；它的返回值从此即被视为可信。直接从头或请求体里读用户 id，等于把自我命名的权力交给每一个调用者。
- **返回稳定的 id**。它是线程挂靠的键。一旦变更——比如把邮箱换成 subject 声明——该用户的既有线程就无法解析了。
- **在 `onRequest` 中发出 `401`**。除了状态码不对——`identifyUser` 抛错会表现为 `500`，id 格式非法表现为 `400`——`transcribe` 和 `agent/suggest` 之类的路由从不调用它，因此只放在这里的检查并非每个请求都会经过。请在 `onRequest` 中认证——它在每条路由上运行且能直接抛出 `Response`——并把 `identifyUser` 内的抛错留作兜底。

<Callout type="warn">
  静态的 `identifyUser` 值只适用于单用户演示。在多用户应用中，每个请求都必须解析出已认证的用户，否则这些用户会共享同一个线程范围。
</Callout>

完整的运行时契约见[将 AG-UI 流限定到登录用户](/threads-lifecycle#scope-rich-threads-to-the-signed-in-user)。

### 自行划定线程范围

没有 CopilotKit Intelligence 时，`threadId` 与用户之间不存在服务器端的绑定。`threadId` 只是随请求旅行的不透明 id：如果用户 A 得到了用户 B 的 id，每条线程路由都会接受它。本节余下内容是自定义存储、纯 SSE 运行时或本地内存运行器的模式——如果你*确实*在平台上，它也正是你收窄到 `threads/events` 和 `threads/state` 时要用的东西。

默认的 `InMemoryAgentRunner` 是最直白的情况。它把线程保存在一个以 `threadId` 为键的进程级全局 map 中，没有所有者字段，因此每条[线程路由](/backend/runtime-endpoints#thread-routes)都会响应交给它的任何 id：`GET /threads` 列出进程内的每个线程，`GET /threads/:threadId/messages` 把该线程的历史返回给任何询问者。任何继承它的实现（如 `AgentCoreRunner`）都会继承同一存储。`SqliteAgentRunner` 则完全不提供这些路由：其读取路由一律返回 `422`。因此更换 runner 解决的是持久化问题，而不是线程授权问题。

#### 自己维护映射

无论用什么存储线程，都要记录每个线程属于谁。最低限度是一张运行时可以查询的表：

```sql
create table thread_owners (
  thread_id text primary key,
  user_id   text not null
);
create index on thread_owners (user_id);
```

在会话首次创建时写入一行——它挂接在聊天生命周期的哪个位置，见[用自己的 API 铸造线程](/threads-lifecycle#creating-a-thread-with-your-own-api-on-the-first-message)。

#### 在 `onBeforeHandler` 中实施

`onRequest` 在路由之前运行，因此看不到正在访问的是哪个线程。`onBeforeHandler` 在其后运行，收到的 `route` 会指明操作，且对线程级路由还会带上 `threadId`：

```ts
const handler = createCopilotRuntimeHandler({
  runtime,
  basePath: "/api/copilotkit",
  hooks: {
    onRequest: async ({ request }) => {
      // Authenticate first: reject anonymous callers outright.
      const user = await verifyRequest(request);
      if (!user) throw new Response("Unauthorized", { status: 401 });
    },

    onBeforeHandler: async ({ request, route }) => {
      const user = await verifyRequest(request);

      // Routes that name a thread directly.
      if ("threadId" in route) {
        if (!(await userOwnsThread(user.id, route.threadId))) {
          throw new Response("Forbidden", { status: 403 });
        }
        return;
      }

      // agent/run and agent/connect carry the thread in the body instead.
      if (route.method === "agent/run" || route.method === "agent/connect") {
        // Clone: the handler still needs to read the original body.
        const { threadId } = await request.clone().json();
        if (threadId && !(await userOwnsThread(user.id, threadId))) {
          throw new Response("Forbidden", { status: 403 });
        }
      }
    },
  },
});
```

在 `route` 上携带 `threadId` 的路由是 `agent/stop`、`threads/update`、`threads/archive`、`threads/messages`、`threads/events` 和 `threads/state`。

<Callout type="warn" title="线程 id 不是秘密">
  把 `threadId` 当作公开标识符，就像 URL 里的数据库主键。它会经过浏览器、出现在日志里，如果你铸造的是顺序 id，它还极易被枚举。授权必须是显式的归属检查——绝不能是“他们知道这个 id，所以必定拥有它”。铸造 UUID 能让猜中变得不现实，但它本身并不是一项控制措施。
</Callout>

#### 过滤线程列表

`threads/list` 没有可供检查的 `threadId`，因此 `onBeforeHandler` 无从授权。离开平台后，这条路由返回配置的存储中所有内容——本地内存运行器只按 `agentId` 过滤，自定义存储则原样返回你写入的东西。请改为从你自己的归属表构建列表，并用选定的 id 驱动聊天。

过滤要在服务器端做。在 UI 里隐藏行，底下的路由依然敞开。

`threads/clear` 是另一条 `route` 上没有 `threadId` 的路由。在内存运行器上它会清空进程内的所有线程并返回 `204`，因此 `onBeforeHandler` 能做的唯一决定就是是否放行这次调用。部署上若不止一个用户，除非调用者是运维人员，否则应拒绝。

<Callout type="info">
  没有平台线程存储时，上面那张归属表*就是*你的线程列表。
</Callout>

## 安全清单

- **始终在后端校验**令牌。永远不要相信前端的声明。
- **每一次读写都限定**到解析出的用户。认证上下文只有在你真正用它过滤数据时才有意义。
- **在 `onRequest` 中认证**。它是唯一在每条路由上都运行的 hook。`identifyUser` 为调用者命名；它不设门禁，而且有些路由从不调用它。
- **把线程绑定到用户**。在 CopilotKit Intelligence 上，这意味着一个正确的 `identifyUser`，加上你对 `threads/events` 和 `threads/state` 的自设防线；在其之外，则是对每条线程路由做归属检查，而不是只在登录时检查。见[线程授权](#线程授权)。
- **不要记录原始令牌**。改为记录解析出的用户 id（或 `anonymous`）。
- **生产环境使用 HTTPS。**Bearer 令牌是敏感信息。
- **刷新策略**。前端负责在过期令牌到达智能体之前轮换它。CopilotKit 不会替你刷新。
