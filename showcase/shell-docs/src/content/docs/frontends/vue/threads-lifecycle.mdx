## 这是什么？

每段 CopilotKit 会话都限定在一个**线程**内，由 `threadId` 标识。本页讲解完整的客户端生命周期：id 如何生成、既有历史如何恢复、如何切换或开启线程，以及 CopilotKit 线程的边界在哪里、你的智能体框架自身的持久化又从哪里开始。

<Callout type="info">
  本页描述的是从 `@copilotkit/vue/v2` 导入的当前 Vue v2 组合式函数与组件。
</Callout>

## 生命周期一览

1. **生成。** 当聊天挂载时未提供显式 `threadId`，客户端会生成一个 UUID v4。
2. **运行。** 消息与工具调用在该 id 下流式进行。如果配置了服务端存储，它们会在发生时即被持久化；没有持久化层的运行时则不在服务端保留任何内容。
3. **水合。** 当聊天以已知 id 挂载时，客户端会建立连接并把已持久化的历史回放到 UI 中。
4. **切换/开启。** 你可以选择一个已知线程并恢复它，或开启一个全新线程并清空视图。

## threadId 如何生成

当你不提供时，CopilotKit 会在组件设置期间在客户端生成一个 `threadId`。该值的解析遵循以下优先级（从高到低）：

1. `<CopilotChat>` 或 `<CopilotChatConfigurationProvider>` 上的显式 `threadId` 属性；它是权威的，并驱动回放。
2. 来自 `setActiveThreadId(...)`、抽屉中被选中的行或 `startNewThread()` 的活动线程覆盖值。
3. 从父配置提供方继承的 `threadId`。
4. 非权威的 `threadId` 种子值。
5. 否则，新生成一个 UUID。

```vue title="显式 threadId（推荐在你自行管理持久化时使用）"
<CopilotChat agent-id="my-agent" :thread-id="myThreadId" />
```

<Callout type="warn">
  **自动生成的 id 能在响应式重渲染中存活，但组件重新挂载时会重新生成。**如果变化的 `:key`、路由切换或父组件卸载/重挂载重建了聊天配置，后备 id 就会改变，一段新会话随之开始。当连续性必须跨越重挂载时，请自行生成并持久化该 id。
</Callout>

## 历史如何恢复（水合）

CopilotKit Vue v2 **不**使用 `initialMessages` 属性来播种会话。历史恢复有下面两种方式。

**1. 服务端回放。** 当聊天以显式 `threadId` 挂载时，客户端会赋值 `agent.threadId` 并连接 agent。已持久化的事件历史会回放到 UI 中，无需手动接线消息：

```vue
<CopilotChat agent-id="my-agent" :thread-id="existingThreadId" />
```

<Callout type="warn">
  回放需要一个**可供回放的服务端存储**，例如 CopilotKit Intelligence 或具备持久化能力的 `AgentRunner`。没有持久化层的自托管运行时没有任何可回放的内容，因此连接会返回空流。如果历史没有恢复，先检查服务端存储，再看 Vue 代码。
</Callout>

对于全新的非显式线程（例如由 `startNewThread()` 创建的线程），没有可回放的内容，因此视图会被清空。

**2. 手动水合。** 对于非平台或自定义场景，从你自己的存储读取消息并直接设置到 agent 上：

<RestoreHistory components={props.components} />

从 `agent.value.messages` 读取当前会话；用 `setMessages(...)` 和 `addMessage(...)` 进行替换或追加。

## 将 Rich Threads 限定到登录用户

终端用户的身份验证由你的应用负责。对于启用了 Intelligence 的运行时，用服务端校验过的会话或令牌实现 `identifyUser(request)`，并返回稳定的用户 id 与名称：

```ts title="server.ts"
import { CopilotKitIntelligence, CopilotRuntime } from "@copilotkit/runtime/v2";

const runtime = new CopilotRuntime({
  agents: { default: agent },
  intelligence: new CopilotKitIntelligence({
    apiKey: process.env.CPK_INTELLIGENCE_API_KEY!,
  }),
  identifyUser: async (request) => {
    const session = await verifyAppSession(request);
    if (!session?.user) throw new Error("Unauthorized");
    return { id: session.user.id, name: session.user.name };
  },
});
```

CopilotKit Intelligence 在划定列表、订阅、历史、重命名、归档、取消归档和删除操作的范围时，会把该应用用户身份与项目结合起来。项目运行时密钥是单独的服务端凭据；不要把创建它的开发者当作应用用户。

<Callout type="warn">
  静态的 `identifyUser` 值只适合单用户演示。在多用户应用中，每个请求都必须解析出经过身份验证的应用用户，否则这些用户将共享同一个线程范围。
</Callout>

身份验证上下文的转发与校验请参阅[身份验证](/auth)，完整的 Intelligence 配置请参阅[将你的运行时连接到 Intelligence](/intelligence/connect-your-runtime)。

## 切换线程与开启新线程

设置活动线程以恢复其历史，或开启一段全新会话：

```vue title="src/components/ThreadControls.vue"
<script setup lang="ts">
import { useCopilotChatConfiguration } from "@copilotkit/vue/v2";

const { existingId } = defineProps<{ existingId: string }>();
const config = useCopilotChatConfiguration();
</script>

<template>
  <button
    @click="config?.setActiveThreadId(existingId, { explicit: true })"
  >
    Open conversation
  </button>
  <button @click="config?.startNewThread()">New chat</button>
</template>
```

- `setActiveThreadId(threadId, { explicit })`：默认的 `explicit: true` 会将其视为已知线程并回放历史；`explicit: false` 则显示欢迎界面。
- `startNewThread()`：重置为全新生成的非显式 id。自定义侧边栏必须调用这个配置方法来生成并切换活动线程。要复现内置抽屉的行为，还需调用 `useThreads().startNewThread()` 以清除陈旧的线程存储错误状态。

<Callout type="warn">
  当 `threadId` 由属性控制时，这两个方法都会空操作并发出警告。如果你以命令式方式驱动线程，就不要同时传入权威的 `threadId` 属性。请选定唯一的事实来源。
</Callout>

## 在首条消息时用自己的 API 创建线程

一个常见需求是拦截首条消息，通过自己的后端创建一条记录，并在会话开始之前使用其 id。

**在内置的 `<CopilotChat>` 上，`submit-message` 事件只是观察性的。**组件发出该事件后仍会继续自己的添加消息/运行流程；它不是可以延迟该次运行的异步拦截缝。

**推荐做法：提前生成并驱动 id。**在渲染聊天之前，或在“新建聊天”动作中创建线程，然后通过配置传入：

```ts
async function startConversation() {
  const { id } = await myApi.createThread();
  config.value?.setActiveThreadId(id, { explicit: true });
}
```

**提交时方案：使用无头输入。**自行组合输入框与处理器，在添加消息之前把 id 设置到 agent 上，然后运行 agent：

```ts
async function submit(text: string) {
  const current = agent.value;
  if (!current) return;

  const { id } = await myApi.createThread();
  current.threadId = id;
  current.addMessage({ id: crypto.randomUUID(), role: "user", content: text });
  await copilotkit.value.runAgent({ agent: current });
}
```

<Callout type="warn">
  对于在同一处理器中触发的运行，请把 id 设置到 **agent** 上。`setActiveThreadId(id)` 会以响应式方式更新配置、稍后才到达 agent，因此立即执行的运行仍可能使用先前的线程。
</Callout>

## CopilotKit 线程与你框架的 checkpointer 对比

这是两个不同的层，仅靠共享的 `threadId` 关联：

| 层 | 存储内容 | 管理方 |
| --- | --- | --- |
| **CopilotKit 线程** | 会话列表与 AG-UI 事件历史，支持实时同步 | CopilotKit Intelligence，通过 `useThreads` |
| **框架原生持久化** | 框架内部的状态与检查点 | 你的 agent，例如 LangGraph checkpointer |

LangGraph checkpointer 创建的是 LangGraph 自己的检查点表，它不会创建 CopilotKit 线程表。反过来，CopilotKit 的重命名/归档/删除操作也不会触及 LangGraph、ADK 或其他原生存储，除非你的后端显式地搭建了桥接。

桥梁就是 `threadId`：CopilotKit 把显式 id 作为 AG-UI 的 `threadId` 转发给后端，框架既可直接使用它，也可映射到自己的标识符。

### 未来的运行可在两侧都保持持久

历史导入之后，未来经 CopilotKit 运行的会话可以写入 CopilotKit Intelligence，同时 agent 继续使用其持久的原生 checkpointer 或会话服务。用户获得 AG-UI 回放、生成式 UI、多模态历史与实时连续性，框架则保留自己的存储与分析。

这是未来由 CopilotKit 介入的运行期间的协调式持久化，而非通用的数据库复制。除非你搭建桥接，CopilotKit 的生命周期操作仍只作用于 CopilotKit 线程。

## MCP Apps 活动与历史

MCP Apps 通过活动消息渲染，渲染是客户端的事务。可见的 iframe 在加载时从回放的会话中重新推导而来；它不是单独存储的制品。

如果服务端存储回放了该线程的工具调用与活动历史，Vue 渲染器会在水合期间再次运行。没有需要单独配置的 MCP Apps 存储。
