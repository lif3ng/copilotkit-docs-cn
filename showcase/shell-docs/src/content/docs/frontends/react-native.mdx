`@copilotkit/react-native` 为 React Native 提供 CopilotKit 的 provider 与 hooks，以及可选的预构建聊天组件。本指南使用这些 hooks 构建完全自定义的聊天 UI，后端由你服务器上的 [Copilot Runtime](/backend/copilot-runtime) 端点支撑。

该包有三个导入入口——`/headless`（provider + hooks，无原生对等依赖，**1.64.0+**）、根入口（root barrel）以及 `/components`（渲染好的聊天 UI）。各入口会引入什么，参见[导入入口](#import-surfaces)；本指南全程使用 `/headless`。

## 从编码智能体开始

使用下面的提示词在 React Native 应用中配置 CopilotKit、设置 Metro 与 polyfill，并针对你的 Runtime 验证聊天功能。也可以按下面的手动步骤操作。

## 前置条件

- 一个 OpenAI API 密钥（或[模型选择](/model-selection)支持的其他模型提供方）
- React Native 0.70+（裸 CLI 或 Expo）
- Node.js 20+
- `devDependencies` 中需要有 `@react-native-community/cli` **（如果你使用 React Native 0.87 或更高版本）**——该版本起不再自带它。新 `init` 的应用已包含它；升级过的应用则可能没有，缺少它时 `react-native bundle` 与 `react-native start` 会停止运行，并报出指明缺失包的错误信息。

            ```bash
            npm ls @copilotkit/react-native
            ```

            在 1.63.x 或更早版本上，优先升级到 1.64.0+。如果无法升级——例如要配合已锁定的 `@copilotkit/runtime`——同样的 `CopilotKitProvider`、`useAgent` 与 `useCopilotKit` 也从包根导出，只需从导入路径中去掉 `/headless` 即可完成全部代码改动。但这并非毫无代价：在这些版本上，根入口会静态导入 `expo-document-picker` 与 `expo-file-system`，因此必须同时安装（或 stub）这两者，否则发布 bundle 会报错 `Unable to resolve module expo-document-picker`。参见[导入入口](#import-surfaces)。
        </Callout>

        <Callout type="info" title="TypeScript：使用 bundler 模块解析">
            `/headless`、`/components` 与 `/polyfills` 子路径是通过包的 `exports` 映射发布的，而 TypeScript 旧版 `"moduleResolution": "node"`（`node10`）会忽略它。在该设置下，即使 Metro 能正常打包应用，类型检查也会报错 `Cannot find module '@copilotkit/react-native/headless'`。请在 `tsconfig.json` 中设置 `"moduleResolution": "bundler"`；如果 `module` 为 `commonjs` 或未设置，还需设置 `"module": "esnext"`。`@react-native/typescript-config` 与 Expo 的基础配置已经使用 `bundler`。
        </Callout>

    <Step>
        ### 添加 polyfill

        React Native 的 JS 运行时（Hermes）缺少 CopilotKit 依赖的若干 Web API。该包会在首次导入时自行安装这些 polyfill，但有两件事必须**在入口文件的最顶部、任何 CopilotKit 导入之前**完成：先引入安全的随机数来源，再引入 polyfill 桶文件（barrel）。

        先安装安全的 RNG：

        ```bash
        npm install react-native-get-random-values
        ```

        ```js title="index.js"
        import "react-native-get-random-values"; // [!code highlight:2] secure RNG — must be first
        import "@copilotkit/react-native/polyfills";

        import { AppRegistry } from "react-native";
        import App from "./App";
        import { name as appName } from "./app.json";

        AppRegistry.registerComponent(appName, () => App);
        ```

        <Callout type="warn" title="导入顺序对 crypto 至关重要">
          CopilotKit 的 `crypto` polyfill 与 `react-native-get-random-values` 都只在 `crypto.getRandomValues` 仍未定义时才安装——先写入者生效。如果任何 CopilotKit 模块先被求值，CopilotKit 的**非加密级** `Math.random` 回退就会被永久锁定，`react-native-get-random-values` 会变成静默的空操作。务必把它放在第一行。参见 [Polyfill](#polyfill)。
        </Callout>

        <Callout type="info" title="细粒度 polyfill">
          如果你已经为其中某些 API（如 `ReadableStream`）自行提供了 polyfill，可以只导入需要的部分，而不使用桶文件：

          ```js
          import "@copilotkit/react-native/polyfills/streams";
          import "@copilotkit/react-native/polyfills/encoding";
          import "@copilotkit/react-native/polyfills/crypto";
          import "@copilotkit/react-native/polyfills/dom";
          import "@copilotkit/react-native/polyfills/location";
          ```
        </Callout>
    </Step>
    <Step>
        ### 创建 Copilot Runtime

        添加一个小的 Node 服务器，在 `/api/copilotkit` 上承载 Copilot Runtime，并注册一个 `default` 内置智能体：

        ```ts title="server.ts"
        import { createServer } from "node:http";
        import { BuiltInAgent, CopilotRuntime } from "@copilotkit/runtime/v2";
        import { createCopilotNodeListener } from "@copilotkit/runtime/v2/node";

        const runtime = new CopilotRuntime({
          agents: {
            default: new BuiltInAgent({
              model: "openai:gpt-5-mini",
              prompt: "You are a helpful assistant for a React Native app.",
            }),
          },
        });

        const port = Number(process.env.PORT ?? 8200);

        createServer(
          createCopilotNodeListener({
            runtime,
            basePath: "/api/copilotkit",
            cors: true,
          }),
        ).listen(port, () => {
          console.log(
            `Copilot Runtime listening at http://localhost:${port}/api/copilotkit`,
          );
        });
        ```
    </Step>
    <Step>
        ### 用 CopilotKitProvider 包裹你的应用

        将 provider 指向运行时端点。Android 模拟器通过 `10.0.2.2` 访问宿主机；iOS 模拟器可以使用 `localhost`。

        ```tsx title="App.tsx"
        import { CopilotKitProvider } from "@copilotkit/react-native/headless"; // [!code highlight]
        import { Platform } from "react-native";
        import { ChatScreen } from "./src/ChatScreen";

        const runtimeUrl =
          Platform.OS === "android"
            ? "http://10.0.2.2:8200/api/copilotkit"
            : "http://localhost:8200/api/copilotkit";

        export default function App() {
          return (
            <CopilotKitProvider runtimeUrl={runtimeUrl}> {/* [!code highlight] */}
              <ChatScreen />
            </CopilotKitProvider>
          );
        }
        ```

        <Callout type="info" title="在物理设备上测试">
          将 `localhost` 或 `10.0.2.2` 替换为你开发机的局域网 IP 地址，例如 `http://192.168.1.23:8200/api/copilotkit`。
        </Callout>
    </Step>
    <Step>
        ### 构建你的聊天 UI

        这些平台无关的 hooks 在这里的用法与 Web 上一致。下面是使用 `useAgent` 与 `useCopilotKit` 的最小聊天屏幕：

        ```tsx title="src/ChatScreen.tsx"
        import { useCallback, useRef, useState } from "react";
        import {
          FlatList,
          KeyboardAvoidingView,
          Platform,
          Text,
          TextInput,
          TouchableOpacity,
          View,
        } from "react-native";
        import { useAgent, useCopilotKit } from "@copilotkit/react-native/headless"; // [!code highlight]

        export function ChatScreen() {
          const [inputText, setInputText] = useState("");
          const flatListRef = useRef<FlatList>(null);

          const { copilotkit } = useCopilotKit(); // [!code highlight:2]
          const { agent } = useAgent({ agentId: "default" });

          const messages = agent?.messages ?? [];
          const isLoading = agent?.isRunning ?? false;
          const chatMessages = messages.flatMap((message) => {
            if (
              (message.role === "user" || message.role === "assistant") &&
              typeof message.content === "string" &&
              message.content.length > 0
            ) {
              return [
                {
                  id: message.id,
                  content: message.content,
                },
              ];
            }
            return [];
          });

          const handleSend = useCallback(async () => {
            const text = inputText.trim();
            if (!text || isLoading || !agent) return;

            setInputText("");
            agent.addMessage({ // [!code highlight:5]
              id: `user-${Date.now()}`,
              role: "user",
              content: text,
            });
            await copilotkit.runAgent({ agent }); // [!code highlight]
          }, [inputText, isLoading, agent, copilotkit]);

          return (
            <KeyboardAvoidingView
              style={{ flex: 1 }}
              behavior={Platform.OS === "ios" ? "padding" : "height"}
            >
              <FlatList
                ref={flatListRef}
                data={chatMessages}
                renderItem={({ item }) => (
                  <View style={{ padding: 12, maxWidth: "80%" }}>
                    <Text>{item.content}</Text>
                  </View>
                )}
                keyExtractor={(item, i) => item.id ?? String(i)}
                onContentSizeChange={() =>
                  flatListRef.current?.scrollToEnd({ animated: true })
                }
              />
              <View style={{ flexDirection: "row", padding: 8 }}>
                <TextInput
                  style={{ flex: 1, borderWidth: 1, borderRadius: 8, padding: 8 }}
                  value={inputText}
                  onChangeText={setInputText}
                  placeholder="Type a message..."
                />
                <TouchableOpacity onPress={handleSend} style={{ padding: 8 }}>
                  <Text>Send</Text>
                </TouchableOpacity>
              </View>
            </KeyboardAvoidingView>
          );
        }
        ```

        <Callout type="info" title="无头（headless）设计">
          `@copilotkit/react-native/headless` 只提供 hooks 而非 UI 组件，因此你可以用标准 React Native 组件完全掌控聊天界面。如果不想自己搭建，`@copilotkit/react-native/components` 提供了渲染好的聊天组件——参见[导入入口](#import-surfaces)。
        </Callout>
    </Step>
    <Step>
        ### 启动运行时与应用

        在一个终端中启动 Copilot Runtime：

        ```bash
        export OPENAI_API_KEY=sk-...
        npx tsx server.ts
        ```

        在另一个终端中运行 React Native 应用：

            <Tab value="iOS">
                ```bash
                npx react-native run-ios
                ```
            </Tab>
            <Tab value="Android">
                ```bash
                npx react-native run-android
                ```
            </Tab>
        </Tabs>
    </Step>
    <Step>
        ### 开始聊天！

        你的 React Native 应用现在已连接到 Copilot Runtime。以下是可用的共享 hooks：

        - `useAgent` - 连接智能体并管理消息
        - `useFrontendTool` - 让智能体调用你应用中的函数
        - `useHumanInTheLoop` - 为智能体操作添加审批流程
        - `useCopilotKit` - 直接访问 CopilotKit 实例
        - `useRenderTool` - 为不归你所有的工具调用绘制 UI，可按名称指定，也可用 `"*"` 作为兜底（参见[前端工具](#前端工具与生成式-ui)）

        <Accordions className="mb-4">
            <Accordion title="故障排查">
                - **Metro 无法解析模块**：使用 `npx react-native start --reset-cache` 清除缓存。
                - **流式传输不工作**：确保 polyfill 在入口文件中先于任何 CopilotKit 代码导入。
                - **运行时无响应**：确认运行时服务器正在运行、`http://localhost:8200/api/copilotkit/info` 能返回 `default` 智能体，且设备能够访问 `runtimeUrl`。物理设备请使用开发机的局域网 IP 而不是 `localhost`。
                - **模型认证错误**：确认运行 `npx tsx server.ts` 的终端中设置了 `OPENAI_API_KEY`。
                - **`Property 'ReadableStream' doesn't exist`**（`TextEncoder`、`DOMException` 或 `Headers` 报同样错误）：polyfill 没有安装。在 **1.69.2 及所有更早版本**中，`polyfills` 桶文件发布时是空的——构建过程把五个 polyfill 导入全部丢弃了——因此按上面的说明安装完什么都不会生效，第一次运行时调用就会失败。请升级到最新版本；如果版本被锁定，可使用从未受影响的[细粒度导入](#polyfill)。这与下面的冲突情形*正好相反*：这里是完全没有 polyfill，而不是存在一个与之竞争的 polyfill。
                - **已有 polyfill 冲突**：改用细粒度导入，而不是 `polyfills` 桶导入。
            </Accordion>
        </Accordions>
    </Step>

## 导入入口

`@copilotkit/react-native` 有三个 JavaScript 入口。它们的差别在于提供什么 UI，以及——对发布 bundle 至关重要——Metro 必须解析哪些原生对等依赖。

| 导入 | 起始版本 | 提供的内容 | Metro 必须解析的原生依赖 |
|------|----------|------------|--------------------------|
| `@copilotkit/react-native/headless` | **1.64.0** | `CopilotKitProvider` 与所有平台无关的 hook。不含组件。 | **无** |
| `@copilotkit/react-native`（根入口） | 所有版本 | `/headless` 的全部内容，外加 `useAttachments`、两个*无头*聊天包装器（`CopilotChat`、`CopilotModal`）以及 `CopilotSidebar` / `CopilotPopup` 外壳 | `expo-document-picker`、`expo-file-system`（经由 `useAttachments`） |
| `@copilotkit/react-native/components` | 所有版本 | **渲染好的**聊天 UI：带消息列表的 `CopilotChat`、底部弹层式 `CopilotModal`、`CopilotMarkdown`、`AssistantMessage`、`UserMessage` | `@gorhom/bottom-sheet`（其自身需要 `react-native-reanimated` + `react-native-gesture-handler`）、`react-native-streamdown` |

辅助入口：

| 导入 | 说明 |
|------|------|
| `@copilotkit/react-native/polyfills` | 安装全部 polyfill（streams、encoding、crypto、dom、location）以及流式 fetch shim 的桶文件 |
| `@copilotkit/react-native/polyfills/{streams,encoding,crypto,dom,location}` | 安装单个 polyfill 的细粒度子路径 |
| `@copilotkit/runtime` | 用于承载智能体的服务端运行时（`CopilotRuntime` / `BuiltInAgent` / `createCopilotNodeListener`） |

<Callout type="warn" title="`CopilotChat` 有两种不同含义">
  根入口的 `CopilotChat` 与 `CopilotModal` 是**无头包装器**——只渲染 context 与 `children`，不渲染消息和工具 UI。真正绘制聊天界面的是 `@copilotkit/react-native/components` 中的同名导出。如果你导入 `CopilotChat` 想要一个聊天界面却得到一片空白，那就是导入成根入口的了。
</Callout>

由于这些都是静态再导出，无论你是否调用相应代码，Metro 都会在打包时解析该入口的对等依赖——因此导入根入口的自定义 UI 应用仍必须安装 `expo-document-picker` 与 `expo-file-system`（或对它们做 stub），否则发布 bundle 会报错 `Unable to resolve module expo-document-picker`。从 `/headless` 导入则完全可以避开这一点，本指南正是因此才使用它：

```tsx title="App.tsx"
import {
  CopilotKitProvider,
  useAgent,
  useFrontendTool,
} from "@copilotkit/react-native/headless"; // [!code highlight]
```

在 `@copilotkit/react-native` 1.63.x 及更早版本上没有 `/headless`——该子路径在 1.64.0 中加入（[#6142](https://github.com/CopilotKit/CopilotKit/pull/6142)），正是为了在没有聊天与附件对等依赖的情况下支持这种自定义 UI 场景。根入口仍是该包默认的完整入口，在每个版本上都导出同样的 provider 与 hooks；`/headless` 是精简的替代选择，而不是替代品。在锁定的旧版本上，请从根入口导入，并安装或 stub `expo-document-picker` 与 `expo-file-system`。

导入 provider 会自动安装 polyfill：`/headless` 把 polyfill 桶文件作为第一条语句执行，根入口则通过它对 `/headless` 的再导出获得同样效果。`/components` 自身**不会**安装它们——它依赖与它一起导入的 provider（来自 `/headless` 或根入口）。而且由于根入口再导出了 `/headless` 的全部内容，既有的 `@copilotkit/react-native` 导入无需任何改动即可继续工作。

### 哪些 hook 是共享的，哪些不是

**该包**（`/headless` 与根入口皆是）再导出了来自 `@copilotkit/react-core` 的平台无关 hooks：`useAgent`、`useFrontendTool`、`useHumanInTheLoop`、`useInterrupt`、`useSuggestions`、`useConfigureSuggestions`、`useAgentContext`、`useThreads`、`useCapabilities`、`useComponent`、`useCopilotKit` 与 `useRenderToolCall`。它们的行为与 Web 上一致。

`useRenderTool` 同样来自 `@copilotkit/react-core`，行为也与 Web 上一致——但它有一段值得了解的历史。React Native 曾以同一名字导出一个*不同的* hook，它同时注册工具和渲染器，因此 `name: "*"` 会注册一个字面上名为 `*` 的前端工具。它在 1.68 中被 react-core 的 hook 取代，并靠一个已弃用的兼容 shim 继续工作，该 shim 后来已被移除。如果你来自 1.68 之前的版本，参见[从旧版 React Native `useRenderTool` 迁移](/reference/react-native/hooks/useRenderTool#migrating-from-the-old-react-native-userendertool)。

还有两点值得了解：

- **`useFrontendTool` 与 `useRenderTool` 不可互换**，其中的区分与 Web 上的划分一致。`useFrontendTool` 注册一个**工具**以及（可选的）它的渲染器：工具会在每次运行时向模型宣告、模型可以调用它，因此它需要 `description` 和 `handler`。`useRenderTool` 只注册**渲染器**——不宣告任何东西，也没有任何东西变得可调用；它为别人拥有的工具调用绘制 UI，例如服务端工具，`name: "*"` 会让它成为所有没有自己渲染器的工具调用的兜底。两者写入同一个 react-core 渲染器注册表，渲染好的聊天读取的正是它。两者的 render 类型也各不相同，与 Web 上完全一致：`useRenderTool` 的 `render` 必须返回 `ReactElement | null`，而 `useFrontendTool` 的 `render` 是一个组件类型，同时也接受裸字符串。真正属于 React Native 特有的是宽松类型带来的后果——裸字符串能通过类型检查，然后在 `FlatList` 内部抛出异常。给 `useFrontendTool` 的渲染器标注可选的 [`FrontendToolRenderFunction<T>`](/reference/react-native/hooks/useFrontendTool#the-render-type-react-native-needs)，即可让编译器替你把它拒之门外。
- **大多数 Web 渲染 hooks 被有意排除在导出之外**：`useDefaultRenderTool`（其内置卡片渲染 `<div>` / `<svg>`）、`useRenderCustomMessages` 与 `useRenderActivityMessage`（二者都绑定 Web 聊天消息栈）。不过 `useRenderToolCall` **是**导出的——它平台无关、不引入 DOM，并返回 `ReactElement | null`，恰好是 `FlatList` 的 `renderItem` 所需要的，因此你可以在任意界面上绘制已注册的工具调用，而不只是聊天内部。

<Callout type="warn" title="在屏幕上渲染数据并不意味着智能体能访问它">
  `useAgentContext` 在上面的共享列表中，而它正是缺失时会*静默*失败的那一个。渲染列表的屏幕只是把列表放进了视图树，并没有放进智能体的上下文——这是两个独立的步骤。缺少第二步的智能体依然会回答：文字通顺、工具 UI 正常绘制、数值看起来也合理，而且没有任何报错。在 Web 上你至少还有控制台可以检查。在这里没有。

  用 `useAgentContext` 注册数据，并在智能体的指令中写明：对上下文未携带的记录要拒绝回答。然后拿一条回答与应用实际持有的记录核对——如果它提到了任何其他内容，那么上下文从未送达，无论屏幕看起来多么正确。
</Callout>

## 发布 bundle 的 Metro 配置

启用包 exports 后，发布 bundle 可能报错 `Unable to resolve module node:crypto`（或其他 `node:` 前缀的说明符），并指向 `jose`。这个问题**只在打包时**出现，绝不会在类型检查时出现。

`jose` 并不是直接依赖。它通过遥测链路传递引入：`@copilotkit/shared` → `@segment/analytics-node` → `jose`。`jose` 在其 `exports` 映射背后发布了独立的 Node 与浏览器构建，其 Node 构建导入了带 `node:` 前缀的模块，而 Hermes 无法打包这些模块。

解决办法是用 `resolveRequest` 专门将 **`jose`** 按其 `browser` 条件解析：

```js title="metro.config.js"
const { getDefaultConfig, mergeConfig } = require("@react-native/metro-config");

const config = {
  resolver: {
    resolveRequest: (context, moduleImport, platform) => {
      // jose reaches the bundle via @copilotkit/shared -> @segment/analytics-node.
      // Its Node build imports node:* modules that Hermes can't bundle.
      if (moduleImport === "jose" || moduleImport.startsWith("jose/")) {
        return context.resolveRequest(
          { ...context, unstable_conditionNames: ["browser"] }, // [!code highlight]
          moduleImport,
          platform,
        );
      }
      return context.resolveRequest(context, moduleImport, platform);
    },
  },
};

module.exports = mergeConfig(getDefaultConfig(__dirname), config);
```

在 Expo 上，换用来自 `expo/metro-config` 的 `getDefaultConfig` 即可；`resolver` 块完全相同。

<Callout type="warn" title="不要全局断言 `browser`">
  直接设置 `resolver.unstable_conditionNames = ["browser", ...]` 看似诱人。请避免这样做：

  - `unstable_conditionNames` 是一个**无序的断言条件集合**，不是优先级列表。最终选中的目标由*每个包自己的* `exports` 映射中的键顺序决定，因此调整这个数组的顺序不会有任何效果。
  - 它是**全局**生效的，依赖图中每个提供双构建的依赖都会切换到浏览器构建——不只是 `jose`。
  - Metro 在 React Native 下的默认值是 `["require", "react-native"]`。整体替换它会丢掉 `react-native` 条件，从而改变任何提供该条件的包的解析结果。

  用 `resolveRequest` 限定范围后，其余地方的 Metro 默认行为都保持不变。
</Callout>

<Callout type="info" title="你需要 `unstable_enablePackageExports` 吗？">
  包 `exports` 解析**从 Metro 0.82 / React Native 0.79 起默认启用**，这些版本无需任何开关。它在 React Native 0.72（Metro 0.76.1）中以可选方式引入——在 React Native 0.72–0.78 上需设置 `resolver.unstable_enablePackageExports = true`，这也正是让 Metro 能解析本包 `/headless`、`/components` 与 `/polyfills` 子路径的开关。低于 0.72 的 React Native 不支持包 exports。
</Callout>

<Callout type="success" title="无头入口免去了 stub">
  从 [`@copilotkit/react-native/headless`](#import-surfaces) 导入意味着 Metro 永远不会解析聊天或附件的对等依赖，因此你完全不需要 `@gorhom/bottom-sheet`、`expo-document-picker` 或 `expo-file-system`。上面的 `jose` 解析器与这一选择无关——无论选哪种都需要它。
</Callout>

## Polyfill

Hermes 缺少 CopilotKit 依赖的若干 Web API：`ReadableStream` / `WritableStream` / `TransformStream`、`TextEncoder` / `TextDecoder`、`DOMException` 与 `Headers`、`crypto.getRandomValues`，以及 `window.location`。它还缺少流式 `fetch` 响应体（`response.body.getReader()`），而 AG-UI 的 SSE 传输正需要它。

导入 provider 会自动安装这些 polyfill：`/headless` 把 polyfill 桶文件作为第一条语句执行（根入口则通过 `/headless` 获得同样效果），并在加载时一并安装基于 XHR 的流式 fetch shim。`/components` 入口自身**不会**安装它们，因此依赖与之一起导入的 provider。每个 polyfill 在其定义的全局对象已存在时都会跳过，因此重复导入是安全的。

无论如何，请把快速开始中显式的 `import "@copilotkit/react-native/polyfills"` 保留在入口文件顶部。由于每个 polyfill 都是**先写入者生效**，入口文件是唯一能让你在 CopilotKit 自身默认值之前控制安装内容的地方——下面要讲的安全 RNG 顺序正是依赖这一点才能成立。

如需细粒度控制——例如你已经自己 polyfill 了 `ReadableStream`——只导入需要的部分，而不使用桶文件：

```js
import "@copilotkit/react-native/polyfills/streams";
import "@copilotkit/react-native/polyfills/encoding";
import "@copilotkit/react-native/polyfills/crypto";
import "@copilotkit/react-native/polyfills/dom";
import "@copilotkit/react-native/polyfills/location";
```

<Callout type="warn" title="内置的 crypto polyfill 并非加密级安全">
  CopilotKit 的 `crypto` polyfill 用 `Math.random` 实现 `crypto.getRandomValues`——对它生成的消息与运行 ID 来说足够了，且安装时会记录一条警告。生产环境请安装 [`react-native-get-random-values`](https://github.com/LinusU/react-native-get-random-values)，并在**入口文件的第一行、任何 CopilotKit 导入之前**导入它：

  ```js title="index.js"
  import "react-native-get-random-values"; // [!code highlight] secure RNG — must be first
  import "@copilotkit/react-native/polyfills";
  // ...
  ```

  这个顺序是硬性要求，不是预防性建议。两种实现都只在 `crypto.getRandomValues` 未定义时安装，因此先加载者永久生效。如果任何 CopilotKit 模块先被求值，`Math.random` 回退就会被锁定，`react-native-get-random-values` 会静默变成空操作——没有警告、没有报错，而且进程存续期间所有 ID 都不是加密级的。
</Callout>

## Provider 选项

`CopilotKitProvider` 是纯 context 的 provider（自身不渲染任何视图），因此可以干净地作为应用最外层的包装器。`runtimeUrl` 是唯一必需的 prop，此外还有若干可用选项：

| 属性 | 类型 | 说明 |
|------|------|------|
| `runtimeUrl` | `string` | Copilot Runtime 端点的 URL（**必需**） |
| `headers` | `Record<string, string> \| (() => Record<string, string>)` | 随每个请求发送的自定义 header。用于认证——例如 `Authorization` bearer 令牌。函数形式会在 **provider 渲染时**调用，而不是每次请求时（见下方提示） |
| `credentials` | `RequestCredentials` | Fetch 凭据模式，例如 `"include"` 可在跨域请求中发送 HTTP-only cookie |
| `properties` | `Record<string, unknown>` | 转发给智能体的自定义属性（如带范围限定的用户 id） |
| `onError` | `(event) => void` | 所有错误类型（运行时连接、智能体、工具）都会调用。默认为 `console.error` |
| `debug` | `DebugConfig` | 启用详细的客户端事件日志 |
| `defaultThrottleMs` | `number` | 流式更新的默认重渲染节流时间；单个 `useAgent` 调用可以覆盖 |
| `useSingleEndpoint` | `boolean` | 运行时是否使用单路由端点（默认自动检测） |

```tsx title="App.tsx"
<CopilotKitProvider
  runtimeUrl={runtimeUrl}
  headers={{ Authorization: `Bearer ${token}` }} // [!code highlight]
  properties={{ userId }}
>
  <ChatScreen />
</CopilotKitProvider>
```

<Callout type="warn" title="轮换认证令牌：`headers` 在渲染时求值，而非按请求求值">
  如果你传入函数，provider 会**在其渲染体中**调用它、缓存结果，并把该对象推入核心，由核心把它快照到每个智能体上。请求时不会有任何东西重新调用这个函数。

  因此只有当 provider **重新渲染**且产生的 headers 有变化时，新令牌才会被采用。用 React state（或 context）管理令牌，让刷新触发渲染：

  ```tsx
  const [token, setToken] = useState(initialToken);

  <CopilotKitProvider runtimeUrl={runtimeUrl} headers={{ Authorization: `Bearer ${token}` }}>
  ```

  保存在 ref、模块变量或不触发渲染的异步 SDK 缓存中的令牌，会无限期地继续发送**过期**值。如果无法触发重渲染，请在令牌轮换时直接调用 `copilotkit.setHeaders({ ... })`。

  Web 端 provider 的 `headers` 构建器现在会在每个请求发送时运行，并且也接受异步函数。这两点在这里都还不适用：React Native provider 仍在渲染时对构建器求值，且只接受同步函数。
</Callout>

<Callout type="info" title="云端属性在 React Native 上尚未支持">
  Web 端 provider 的 `publicApiKey` / `licenseToken` 云端属性不受 React Native provider 支持。请将 `runtimeUrl` 指向你自己的 Copilot Runtime。
</Callout>

## 运行时与模型的连接配置

快速开始中的运行时承载一个 `BuiltInAgent`，并用 `createCopilotNodeListener` 对外提供服务——它可以直接接入 Node 内置的 `node:http` `createServer`，无需 Hono 或 Express 依赖。`createCopilotNodeListener({ runtime, basePath, cors })` 返回一个请求监听器。

`cors: true` 会添加 `Access-Control-*` 响应头并应答 `OPTIONS` 预检。这对**浏览器**客户端——Expo Web 或 `react-native-web`——很重要，但对原生 iOS 或 Android 构建能否访问服务器没有任何影响：CORS 由浏览器强制执行，而 React Native 的原生网络栈（`NSURLSession` / OkHttp）既不发送 `Origin` 头，也不理会 `Access-Control-Allow-Origin`。原生的可达性由服务器的绑定地址、局域网路由与防火墙，以及平台传输安全策略决定——参见[从设备或测试机连接](#connecting-from-a-device-or-bench)。

`BuiltInAgent` 接受 `provider:model`（或 `provider/model`）形式的模型**字符串**，适用于 OpenAI、Anthropic 与 Google：

```ts
new BuiltInAgent({ model: "openai:gpt-5-mini", prompt: "..." });      // OPENAI_API_KEY
new BuiltInAgent({ model: "anthropic:claude-sonnet-4-6", prompt: "..." }); // ANTHROPIC_API_KEY
new BuiltInAgent({ model: "google:gemini-3.8-flash", prompt: "..." }); // GOOGLE_API_KEY
```

字符串形式会从环境中读取对应提供方的 API 密钥。你也可以在配置中传入 `apiKey`，或者用已构造好的 AI SDK `LanguageModel` 实例代替字符串。

### OpenAI 兼容端点

要把字符串模型形式指向 OpenAI 兼容端点（网关、Azure OpenAI、自托管服务器等），请设置 base URL 环境变量——运行时在构造提供方时会遵循它：

```bash
export OPENAI_BASE_URL=https://your-gateway.example.com/v1
export OPENAI_API_KEY=sk-...
npx tsx server.ts
```

在 OpenAI 或 Azure 之外的主机上，`openai:` 模型使用 Chat Completions API。若要在 OpenAI 前置的网关上继续使用 Responses API，还需设置 `COPILOTKIT_OPENAI_API=responses`。参见[模型选择](/model-selection#openai-compatible-endpoints)。

`ANTHROPIC_BASE_URL` 与 `GOOGLE_GENERATIVE_AI_BASE_URL` 同理。变量未设置时，提供方会回退到默认端点，因此完全向后兼容——仅仅为了改 base URL 并**不**需要构造自定义模型实例。

<Callout type="info" title="BuiltInAgent 的其他选项">
  除 `model` 与 `prompt` 之外，`BuiltInAgent` 还接受 `maxSteps`（工具调用迭代次数，默认 `1`）、`tools`（通过 `defineTool` 在服务端执行的工具）、`temperature`、`maxOutputTokens`、`providerOptions`（如 OpenAI 的 `reasoningEffort`），以及 `mcpServers` / `mcpClients`。会改动应用 UI 的工具应通过 `useFrontendTool`（下文）放在**客户端**，而不是放进服务端的 `tools` 列表。
</Callout>

## 从设备或测试机连接

`runtimeUrl` 必须是**设备**能够访问的地址——物理设备或模拟器上的 `localhost` 解析到设备自身，而不是你的开发机。

| 环境 | `runtimeUrl` 主机 |
|------|-------------------|
| iOS 模拟器 | `localhost` 可访问宿主机 |
| Android 模拟器 | `10.0.2.2` 是模拟器对宿主机 `localhost` 的别名 |
| USB 连接的 Android 设备 | 先运行 `adb reverse tcp:8200 tcp:8200`，然后在设备上使用 `localhost`。`adb reverse` 仅限 Android——iOS 没有等价物 |
| iOS 设备 | 开发机的局域网 IP，且与设备同一 Wi-Fi 网络——再加上明文 `http://` 地址所需的 [ATS 例外](#物理设备上的明文-http) |
| 同一局域网内的物理设备（测试台） | 开发机的局域网 IP，例如 `http://192.168.1.23:8200/api/copilotkit` |
| 生产环境 | 基于 HTTPS 的托管运行时 URL |

快速开始已经针对模拟器情况按 `Platform.OS` 分支处理。请把这个 URL 保留为单个带注释的命名常量，方便按环境替换。

### 物理设备上的明文 HTTP

两个平台默认都阻止明文（非 TLS）HTTP，因此设备会静默地无法访问普通的 `http://<lan-ip>` 开发运行时。这些都只是开发环境的便利配置——托管的 TLS 运行时一概不需要。

在 Expo 上，请通过 `app.json` 配置这两项，使其在 `expo prebuild` 重新生成 `android/` 与 `ios/` 后依然保留（切勿手工编辑生成的 `AndroidManifest.xml` 或 `Info.plist`——下次 prebuild 就会被丢弃）。先安装配置插件：

```bash
npx expo install expo-build-properties
```

**Android** —— Android *发布*构建需要显式允许明文流量：

```jsonc title="app.json"
{
  "expo": {
    "plugins": [
      ["expo-build-properties", { "android": { "usesCleartextTraffic": true } }]
    ]
  }
}
```

**iOS** —— App Transport Security 对调试与*发布*构建一视同仁，而 `expo-build-properties` 没有 iOS ATS 选项，因此要写进 `ios.infoPlist`。自 iOS 17 起，ATS 会拒绝裸 IP 地址，除非该地址列在 `NSExceptionDomains` 中，所以要显式写明开发机的 IP（不含端口）：

```jsonc title="app.json"
{
  "expo": {
    "ios": {
      "infoPlist": {
        "NSAppTransportSecurity": {
          "NSExceptionDomains": {
            "192.168.1.23": { "NSExceptionAllowsInsecureHTTPLoads": true }
          }
        },
        "NSLocalNetworkUsageDescription": "Connects to the local Copilot Runtime during development."
      }
    }
  }
}
```

`NSLocalNetworkUsageDescription` 需要单独配置：iOS 把本地网络访问置于用户权限提示之后，没有这个字符串时，无论 ATS 如何设置连接都会失败。

<Callout type="warn" title="不要把这些带进生产构建">
  `usesCleartextTraffic` 与 ATS 例外都只是测试台的便利配置。请将它们限定在开发构建中（单独的 Expo profile 或应用变体），生产环境则一律对接不带这两项配置的 HTTPS 运行时。在 Android 上还可以用 network-security-config 把明文流量进一步限定为只有开发主机。
</Callout>

<Callout type="info" title="仅靠 `NSAllowsLocalNetworking` 并不够">
  Expo 与 React Native 模板已经自带 `NSAllowsLocalNetworking: true`，它覆盖 `.local` 主机名与不带后缀的主机名——但在 iOS 17+ 上**不**覆盖裸 IP 地址。它的存在还会导致 `NSAllowsArbitraryLoads` 被忽略。上面的 `NSExceptionDomains` 条目才是对局域网 IP 真正有效的写法。
</Callout>

## 前端工具与生成式 UI

前端工具让智能体在模型运行期间调用你应用中的函数——并渲染 UI。使用 `useFrontendTool` 注册它们。`parameters` 遵循 [Standard Schema](https://standardschema.dev)，因此 `zod` schema（zod ≥ 3.24 实现了 Standard Schema）就是预期的形态。`zod` 是 `@copilotkit/react-native` 的可选对等依赖，请把它加入你的应用：

```tsx title="src/useComposeStage.ts"
import { useFrontendTool } from "@copilotkit/react-native/headless";
import { z } from "zod";

export function useComposeStage() {
  useFrontendTool({
    name: "composeStage",
    description: "Render POI panels on the screen.",
    agentId: "default", // scope the tool to one agent
    parameters: z.object({
      mode: z.enum(["home", "nearby", "hotels"]),
      panels: z.array(
        z.object({ title: z.string(), body: z.string().optional() }),
      ),
    }),
    handler: async (args) => {
      // Runs on the device. Push args into your own state/reducer here.
      return "rendered";
    },
  });
}
```

由于工具注册在设备上，模型的调用会在客户端到达你的 `handler`——这是驱动状态 reducer 的理想位置，你的 React Native 视图再以声明方式渲染它（智能体发送*状态*，客户端负责渲染）。可辨识联合 / `oneOf` / `anyOf` 参数 schema 会在运行时的 schema 转换中保留，因此 `z.discriminatedUnion(...)` 参数可用。在 handler 中做防御性归一化仍是好习惯——把部分填充的工具调用规整成有效状态，而不是让畸形调用渲染出错乱的界面。

<Callout type="warn" title="按工具的归属选 hook，而不是按 UI 的去向">
  两个 hook 写入的是**同一个**地方：react-core 的渲染器注册表，渲染好的 React Native 聊天（`@copilotkit/react-native/components`）通过 `useRenderToolCall` 读取它。因此内嵌聊天的 UI 两者都办得到——传给 `useFrontendTool` 的 `render` *确实*会在那里绘制。区别在于是否注册**工具**。

  应用自己拥有的工具用 `useFrontendTool`：它会向模型宣告该工具，并在设备上运行你的 `handler`。如果还想让它显示在聊天里，就在 handler 之外再传 `render`。

  ```tsx
  import { useFrontendTool } from "@copilotkit/react-native/headless";

  useFrontendTool({
    name: "composeStage",
    description: "Render POI panels on the screen.",
    parameters: z.object({ mode: z.string() }),
    handler: async (args) => { /* drive your own state */ return "rendered"; },
    render: ({ args, status }) => (
      <StagePreview mode={args.mode} pending={status !== "complete"} />
    ),
  });
  ```

  工具**不**归你所有时用 [`useRenderTool`](/reference/react-native/hooks/useRenderTool)——例如你只想绘制某个服务端工具，或用 `name: "*"` 为所有没有自己渲染器的工具调用兜底。它不注册工具，不接受 `description` 和 `handler`，并把参数以 `parameters` 暴露：

  ```tsx
  import { useRenderTool } from "@copilotkit/react-native/headless";

  useRenderTool(
    {
      name: "lookupPlaces",
      parameters: z.object({ mode: z.string() }),
      render: ({ parameters, status }) => (
        <StagePreview mode={parameters.mode} pending={status !== "complete"} />
      ),
    },
    [],
  );
  ```

  `useRenderTool` 的 `render` 必须返回 `ReactElement | null`，返回 `null` 就什么都不绘制。`useFrontendTool` 的 `render` 是组件类型，同时也接受裸字符串——它能通过类型检查，然后在 `FlatList` 内部抛出异常——所以那里也要返回元素或 `null`，如果你想让编译器替你把关，就用可选的 [`FrontendToolRenderFunction<T>`](/reference/react-native/hooks/useFrontendTool#the-render-type-react-native-needs) 标注渲染器。

  在 1.68 之前的 React Native 上，`useRenderTool` 是一个*不同的*、RN 本地的 hook，会同时注册工具和渲染器。现在携带 `description` 或 `handler` 的调用将无法通过类型检查——请把它改名为 `useFrontendTool`。[迁移说明](/reference/react-native/hooks/useRenderTool#migrating-from-the-old-react-native-userendertool)。

  两个 hook 中 `status` 都是 `"inProgress"` / `"executing"` / `"complete"`——在 `useRenderTool` 的 render props 中类型是字符串字面量，在 `useFrontendTool` 中则是 `ToolCallStatus` 枚举成员。**你不必关心用的是哪种**。字符串枚举成员可以赋给其自身的字面量类型，因此字符串与成员对两种形态都可以互换比较，且两种形式都能收窄类型。如果你更想用枚举成员，`ToolCallStatus` 已作为值从 `/headless` 导出。

  对于长度无法预知的智能体生成内容，把它放进 `ScrollView` 并把 `maxHeight` 设为可用高度来渲染——内容短时随内容收缩，内容长时可滚动，因此永远不会被硬性截断。
</Callout>

### 发送一轮对话并读取运行状态

运行一轮用户输入就是快速开始展示的两步：先 `agent.addMessage(...)`，再 `copilotkit.runAgent({ agent })`（runner 位于核心上，而不是智能体上）。要取消进行中的运行，调用 `copilotkit.stopAgent({ agent })`。

当另一个组件只需要运行标志——比如“思考中”指示器——时，用 `useAgent` 订阅（纯读取，不注册任何东西）并读取 `agent.isRunning`。注册工具的 hook 对每个智能体只能调用**一次**，避免工具被注册两遍。

## 运行生命周期与 UI

客户端执行的前端工具会在**运行中途**渲染它的 UI：工具触发、你的 handler 绘制屏幕，而智能体的运行仍在继续（更多推理、收尾总结）。因此内容已经可见之后，`agent.isRunning` 仍会保持 `true`——推理档模型更是如此。围绕这个时间差设计受运行控制的 UI：

- 把加载遮罩严格绑定在 `isRunning` 上（为 `false` 时不渲染任何东西），这样出错的回合不会让遮罩卡在屏幕上。把始终可用的控件（主页或取消按钮）放在遮罩之上，运行收尾时它们仍可点击。
- 如果要做揭示动画，应在 `isRunning` 的**下降沿**（true → false）触发，而不是在内容到达的状态变化时——否则动画会在遮罩仍在时播放，用户根本看不到。
- 用智能体上的 `maxSteps` 约束运行的尾程，避免它停留得比必要的更久。

## 语音与语音转文本

`@copilotkit/voice` **尚未**适配 React Native，因此没有开箱即用的语音 hook。语音需要自备 STT：用 React Native 语音识别器采集转写文本，再把最终文本送入与上面相同的发送路径（`agent.addMessage` + `copilotkit.runAgent`）。

<Callout type="warn" title="不要假设平台语音识别器一定存在">
  封装操作系统语音服务的识别器（iOS `SFSpeechRecognizer` / Android `SpeechRecognizer`）在去 Google 化或车机硬件上可能**不存在**，此时调用会直接抛错而不是优雅降级。如果你的目标设备属于这类，请对不可用的情况做防护并回退到文本输入，或嵌入一个设备端识别器（如 Vosk）作为保底。始终为语音提供确定的**发送**控件，不要依赖静音检测来结束一轮。
</Callout>

## 验证它确实可用

在 Web 上，你打开浏览器、看着工具 UI 绘制出来，就能证明集成生效。这里没有浏览器，这一步无法照搬——而各个替代手段证明的东西都比看起来要少。三项检查合起来才能覆盖；单独任何一项都不充分。

### 1. 运行时可达且智能体有应答

```bash
npx copilotkit verify --round-trip
```

它通过运行时发送一个请求，并从会话线程读回答案，从而把*已配置*的智能体与*能工作*的智能体区分开——全程不涉及浏览器和设备。请在承载运行时的机器上运行，而不是在设备上。CLI 默认探测 `http://localhost:3000/api/copilotkit`，因此针对本指南搭建的运行时要传 `--runtime-url http://localhost:8200/api/copilotkit`，如果运行时声明了多个智能体，还要传 `--agent <id>`。

<Callout type="warn" title="--round-trip 不能证明什么">
  它只能证明有答案返回——不能证明答案说了什么，也不能证明是*哪个*部署回答的。完整的边界参见 [`--round-trip` 不能证明什么](/cli#verify-your-setup)。所以这只是三步中的第一步，不是放行信号。
</Callout>

### 2. 工具 UI 确实在设备上渲染

启动模拟器、操作应用并截取屏幕。Android 上：

```bash
adb devices                                   # 确认有一个已启动的目标设备
adb exec-out screencap -p > proof.png         # 截取已渲染的屏幕
adb logcat -d -s ReactNativeJS:E              # 没有未解决的 redbox
```

如果你用的是 USB 设备，先执行 `adb reverse tcp:8200 tcp:8200`，让设备上的 `localhost` 能到达你的运行时——参见[从设备或测试机连接](#connecting-from-a-device-or-bench)。

这方面 iOS 没有 `adb` 的等价物。最接近的是 `xcrun simctl io booted screenshot proof.png`，且它需要完整版 Xcode——仅装 Command Line Tools 不带 `simctl`。如果你的环境连模拟器都没有，请如实说明，不要用浏览器替代：网页截图证明的是另一个应用。

### 3. 应答内容与你的数据相符

这一项检查能抓住前两项抓不住的问题。基于应用并不持有的记录渲染的工具卡片，与正确的卡片看起来*一模一样*——截图里、视频里，以及在不熟悉你数据的人眼里都是如此。

所以请读取应用实际持有的记录，确认回答提到的正是这些记录而没有别的。如果它提到了其他东西，问题出在 UI 的上游：上下文从未注册（参见[哪些 hook 是共享的，哪些不是](#which-hooks-are-shared-and-which-arent)一节中的提示）、智能体的指令忽略了它，或者屏幕在上下文注册之后才加载数据。

## 已知限制

- **自定义 UI 中的 Markdown** —— `@copilotkit/react-native/components` 上的渲染聊天会替你渲染 markdown（经由 `CopilotMarkdown`，底层是 `react-native-streamdown`）。如果自建 UI，普通 `Text` 会原样显示 markdown——请复用 `CopilotMarkdown` 或自备渲染器。
- **Inspector** —— [Inspector](/inspector#where-inspector-runs) 是把自定义元素挂载进 DOM 的浏览器覆盖层，因此没有 React Native 形态，`@copilotkit/react-native` 也不提供它。[验证它确实可用](#proving-it-works)下的三项检查覆盖了它本可以展示给你的内容。
- **语音** —— `@copilotkit/voice` 尚未适配 React Native；按上文接入你自己的 STT。
- **`useAgent` 上的 `threadId`** —— 尚不支持（[#6141](https://github.com/CopilotKit/CopilotKit/pull/6141)）。线程范围由聊天配置 provider 提供；传给 `useAgent` 的 `threadId` 无法通过类型检查且会被忽略。
- **云端 provider 属性** —— `publicApiKey` / `licenseToken` 不受 React Native provider 支持；请通过 `runtimeUrl` 连接。
- **仅限 Web 的渲染 hooks** —— `useDefaultRenderTool`、`useRenderCustomMessages` 与 `useRenderActivityMessage` 未导出，因为它们渲染宿主 DOM 或绑定 Web 聊天消息栈。`useRenderToolCall` **是**导出的；用它可以在聊天之外绘制已注册的工具调用。
