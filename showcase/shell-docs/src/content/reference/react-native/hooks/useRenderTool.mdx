## 概览

`useRenderTool` 只注册**渲染器**。它为别人拥有的工具调用提供 UI——服务端工具，或者当 `name: "*"` 时，为所有没有自己渲染器的工具调用提供回退。它不注册工具：不会向模型通告任何东西，也没有任何东西变得可调用。

这个契约来自 react-core，因此本页与 [React (V2) 的 `useRenderTool`](/reference/v2/hooks/useRenderTool) 描述的是同一种行为；仅导入路径不同。

<Callout type="warn" title="注册工具是另一个钩子">
  如果你希望智能体能够*调用*你的函数并绘制它的 UI，那是 [`useFrontendTool`](/reference/react-native/hooks/useFrontendTool)——它接受 `description`、`handler` 和 `render`，并在每次运行时向模型通告该工具。仅渲染器注册两者都不做：不向模型提供任何东西，也没有任何东西可调用。
</Callout>

<Callout type="warn" title="在 React Native 上它曾经是另一个钩子">
  在 1.68 之前，`@copilotkit/react-native` 以这个名字导出一个**本地**钩子，其整个函数体转发给 `useFrontendTool`，于是它借另一个钩子的名字提供了一种能力——而且 `name: "*"` 会注册一个字面上名为 `*` 的前端工具。1.68 用 react-core 的钩子替换了它，并通过一个已弃用的兼容垫片保持旧调用形态可用；该垫片随后已被移除（[#6976](https://github.com/CopilotKit/CopilotKit/issues/6976)），因此 `description` 与 `handler` 在这里不再能编译，也不再注册工具。

  如果你从早于 1.68 的版本升级，参见[从旧版 React Native 的 `useRenderTool` 迁移](#从旧版-react-native-的-userendertool-迁移)了解要改什么，以及哪些问题编译器不会替你发现。
</Callout>

<Callout type="info">
  `useRenderToolCall` 在 React Native 上**确实**有导出——从 `@copilotkit/react-native` 导入它，即可在任意界面渲染已注册的工具调用，而不限于聊天内部（参见[在聊天之外渲染工具调用](#在聊天之外渲染工具调用)）。其余的 Web 渲染钩子（`useDefaultRenderTool`、`useRenderActivityMessage`、`useRenderCustomMessages`）在 React Native 上**没有**导出，因为它们渲染宿主 DOM 或依赖 Web 的聊天消息栈。
</Callout>

## 签名

有两个重载：一个不接受 schema 的通配符回退，以及一个需要 schema 的具名渲染器。

### 通配符重载

```tsx
import { useRenderTool } from "@copilotkit/react-native";

useRenderTool(
  {
    name: "*",
    render: (props: any) => React.ReactElement | null,
    agentId?: string,
  },
  deps?: ReadonlyArray<unknown>,
);
```

### 具名重载

```tsx
import { useRenderTool } from "@copilotkit/react-native";
import { z } from "zod";

useRenderTool<S extends StandardSchemaV1>(
  {
    name: string,
    parameters: S,
    render: (props: RenderToolProps<S>) => React.ReactElement | null,
    agentId?: string,
  },
  deps?: ReadonlyArray<unknown>,
);
```

`S` 是 **schema** 类型，而不是解析后的参数对象——`render` 内 `props.parameters` 的形态由它推断。

## 参数

<PropertyReference name="config" type="object" required>
  渲染器配置。

  <PropertyReference name="name" type='string | "*"' required>
    要渲染的工具名称。必须与智能体调用的名称一致。`"*"` 选择通配符重载：作为回退，用于任何没有注册同名渲染器的工具调用。
  </PropertyReference>

  <PropertyReference name="parameters" type="S extends StandardSchemaV1" required>
    描述工具参数的 schema，它为 `render` 中的 `props.parameters` 提供类型。接受任何与 [Standard Schema](https://standardschema.dev/) 兼容的 schema（Zod、Valibot、ArkType 等）。

    在具名重载上必填；通配符重载完全不接受 schema，其渲染 props 的类型为 `any`。
  </PropertyReference>

  <PropertyReference name="render" type="(props: RenderToolProps<S>) => React.ReactElement | null" required>
    工具调用的渲染函数。返回 `null` 时不绘制任何东西，这就是隐藏不想展示的工具调用 UI 的方式。

    返回类型是 `ReactElement | null` 而非 `ReactNode`，这在 React Native 上很重要：`FlatList` 无法渲染裸字符串，因此返回裸字符串的渲染器能通过类型检查，然后在运行时抛出异常。本钩子的签名会拒绝它。

    [`useFrontendTool`](/reference/react-native/hooks/useFrontendTool) 的 `render` **没有**这样收窄——它是一个 `React.ComponentType`，返回 `ReactNode`，裸字符串在那里能编译。用 [`FrontendToolRenderFunction<T>`](/reference/react-native/hooks/useFrontendTool#the-render-type-react-native-needs) 标注那个渲染器可获得同样的保护。
  </PropertyReference>

  <PropertyReference name="agentId" type="string">
    将注册表**键**限定到单个智能体。注册按 `agentId:name` 去重，因此 `agentId` 允许两个渲染器在同一个工具名称下共存。

    `agentId` 本身不在钩子的重新注册检查之列，因此如果它来自一个会在运行时变化的值，请把该值也列入 `deps`。
  </PropertyReference>
</PropertyReference>

<PropertyReference name="deps" type="ReadonlyArray<unknown>">
  可选的依赖数组。这些值变化时重新注册渲染器。`render` 函数在**注册时捕获**，只在渲染器重新注册时刷新——它不会在每次渲染时重新读取最新闭包。

  `deps` 对普通数据（字符串、数字、布尔值、`null`、日期，以及由它们构成的普通对象和数组）按值进行比较，因此诸如 `[{ status }]` 这样的内联字面量只在其内容变化时才重新注册。函数与之前一样永远不算变化，所以要把会变化的回调保存在 ref 中。类实例和其他对象按引用（同一性）比较，因此传入来自 `useAgent` 的 `agent` 这类循环引用的值是安全的。增加或移除条目都算变化。参见 [依赖比较](#依赖比较)。
</PropertyReference>

### `RenderToolProps<S>`

具名重载下传给你的 `render` 函数的 props。`@copilotkit/react-native` 从 react-core 重新导出该类型，因此 React Native 与 Web 之间不会产生偏差：

```ts
import type { RenderToolProps } from "@copilotkit/react-native";
```

它是一个以 `status` 判别的三分支联合类型。`parameters` 在进行中分支上是 `Partial<InferSchemaOutput<S>>`，在执行与完成分支上是完整的 `InferSchemaOutput<S>`；`result` 仅在完成分支上是 `string`。读取 `parameters` 字段或 `result` 之前，先按 `status` 收窄。

`S` **没有默认值**，因此类型参数必填：裸写 `RenderToolProps` 会得到 `TS2314: Generic type 'RenderToolProps' requires 1 type argument(s)`。传入 schema 的类型——`RenderToolProps<typeof mySchema>`——或者对于没有自己 schema 的渲染器，传 `RenderToolProps<z.ZodTypeAny>`。

<PropertyReference name="name" type="string">
  正在渲染的工具名称。
</PropertyReference>

<PropertyReference name="toolCallId" type="string">
  该工具调用的唯一 ID。
</PropertyReference>

<PropertyReference name="parameters" type="Partial<InferSchemaOutput<S>> | InferSchemaOutput<S>">
  工具调用参数，类型来自你的 `parameters` schema：进行中分支为部分值（智能体仍在书写调用），执行与完成分支为完整值。

  这种放宽是**类型层面的断言，不是运行时解析**。每个分支收到的是同一个值——原始工具调用参数字符串经 CopilotKit 的部分 JSON 解析器处理后的产物——你的 `parameters` schema 从不会在它到达 `render` 之前被用来校验或强制转换。因此截断或畸形的参数字符串仍会产生部分解析的结果，却带着完整的类型。即便在后面的分支上，也要让渲染器对缺失字段保持防御。
</PropertyReference>

<PropertyReference name="status" type='"inProgress" | "executing" | "complete"'>
  当前工具调用状态，为**字符串字面量**：参数流式传输时为 `"inProgress"`，调用执行时为 `"executing"`，结果可用后为 `"complete"`。

  `ToolCallStatus` 枚举成员（`ToolCallStatus.InProgress`、`ToolCallStatus.Executing`、`ToolCallStatus.Complete`）携带的正是这三个字符串，而字符串枚举成员可赋值给它自己的字面量类型——因此 `status === ToolCallStatus.Complete` 既能编译**也**能像 `status === "complete"` 一样针对该联合类型收窄。用哪种都可以。

  `ToolCallStatus` 仍作为值从 `@copilotkit/react-native` 导出，而且在权威的 `ReactToolCallRenderer` 契约上你实际遇到的就是它——基于该契约编写的渲染器（无论用 `defineToolCallRenderer` 构建，还是把 `render` 传给 `useFrontendTool`），其 `status` 都是枚举成员而非字符串字面量。
</PropertyReference>

<PropertyReference name="result" type="string | undefined">
  该 `toolCallId` 对应的**工具结果消息的内容**——不是 `handler` 返回的值。工具调用通过 `toolCallId` 与其结果关联，渲染器把该消息的 `content` 透传。在完成分支上是 `string`；在另外两个分支上是 `undefined`。

  值得了解的推论：

  - 完成分支之所以被选中，**是因为存在**对应此 `toolCallId` 的工具结果消息，而不是因为某个处理函数结束了。
  - 预构建的 React Native 聊天会在它到达你之前把非字符串的 `content` 序列化：`null` / `undefined` 变成 `""`，其他值做 `JSON.stringify`，两种情况下都会在开发环境发出警告。
  - 在回放时，`result` 来自线程历史中存储的工具消息，因此它能在没有任何处理函数运行的情况下在重新加载后保留。
</PropertyReference>

### `RenderToolInProgressProps`、`RenderToolExecutingProps`、`RenderToolCompleteProps`

`@copilotkit/react-native` 从 react-core 重新导出这三个类型。它们就是上文 `RenderToolProps<S>` 联合类型的各个**分支**，因此你可以直接指名单个状态：

```tsx
import type { RenderToolCompleteProps } from "@copilotkit/react-native";
import { Text } from "react-native";
import { z } from "zod";

const schema = z.object({ city: z.string() });

function WeatherResult(props: RenderToolCompleteProps<typeof schema>) {
  // `props.parameters.city` is a `string`, and `props.result` is a `string`.
  return <Text>{props.parameters.city}: {props.result}</Text>;
}
```

每一个都以 **schema**（`S extends StandardSchemaV1`）为泛型参数，与 `RenderToolProps<S>` 一致。

## 用法

```tsx
import { useRenderTool } from "@copilotkit/react-native";
import { CopilotChat } from "@copilotkit/react-native/components";
import { ActivityIndicator, Text, View } from "react-native";
import { z } from "zod";

function ChatScreen() {
  useRenderTool(
    {
      // A tool your agent executes server-side; this only draws it.
      name: "showWeather",
      parameters: z.object({
        city: z.string(),
        temp: z.number(),
        condition: z.string(),
      }),
      render: ({ status, parameters }) => {
        if (status === "inProgress") return <ActivityIndicator />;
        return (
          <View
            style={{ padding: 12, backgroundColor: "#f0f0f0", borderRadius: 8 }}
          >
            <Text style={{ fontWeight: "bold" }}>{parameters.city}</Text>
            <Text>
              {parameters.temp}°C · {parameters.condition}
            </Text>
          </View>
        );
      },
    },
    [],
  );

  return <CopilotChat agentName="default" />;
}
```

请从 **`/components`** 子路径导入 `CopilotChat`。那才是读取渲染注册表并内联绘制工具调用的预构建 UI；从 `@copilotkit/react-native` 根导出的 `CopilotChat` 是[无头的](/reference/react-native/components/CopilotChat)，不渲染消息列表，因此注册的 `render` 永远不会出现。

### 通配符回退

`"*"` 条目会绘制任何没有同名渲染器的工具调用。它不接受 schema，因此其渲染 props 没有类型：

```tsx
useRenderTool(
  {
    name: "*",
    render: ({ name, status }) => (
      <Text>
        {status === "complete" ? "✓" : "⏳"} {name}
      </Text>
    ),
  },
  [],
);
```

从渲染器返回 `null` 时不绘制任何东西，因此 `render: () => null` 就是让工具调用静默的方式——针对一个具名工具，或者用 `"*"` 时针对所有没有自己渲染器的工具。

## 行为

- **仅渲染器。** 运行时交给智能体的工具列表中不会添加任何东西，模型也无法调用在此注册的名称。
- **`render` 返回 `ReactElement | null`**，而非 `ReactNode`。React Native 的 `FlatList` 无法渲染裸字符串或 portal，本签名强制了这一点。
- **按 `agentId:name` 去重**——同一个键下最新的注册生效。
- **参数流式传输。** 智能体还在书写调用时，`status` 是 `"inProgress"`，`parameters` 是部分值——字段逐步到达。编写能容忍缺失字段的渲染器；正是这一点让 UI 能随智能体的书写逐步构建。
- **`render` 在注册时捕获。** 它不会在每次渲染时刷新——只在渲染器重新注册时刷新，重新注册发生在 `name` 变化或 `deps` 比较为已变化时。如果你的 `render` 闭包引用了随时间变化的组件状态或 props，把它们列入 `deps`，或者通过 ref 读取（见[下文](#依赖比较)）；否则聊天会一直调用过期的闭包并绘制过时的 UI。
- **卸载时不清理。** 渲染器条目被刻意保留，这样聊天历史中已有的工具调用在你离开页面后仍能渲染。

### 依赖比较

钩子把 `deps` 归约为一个版本号
（[源码](https://github.com/CopilotKit/CopilotKit/blob/main/packages/react-core/src/v2/hooks/tool-registration.ts)）
且从不序列化它：

- 普通数据按值比较：字符串、数字、布尔值、`null`、`undefined`、日期，以及由它们构成的普通对象和数组。诸如 `[{ status }]` 或 `[items.filter(isOpen)]` 这样的内联字面量只在其内容变化时才重新注册。键顺序无关紧要。
- 函数与之前一样永远不算变化：`deps` 中的新回调不会触发工具重新注册。通过 ref 读取会变化的回调（见下文）。
- 类实例、`Map`、`Set` 及其他非普通对象按引用（同一性）比较。
- 循环引用的值（例如 `useAgent` 返回的 `agent`）可以安全列出。普通数据内部的循环引用同样安全。
- 增加或移除条目都算变化。

当变化的是行为而非展示数据时，ref 可以完全避免重新注册。把值保存在 ref 中，`render` 运行时解引用它：

```tsx
function SeatPicker({ onSelect }: { onSelect: (id: string) => void }) {
  // Reassigned on every render; the captured `render` reads it at call time.
  const onSelectRef = useRef(onSelect);
  onSelectRef.current = onSelect;

  useRenderTool(
    {
      name: "pickSeat",
      parameters: z.object({ seats: z.array(z.string()) }),
      render: ({ parameters }) => (
        <SeatGrid
          seats={parameters.seats ?? []}
          onSelect={(id) => onSelectRef.current(id)}
        />
      ),
    },
    [],
  );
}
```

被捕获的 `render` 仍是过期的那个，但它读取的 ref 是最新的，因此渲染器无需重新注册就能用到最新的回调。这使得当变化的是行为而非展示数据时，ref 模式是更可靠的默认选择。

## 在聊天之外渲染工具调用

[`CopilotChat`](/reference/react-native/components/CopilotChat#prebuilt-ui) 会内联渲染工具调用。要在其他任何地方渲染已注册的组件——仪表盘、自助终端、智能体编排的全屏舞台——在挂载于 `CopilotKitProvider` 之下的组件内调用 `useRenderToolCall()`，并从智能体自己的消息列表中读取工具调用：

```tsx
import { useAgent, useRenderToolCall } from "@copilotkit/react-native";
import { View } from "react-native";

function ToolCallStage({ agentId = "default" }: { agentId?: string }) {
  const { agent } = useAgent({ agentId });
  const renderToolCall = useRenderToolCall();

  const messages = agent.messages ?? [];

  // Pair each call with its result message — the same correlation the prebuilt
  // chat does. `toolMessage` is what selects the complete arm: pass it and the
  // call resolves to `"complete"` with `result`. Without one, `result` is
  // `undefined` and the status comes from the provider instead — `"executing"`
  // while this call id is one the provider is tracking as executing, and
  // `"inProgress"` otherwise.
  const toolMessages = new Map(
    messages.flatMap((message) =>
      message.role === "tool" ? [[message.toolCallId, message] as const] : [],
    ),
  );

  const toolCalls = messages.flatMap((message) =>
    message.role === "assistant" ? (message.toolCalls ?? []) : [],
  );

  // Each returned element is already keyed by tool-call id.
  return (
    <View>
      {toolCalls.map((toolCall) =>
        renderToolCall({
          toolCall,
          toolMessage: toolMessages.get(toolCall.id),
        }),
      )}
    </View>
  );
}
```

<PropertyReference name="useRenderToolCall" type="() => (input: { toolCall, toolMessage? }) => ReactElement | null">
  返回一个函数，用为该调用注册的渲染函数渲染单个工具调用。优先精确名称匹配，回退到 `"*"` 条目，两者都不存在时返回 `null`。参数经过部分解析，因此组件能随智能体书写调用而逐步绘制。
</PropertyReference>

## 从旧版 React Native 的 `useRenderTool` 迁移

React Native 曾以这个名字导出一个**本地**钩子。它不是 react-core 的 `useRenderTool`：它的整个函数体转发给 react-core 的*另一个*钩子 `useFrontendTool`，于是它在顶着仅渲染器钩子名字的同时，注册了工具**和**渲染器。

1.68 删除了那个钩子，把名字指向 react-core 的钩子，中间隔着一个已弃用的兼容垫片，它把旧形态的调用按旧钩子的方式路由，并在开发环境发出警告。**垫片已经移除。** `@copilotkit/react-native` 现在直接重新导出 react-core 的 `useRenderTool`，自身不携带任何渲染工具实现，因此本页描述的就是这个名字的全部行为。

### 需要改什么

下表的大多数行都是编译错误，因此无论你是否先读本页，编译器都会把你带到这里。例外是第一行，它只在 TypeScript 的多余属性检查能够触及的地方才失败——参见[编译器看不见的三种形态](#编译器看不见的三种形态)了解它检查不到的调用形态。

由于该钩子是**重载的**，多余的 `description` 或 `handler` 会报告为 `TS2769: No overload matches this call`，而不是单签名函数上你会得到的裸 `TS2353`。多余属性在嵌套的逐重载细节中被点名，所以请读完第一行继续往下看。

| 之前（旧版 RN 钩子） | 改成 | 不改会怎样 |
| --- | --- | --- |
| `useRenderTool({ name, description, parameters, handler, render }, deps)` | `useFrontendTool({ …对象完全相同 }, deps)`——仅改名 | **`TS2769: No overload matches this call`**，在具名重载下点名 `description`——但参见[编译器看不见的三种形态](#编译器看不见的三种形态)，那些情况下它能编译通过，而工具会静默停止注册 |
| 仅渲染器注册：TypeScript 中不可能（`description` 是必填的），纯 JS 可以触达 | `useRenderTool({ name, parameters, render, agentId? }, deps)`——具名渲染器要求 `parameters` | 本来就正确；无需操作 |
| 通配符：注册一个名为 `*` 的工具 | `useRenderTool({ name: "*", render })`——唯一不需要 schema 的情况 | **`TS2769`**——`description` / `handler` / `parameters` 不在这个重载上；删掉它们 |
| 渲染 props `{ args, status, … }` | `{ parameters, status, … }` | **`TS2339: Property 'args' does not exist on type 'RenderToolProps<…>'**。（通配符重载的 props 类型是 `any`，所以 `args` 在那里仍能编译。） |
| `RenderToolProps<T>`（args 形态，以解析后的参数为泛型） | `RenderToolProps<S>`（parameters 形态，以 schema 为泛型） | 从 react-core 重新导出 |
| 裸写 `RenderToolProps`——RN 版有默认 `T = Record<string, unknown>` | `RenderToolProps<typeof mySchema>` | **`TS2314: Generic type 'RenderToolProps' requires 1 type argument(s)`**。core 的 `S` 没有默认值，因此无类型渲染器的自然写法不再能编译 |
| `UseRenderToolOptions<T>` | 已移除——把配置写成内联形式（`RenderToolConfig` 是 core 内部类型） | 导入时报 `TS2305` |
| `RenderToolFunction<T>` | 对 `useRenderTool` 渲染器：无需改动，钩子已把 `render` 声明为 `ReactElement \| null`。对 `useFrontendTool` 渲染器：[`FrontendToolRenderFunction<T>`](/reference/react-native/hooks/useFrontendTool#the-render-type-react-native-needs) | 导入时报 `TS2305` |

没有一个可用于标注调用的导出配置类型，这是刻意的而非疏忽。`RenderToolConfig`——core 对该形态的内部命名，声明时没有 `export`，只被实现签名引用——**比重载实际接受的更宽松**：它声明的是 `parameters?: S`，因此它会允许不带 schema 的 `{ name: "showWeather", render }`，而具名重载会拒绝这种调用。导出它等于交给你一个描述编译器所拒绝调用的类型。把配置写成内联对象字面量，让重载去推断。`RenderToolProps<S>` **是**导出的，它才是你标注独立渲染函数所用的类型。

如果你的调用点想要一个**可调用**的工具，`useFrontendTool` 只是改名而已——它接受同一个对象，包括 `description` 和 `handler`。如果它只是为智能体已有的工具绘制 UI，去掉 `description`（以及 `handler`，如果你传过），并把 `args` 改名为 `parameters`。

通配符是行为变得更好而非仅仅搬家的情况。旧钩子上的 `name: "*"` 会注册一个**字面命名为** `*` 的前端工具，没有描述也没有 schema。

那个工具从未被提供给模型——core 会把名称 `*` 从交给智能体的工具列表中过滤掉，正是为了不让智能体被提供一个名字是通配符的工具。后果出现在别处，而且对写它的人更糟。`*` 是 core 的**兜底处理函数**名称：当一个工具调用既没有匹配的前端工具也没有结果时，core 会求助于 `*` 工具并运行它的通配符路径——而在这条路径中，工具结果的插入与后续轮次的请求位于“通配符工具是否真的有 `handler`”这一检查的**外部**。一个没有 `handler` 的 `*` 工具——恰恰是想要纯展示回退的人会写出的东西——因此仍会用**空工具结果**应答该调用，并且仍会请求下一轮。

用两种写法各驱动一轮就能直接看到差异：一条调用无人注册工具的助手消息，经旧钩子会产生两轮和一个空工具结果，经本钩子只产生一轮且没有工具结果。影响范围是有界的——只有既没有同名工具*又*尚无结果的工具调用才会走到那条路径，因此结果已经到达的服务端调用从未受影响。

在 core 的钩子上，`"*"` 与它在 Web 上一样：一个无 schema 的回退渲染器，完全不注册工具。

### 编译器看不见的三种形态

`description` 与 `handler` 在这个钩子上现在是编译错误——但只在 TypeScript 的**多余属性检查**真正生效的地方，也就是写在**全新**对象字面量内联的属性上。有三种形态能绕过它，而且三者都能干净地编译，同时工具静默停止注册：不再向模型通告任何东西，`handler` 也不再运行。

它们也是屏幕上看起来毫无变化的形态。React-core 的渲染器桥会向你的渲染器展开 `{ ...props, parameters: props.args }`，因此旧的 `render: ({ args }) => …` 的绘制效果与从前完全一样。UI 一模一样；工具没了。在 1.68 到垫片移除之间发布的已弃用垫片，在开发环境警告的正是这类代码——垫片没了，就再没有任何东西发出警告。**请人工审计这些代码。**

1. **提升的配置对象。** 先把配置赋给一个变量再传入变量，多余的 `description` 就不再是多余的：

   ```tsx
   const cfg = {
     name: "showWeather",
     description: "Show weather info",
     parameters: z.object({ city: z.string() }),
     handler: async ({ city }: { city: string }) => fetchWeather(city),
     render: () => <WeatherCard city="Berlin" />, // ignores its props
   };
   useRenderTool(cfg); // compiles clean, registers a renderer and nothing else
   ```

   一个其 `render` *确实*解构了 `args` 的提升配置无论如何都会被抓住——render 参数是逆变的，所以它会在 `render` 上失败——因此这里特指“提升**且** `render` 忽略其 props”的组合。

2. **展开携带的字段。** 同样的原因，而且它能逃过调用点处的全新字面量：多余属性检查触及不到经展开传入的属性，因此旧的 `description` 不会被标记。

   ```tsx
   const base = {
     name: "showWeather",
     description: "Show weather",
     parameters: z.object({ city: z.string() }),
   };
   useRenderTool({ ...base, render: () => <WeatherCard city="Berlin" /> }); // compiles clean
   ```

   与上文完全一样，*确实*解构 `args` 的 `render` 会因逆变被抓住。

3. **无类型的调用点。** 纯 JavaScript 的屏幕，或处于 `@ts-nocheck` 之下的屏幕，什么都不检查它。

如果你有 JavaScript 的 React Native 屏幕，grep 一下 `useRenderTool`，逐个调用点判断它想要的是工具（`useFrontendTool`）还是仅渲染器。在这些文件上编译器永远不会替你做这件事。

### 两种情况下看起来都正确的形态

`{ name, parameters, render }`——没有 `description`，没有 `handler`——是唯一同时满足以下两点的调用：

- **正确的**仅渲染器写法，即本页所记录的；以及
- 过去会注册并通告真实工具的**旧式纯 JS 调用**。

两者是同一个对象，没有任何东西能区分它们。`description` 在旧钩子的类型中是必填的，因此 TypeScript 调用者永远写不出这个形态——但无类型的 JavaScript 调用者可以。在旧钩子上，`handler` 是可选的，也没有任何机制会因为缺少它而过滤掉某个工具，所以 `{ name, parameters, render }` 会注册 `name` **并通告给模型**，附带一个空描述。

如今它注册一个渲染器，仅此而已。如果你依赖它通告工具，把这个调用移到 [`useFrontendTool`](/reference/react-native/hooks/useFrontendTool)。如果你只是想为别人拥有的工具绘制 UI，那它已经是对的。

### `status` 不是破坏性变更

旧钩子的渲染 props 把 `status` 类型定义为 `ToolCallStatus` **枚举**；core 的 `RenderToolProps` 把它定义为字符串字面量 `"inProgress" |
"executing" | "complete"`。**这不需要任何迁移工作。** 字符串枚举成员可赋值给它自己的字面量类型，因此 `status === ToolCallStatus.Complete` 能编译*也*能针对字面量联合收窄——现有的枚举比较原样继续工作。两种形式都行；选定一种并保持一致。

`ToolCallStatus` 仍是 `@copilotkit/react-native` 的值导出，而且在权威的 `ReactToolCallRenderer` 契约生效的地方你遇到的仍是这个形态：用 `defineToolCallRenderer` 构建的渲染器，或传给 `useFrontendTool` 的 `render`，收到的 `status` 是枚举成员。
