---
title: StoreConfig
description: 配置每线程状态、StateStore 后端、会话记录与轮次并发控制。
---

`StoreConfig` 是 `createChannel({ store })` 的取值。

```ts
interface StoreConfig<TStateSchema> {
  adapter?: StateStore;
  state?: TStateSchema;
  transcripts?: TranscriptsConfig;
  actionRetentionMs?: number;
  concurrency?: "parallel" | "serial" | "drop";
  /** @deprecated Prefer `concurrency`. */
  onLockConflict?:
    | "drop"
    | "force"
    | ((
        conversationKey: string,
        message: IncomingMessage,
      ) => "drop" | "force" | Promise<"drop" | "force">);
  lockTtl?: number;
  dedupTtl?: number;
}
```

| 选项                | 默认值                    | 行为                                                                                                                                               |
| ------------------- | ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `adapter`           | `MemoryStore`             | SDK 状态的持久化后端。                                                                                                                             |
| `state`             | 无                        | 对 `thread.state()` 与 `setState()` 进行类型定义和校验的 Standard Schema。                                                                         |
| `transcripts`       | 无                        | 可选的保留策略与每用户上限，以顶层 `identifyUser` 得到的应用用户为键。                                                                             |
| `actionRetentionMs` | `604_800_000`             | 持久回调与一次性 HITL 延续的保留时长。                                                                                                             |
| `concurrency`       | `"parallel"`              | 同一会话上重叠轮次的处理方式（见下文）。                                                                                                           |
| `onLockConflict`    | （映射进 `concurrency`）  | **已弃用**。请改用 `concurrency`。静态值 `"drop"` / `"force"` 分别映射为 `"drop"` / `"parallel"`。使用回调则保留旧版独占锁路径。                    |
| `lockTtl`           | `60_000`                  | 每会话轮次锁的 TTL（毫秒），供 `drop` / 旧版锁路径使用。                                                                                           |
| `dedupTtl`          | `300_000`                 | 入站事件的去重窗口（毫秒）。                                                                                                                       |

### 轮次并发

| 模式                   | 行为                                                                                                                                       |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `"parallel"`（默认）   | 同一会话上重叠的轮次一起运行。多人在同一个 Slack 线程中提问，每人都会得到并发回复。                                                        |
| `"serial"`             | 同一会话上的后续轮次会等待进行中的轮次完成（每会话队列）。                                                                                 |
| `"drop"`               | 当已有轮次在进行中时，后续轮次将被丢弃。                                                                                                   |

配置为**单例**的智能体（`agent: sharedInstance`）会在底层通过 `agent.clone()` 按次运行隔离，因此并行模式不会修改同一个共享智能体对象。若想显式掌控，建议改用智能体工厂：

```ts
agent: (threadId) => {
  const a = new HttpAgent({ url });
  a.threadId = threadId;
  return a;
};
```

```ts
const stateSchema = z.object({
  stage: z.enum(["draft", "review", "done"]),
});

const channel = createChannel({
  name: "support-slack",
  identifyUser: "platform",
  agent: makeAgent,
  store: {
    adapter: durableStateStore,
    state: stateSchema,
    // Opt into one-at-a-time processing for stateful workflows:
    // concurrency: "serial",
  },
});
```

`thread.setState(value)` 会替换整个已存储的值，并依据 `state` 对其进行校验。它不会合并补丁。在 `"parallel"` 下，同时调用 `setState` 的并发轮次可能产生竞态——对于依赖独占式状态更新的工作流，请使用 `"serial"`。

在托管路径上，Intelligence 负责跨实例的投递认领与有序的提供方副作用。托管准入还会保证一个 Runtime 上同一时间只有一个规范 Thread 投递处于活动状态，因此 `"parallel"` 并不会提高该投递上限。SDK 存储仍然掌管应用状态与回调快照。
