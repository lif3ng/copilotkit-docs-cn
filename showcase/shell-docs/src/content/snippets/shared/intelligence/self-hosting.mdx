## 概览

CopilotKit Intelligence——为线程、共享状态和 inspector 提供支撑的平台——可以使用 `copilot-intelligence` Helm chart 自托管在你自己的 Kubernetes 集群上。控制平面与数据平面都运行在你自己的网络边界之内；身份、存储与密钥则由你全权掌管。

**你需要自备：**

- Postgres 与 Redis——用你自己的，或使用内置的 Bitnami 子 chart
- 一个用于身份验证的 OIDC 提供方
- 密钥来源：External Secrets Operator、直接创建 Kubernetes Secrets，或由 chart 托管的凭据

**chart 会部署：**

| 组件                            | 作用                                | 端口 |
| ------------------------------- | ----------------------------------- | ---- |
| `app-api`                       | 后端服务                            | 4201 |
| `app-frontend`                  | Web UI                              | 8080 |
| `realtime-gateway` _（可选）_   | 用于实时同步的 WebSocket 服务       | 4401 |

此外还包括一个 `database-migrations` Job、一个 `thread-culler` CronJob，以及常见的配套资源（Services、Ingress、HPA、PodDisruptionBudgets、ConfigMaps，以及启用 ESO 时的 ExternalSecret 资源）。

## 什么时候应该使用它？

- 出于合规、数据驻留或安全原因，你的组织要求 CopilotKit Intelligence 运行在自己的 VPC 或数据中心内
- 你想把 CopilotKit Intelligence 连接到云托管版本无法访问的内部数据库、身份提供方或密钥存储
- 你需要在你现有的 Kubernetes 工具链、CI/CD 和监控体系下运维该平台
- 你拥有 CopilotKit Intelligence 许可证，并具备运行生产级 Kubernetes 工作负载的平台工程能力

<Callout type="info" title="在正式集群之前先在本地验证">
这套 chart 在本地 Docker Desktop 或 k3d 集群上的安装方式与在生产集群上完全相同，所以请先在笔记本上完整走一遍本指南。本地有两条路径可选：

- **内置 overlay**——使用 chart 自带的 `values-quickstart-local.yaml` overlay 安装。它会启用集群内 Postgres、Redis 以及（可选的）Keycloak；安装过程由你自己按照本指南操作。
- **一键脚本**——`scripts/local-demo.sh` 用一条命令拉起一个一次性的 k3d 集群、从 GHCR 安装已发布的 chart，并启动内置 Keycloak：

```bash title="Terminal"
./scripts/local-demo.sh --version <chart-version>
```

两条路径都使用下文描述的同一套安装命令——选适合你的即可。

</Callout>

## 前置条件

开始之前，请确认以下事项已就绪。[CopilotKit Intelligence 架构](/intelligence/intelligence-platform)更深入地解释了应用/运行时/平台各分层。

**许可证与 registry 访问：**

- 有效的 CopilotKit Intelligence 许可证密钥（如尚未拥有，请联系你的 CopilotKit 客户团队）
- 对 chart OCI registry `oci://ghcr.io/copilotkit/charts/intelligence` 的读取权限（已发布的 chart 允许匿名拉取）
- 最新发布的 chart 版本。请在 GHCR 上查看 [chart releases](https://github.com/CopilotKit/Intelligence/pkgs/container/charts%2Fintelligence)，并把版本值代入本指南通篇使用的 `<chart-version>` 占位符（例如 `0.1.0-rc.16`）。

**集群与工具：**

- Kubernetes ≥ 1.28
- Helm ≥ 3.12
- `kubectl` 已配置指向目标集群、使用管理员等效的 context

**平台前置组件（集群范围，只需安装一次）：**

- 一个 ingress controller——`nginx-ingress` 或 AWS Load Balancer Controller 均可
- `cert-manager`（或 AWS ACM 等云端托管证书替代方案），用于公共主机名的 TLS
- `External Secrets Operator`：如果你打算从 AWS Secrets Manager、HashiCorp Vault 或 GCP Secret Manager 同步密钥（生产环境推荐，但非必需——参见 [Secrets](#create-secrets)）

**外部依赖（集群可访问）：**

- PostgreSQL ≥ 14——托管服务（Amazon RDS、Aurora、Cloud SQL）或通过 operator 部署在集群内
- Redis ≥ 7（或 Valkey 兼容服务，例如 Amazon ElastiCache）
- 一个 OIDC 身份提供方——Keycloak、Okta、Azure AD、Auth0、Google Workspace 或同类产品

**可选：**

- Amazon OpenSearch（仅在使用分析功能时需要）
- S3 兼容的对象存储（仅在 realtime gateway 配置为持久化 AG-UI 事件时需要）

## 实施步骤

<Steps>
  <Step>
    ### 准备 Kubernetes 集群

    确保 `kubectl` 指向将要运行 CopilotKit Intelligence 的集群。

    ```bash title="Terminal"
    kubectl config current-context
    kubectl auth can-i create namespace --all-namespaces
    ```

    确认 context 对应你的目标集群，且权限检查返回 `yes`。如果不是，请先修正 kubeconfig 再继续。

  </Step>

  <Step>
    ### 安装平台前置组件

    这些组件作用于整个集群，每个集群只需安装一次，与应用 chart 相互独立。

    <Tabs items={["AWS（EKS）", "本地部署 / 通用", "本地（Docker Desktop / k3d）"]}>
      <Tab value="AWS（EKS）">
        ```bash title="Terminal"
        # AWS Load Balancer Controller（kube-system）
        helm repo add eks https://aws.github.io/eks-charts
        helm install aws-load-balancer-controller eks/aws-load-balancer-controller \
          -n kube-system \
          --set clusterName=<YOUR_CLUSTER_NAME>

        # cert-manager
        helm repo add jetstack https://charts.jetstack.io
        helm install cert-manager jetstack/cert-manager \
          -n cert-manager --create-namespace \
          --set installCRDs=true

        # External Secrets Operator（可选——见 Secrets 步骤）
        helm repo add external-secrets https://charts.external-secrets.io
        helm install external-secrets external-secrets/external-secrets \
          -n external-secrets --create-namespace
        ```
      </Tab>
      <Tab value="本地部署 / 通用">
        ```bash title="Terminal"
        # NGINX Ingress Controller
        helm repo add ingress-nginx https://kubernetes.github.io/ingress-nginx
        helm install ingress-nginx ingress-nginx/ingress-nginx \
          -n ingress-nginx --create-namespace

        # cert-manager
        helm repo add jetstack https://charts.jetstack.io
        helm install cert-manager jetstack/cert-manager \
          -n cert-manager --create-namespace \
          --set installCRDs=true
        ```
      </Tab>
      <Tab value="本地（Docker Desktop / k3d）">
        ```bash title="Terminal"
        # NGINX Ingress Controller 使用 ClusterIP——稍后你会通过
        # `kubectl port-forward` 访问它，因此不需要 LoadBalancer 服务。
        helm upgrade --install ingress-nginx ingress-nginx \
          --repo https://kubernetes.github.io/ingress-nginx \
          --namespace ingress-nginx --create-namespace \
          --set controller.service.type=ClusterIP \
          --wait
        ```

        本地验证时无需 cert-manager 与 External Secrets Operator——TLS 在集群外终止，密钥由 chart 托管（即下文路径 C）或手动预先创建（路径 B）。
      </Tab>
    </Tabs>

    各 controller 运行起来之后，其 Pod 应在各自的命名空间中处于 `Ready` 状态。

  </Step>

  <Step>
    ### 预置外部依赖

    智能中枢需要 Postgres、Redis 和一个 OIDC issuer。你既可以让 chart 指向你已经在用的托管服务，也可以启用内置的 Bitnami 子 chart 在集群内运行 Postgres 和 Redis（适合评估和小型自托管安装）。

    **使用托管服务（生产环境推荐）：**

    - 创建 Postgres 数据库和用户。记录主机、端口（默认 `5432`）、数据库名、用户名和密码。
    - 创建启用 TLS 的 Redis 实例。记录主机、端口（默认 `6379`）和密码。
    - 在你的身份提供方中配置一个 OIDC client。记录 issuer URL、client ID 和 client secret。

    **使用内置的集群内子 chart：**

    在 values 文件中设置 `postgresql.enabled: true` 和 `redis-subchart.enabled: true`（下一步会讲到）。集群中必须存在匹配的 `StorageClass`。如果你在评估时还需要一个快速可用的 OIDC 提供方，可以通过 `keycloak.enabled: true` 启用内置 Keycloak 子 chart；生产工作负载不要使用内置 Keycloak。它创建的 realm 和凭据参见[内置 Keycloak（仅用于评估）](#内置-keycloak仅用于评估)。

    chart 自带了一个针对这种形态经过测试的 overlay——`values-quickstart-local.yaml`——它会启用内置 Postgres + Redis、设置 `migrations.enabled: true`、按笔记本规格分配资源，并创建一次性密钥，让安装无需任何手工准备即可端到端跑通。在它之上叠加你自己的 overlay（见下一步），接入你的 IdP 和 ingress。

  </Step>

  <Step>
    ### 创建 values 文件

    已发布的 chart 附带了多个针对常见部署形态的示例 values 文件。选择与你环境最接近的一个，复制成一份可编辑的工作 overlay。先拉取并解包 chart，以便在本地留有可对比的副本：

    ```bash title="Terminal"
    helm pull oci://ghcr.io/copilotkit/charts/intelligence --version <chart-version> --untar

    # AWS 风味（ALB、IRSA、来自 AWS Secrets Manager 的 External Secrets）
    cp intelligence/values-aws-example.yaml my-values.yaml

    # 或者本地部署风味（nginx、手动管理 Kubernetes Secrets）
    cp intelligence/values-onprem-example.yaml my-values.yaml

    # 或者自托管评估（内置 Keycloak + 集群内 Postgres/Redis）
    cp intelligence/values-self-hosted-eval.yaml.example my-values.yaml
    ```

    chart 解包后得到名为 `intelligence/` 的目录（即 GHCR 上发布的 chart 名称；chart 的 `nameOverride` 会让带 release 前缀的资源保持 `cpki-*` 命名）。

    编辑 `my-values.yaml`，至少设置：

    - `database.host`、`database.port`、`database.name`——你的 Postgres 连接信息（`name` 默认为 `intelligence`）
    - `redis.host`、`redis.port`、`redis.tls`——你的 Redis 连接（TLS 默认开启；托管 Redis 要求开启）
    - `auth.issuer`——你的 OIDC 提供方的 issuer URL
    - `auth.existingSecret`——包含 `auth-secret`、`auth-client-id`、`auth-client-secret` 的 Kubernetes Secret 名称（或使用 [Secrets](#create-secrets) 中的其他路径之一）
    - `ingress.ui.host`——用户加载智能中枢 UI 所用的主机名（例如 `intelligence.example.com`）
    - `ingress.api.host`——可选的独立 API 主机名。省略时，`ui.host` 规则会把 `/api` 和 `/auth` 路径路由到 `app-api`，因此对多数安装来说单一主机名即可。
    - `ingress.tls`——上述主机名的 TLS 配置
    - `migrations.enabled: true`——**首次安装时必需**；默认为 `false`。不设置它，数据库 schema 永远不会被应用，`app-api` 会不断崩溃重启。（如果你在评估 overlay `values-quickstart-local.yaml` 之上叠加配置，它会替你设置好。）

    <Callout type="warn" title="OIDC issuer URL——末尾斜杠很重要">
      部分提供方（尤其是 Auth0）只接受带末尾斜杠的 issuer URL（例如 `https://your-tenant.auth0.com/`）。少写或多写一个斜杠，登录时就会出现一个含义模糊的 “issuer mismatch” 失败。该值必须与你的提供方 discovery 端点公布的值完全一致。
    </Callout>

    完整的取值参见[配置参考](#配置参考)一节。

  </Step>

  <Step id="create-secrets">
    ### 创建 Secrets

    chart 支持三条密钥管理路径。只能选择其中一条。

    **路径 A——External Secrets Operator（生产环境推荐）：**

    1. 确保你的密钥后端（AWS Secrets Manager、Vault 等）中已有数据库 URL、Redis URL 和身份验证凭据对应的条目。
    2. 创建引用该后端的 `ClusterSecretStore`（或 `SecretStore`）。
    3. 在 `my-values.yaml` 中相应设置 `externalSecrets.enabled: true`、`externalSecrets.store.kind` 和 `externalSecrets.store.name`。chart 随后会生成 `ExternalSecret` 资源，把这些条目同步成 Kubernetes Secrets，命名与 `app-api` 的预期一致。

    **路径 B——直接使用 Kubernetes Secrets（轮换由你自行管理）：**

    保持 `externalSecrets.enabled: false`（默认值），在安装前手动创建 Secrets：

    ```bash title="Terminal"
    kubectl create namespace copilot-intelligence

    kubectl create secret generic cpki-db \
      --from-literal=database-url='postgresql://user:pass@host:5432/intelligence' \
      -n copilot-intelligence

    kubectl create secret generic cpki-redis \
      --from-literal=redis-url='rediss://:password@host:6379' \
      -n copilot-intelligence

    kubectl create secret generic cpki-auth \
      --from-literal=auth-secret="$(openssl rand -hex 32)" \
      --from-literal=auth-client-id='<OIDC client id>' \
      --from-literal=auth-client-secret='<OIDC client secret>' \
      -n copilot-intelligence
    ```

    在 values 文件中通过 `database.existingSecret`、`redis.existingSecret` 和 `auth.existingSecret` 引用这些名称。Secret 的键为小写连字符格式（`auth-secret`、`database-url`、`runner-auth-secret`）；工作负载则以对应的大写环境变量（`AUTH_SECRET`、`DATABASE_URL`、`RUNNER_AUTH_SECRET`）消费它们。

    **路径 C——由 chart 托管密钥（最简单的 BYOC 方式）：**

    适用于你没有运行密钥管理服务、希望 Helm 直接根据安装时提供的值创建 Kubernetes Secrets 的场景。设置 `selfHostedSecrets.enabled: true` 并内联提供凭据：

    ```yaml title="my-values.yaml"
    selfHostedSecrets:
      enabled: true
      db:
        url: "postgresql://user:pass@host:5432/intelligence"
      redis:
        url: "rediss://:password@host:6379"
      auth:
        # Auto-generated when left empty.
        secret: ""
        clientId: "<OIDC client id>"
        clientSecret: "<OIDC client secret>"
      realtimeGateway:
        # Auto-generated when left empty.
        runnerAuthSecret: ""
        secretKeyBase: ""
      beam:
        # Auto-generated when left empty.
        releaseCookie: ""
    ```

    这些字段留空时，chart 会自动生成 `auth.secret`、realtime-gateway 的 runner/key-base 以及 BEAM cookie，因此你只需提供手头实际拥有的值。

  </Step>

  <Step>
    ### 安装 chart

    release 可以直接从 GHCR OCI registry 安装——安装本身不需要先在本地解包。使用 `helm upgrade --install`，同一命令既可用于首次安装，也可用于升级。

    ```bash title="Terminal"
    helm upgrade --install copilot-intelligence \
      oci://ghcr.io/copilotkit/charts/intelligence \
      --version <chart-version> \
      -f my-values.yaml \
      -n copilot-intelligence \
      --create-namespace \
      --wait \
      --timeout 10m
    ```

    支持叠加多个 values 文件，这也是评估时的推荐模式：把 chart 自带的 `values-quickstart-local.yaml`（集群内 Postgres/Redis、评估规格资源、`migrations.enabled: true`、一次性密钥）与你自己的 overlay（IdP、ingress 等集群特定配置）组合起来。先拉取 chart，以便在本地留有 `values-quickstart-local.yaml` 副本可供引用：

    ```bash title="Terminal"
    helm upgrade --install copilot-intelligence \
      oci://ghcr.io/copilotkit/charts/intelligence \
      --version <chart-version> \
      -f intelligence/values-quickstart-local.yaml \
      -f my-values.yaml \
      -n copilot-intelligence --create-namespace \
      --wait --timeout 10m
    ```

    `--wait` 会阻塞到所有 `Deployments` 副本报告健康为止；`--timeout 10m` 为镜像拉取和首次数据库迁移 Job 留出足够时间。冲突时以最右侧的 `-f` 文件为准，所以请把你的 overlay 放在最后。

    <Callout type="info" title="migrations Job 何时运行">
    密钥预先创建时（上文路径 A 或路径 B），migrations Job 会作为 **pre-install/pre-upgrade** 钩子（weight `-5`）运行，从而在应用 Pod 启动前 schema 就已就绪。密钥由 Helm 托管时（路径 C，或使用 `postgresql.enabled: true` 时），它会作为 **post-install/post-upgrade** 钩子（weight `5`）运行，因为在 Helm 创建这些 Secret 资源之前它们并不存在。
    </Callout>

  </Step>

  <Step>
    ### 验证安装

    检查所有 Pod 是否处于 `Running` 状态、ingress 是否就绪：

    ```bash title="Terminal"
    kubectl get pods -n copilot-intelligence
    kubectl get ingress -n copilot-intelligence
    ```

    你应该能看到 `app-api`、`app-frontend`，以及（如已启用）`realtime-gateway` 的 Pod 在运行。migrations `Job` 会显示为 `Completed`。

    确认 API 健康检查返回 `ok`：

    ```bash title="Terminal"
    curl https://<ingress.api.host>/api/health
    ```

    只有数据库可达时，该端点才会返回 `200 OK`——健康检查失败几乎总是数据库连接问题。

    各服务专属的健康端点，向单个 Pod 做端口转发时很有用：

    | 服务              | 路径          |
    |-------------------|---------------|
    | `app-api`         | `/api/health` |
    | `app-frontend`    | `/healthz`    |
    | `realtime-gateway`| `/health`     |

    最后，在浏览器打开 `https://<ingress.ui.host>`，通过你的 OIDC 提供方登录。登录成功即证明端到端链路已打通。

    <Callout type="info" title="本地验证——对 ingress controller 做端口转发">
    在没有公共 DNS 名称的本地集群（Docker Desktop、k3d）上，应针对 **ingress controller** 而非前端服务做端口转发，这样 UI 主机规则仍能把 `/api` 和 `/auth` 路由到 `app-api`。在 overlay 中设置 `ingress.ui.host: "localhost"`，然后在使用应用期间保持该终端开启：

    ```bash title="Terminal"
    kubectl -n ingress-nginx port-forward svc/ingress-nginx-controller 8080:80
    ```

    在浏览器打开 `http://localhost:8080`。直接对 `app-frontend` 服务做端口转发会绕过 ingress，破坏 `/api` 和 `/auth` 路由。
    </Callout>

  </Step>

  <Step>
    ### 升级与卸载

    **升级**——把安装命令中的版本号提高后重新执行。由于安装命令本就使用 `helm upgrade --install`，同一调用既适用于全新安装，也适用于升级：

    ```bash title="Terminal"
    helm upgrade --install copilot-intelligence \
      oci://ghcr.io/copilotkit/charts/intelligence \
      --version <new-chart-version> \
      -f my-values.yaml \
      -n copilot-intelligence \
      --wait
    ```

    升级前，先为目标版本重新生成示例 values（`helm pull ... --version <new-chart-version> --untar`），与你的 overlay 做对比，以便发现新增的键。

    **卸载**——如果启用了内置子 chart，release 卸载后默认会保留 PersistentVolume；如果你打算彻底清除数据，请手动删除它们。

    ```bash title="Terminal"
    helm uninstall copilot-intelligence -n copilot-intelligence
    ```

  </Step>
</Steps>

## 内置 Keycloak（仅用于评估）

设置 `keycloak.enabled: true` 后，chart 会部署 Bitnami Keycloak 子 chart，其中预置了一个 realm 和演示用户。这仅用于评估和演示——不适合生产环境。realm 导入会创建：

- **Realm**：`cpk-dev`
- **OIDC client**：`cpk-self-hosted`，secret 为 `cpk-self-hosted-secret`（可通过 `auth.keycloakClient.clientId` / `auth.keycloakClient.clientSecret` 覆盖）
- **演示用户**：`engineer` / `engineer`（可通过 `auth.keycloakDemoUser` 覆盖）
- **Redirect URI / web origins**：默认 `["*"]` 以便评估灵活使用（可通过 `auth.keycloakClient.redirectUris` / `webOrigins` 覆盖）

chart 会自动把 `auth.issuer` 接到集群内的 Keycloak 服务上，因此在 `keycloak.enabled: true` 时把 `auth.issuer` 留空是有意为之。

生产级自托管部署请保持 `keycloak.enabled: false`，并把 `auth.issuer` 指向你自己的 IdP。
